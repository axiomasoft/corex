## A1 — Major / issue: перенос меняет Composer metadata, но оставляет старые имена в lock

**Место:** [P03.2.md](../plans/2026.09.27-№1-COREX-KERNEL/phases/P03/P03.2.md), Files / Validation;
[P03-design.md:68](../plans/2026.09.27-№1-COREX-KERNEL/research/P03-design.md#42-p032--перенос-по-карте), шаги переноса;
`p03-transfer.py:127–134`, переиспользуемый `p02-transfer.py:27,300–328`.

Литеральный проход меняет `extra.corex.public-api` в шести package manifests: access, core, operations,
tasks-workflow, tasks, tenancy. Например, `CoreX\Config\InvalidConfiguration` становится
`CoreX\Config\Exceptions\InvalidConfiguration`. `composer.lock` исключён из этого прохода; Rector его тоже не обрабатывает.
Runbook вызывает `composer install` до переноса, но после переноса не обновляет lock metadata.

**Воспроизведение:** в изолированном worktree применены настоящие `apply --no-rector`, `manifest`, `golden`.
Изменились шесть `composer.json`, lock байт в байт совпал с исходным. `rename-completeness-gate.php` вернул exit 1:
`rename-completeness FAIL: 13 occurrence(s)` — все 13 в `composer.lock`.
См. [manifest-delta.patch](2026-09-29-p03-design/manifest-delta.patch),
[dry-rename.log](2026-09-29-p03-design/dry-rename.log), [checks.json](2026-09-29-p03-design/checks.json).
Эта причина не зависит от пропуска Rector: lock исключён из всех преобразующих проходов.

**Последствие:** заявленный зелёный стек P03.2 недостижим по описанной последовательности; Files не включает
необходимые package manifests и root lock. Утверждение D57 п.6 «манифесты не меняются» расходится с инструментом.
**Принятое требование:** D01 — отсутствие старых ссылок; P03.2 Validation — `rename-completeness OK`.
**Владелец:** дизайн P03.2. Явно включить manifests и lock в Files; задать обновление metadata после переноса,
сохранение версий зависимостей и проверку результата. Не исключать lock из гейта полноты. Согласовать D57 и runbook.

## A2 — Major / issue: runbook требует golden-правила раньше, чем создаёт их

**Место:** `P03-design.md:68`; P03.2 Scope Included / Validation;
`p03-transfer.py:201–207` (`cmd_verify`).

Runbook задаёт `apply → verify → manifest → golden`. Однако `verify` уже требует присутствия всех
`manual` golden-правил, а `apply` их не добавляет. Их создаёт отдельная команда `golden`.

**Воспроизведение:** после настоящего переноса `verify` вернул exit 1 и `verify: 376 problems`;
каждая ошибка — `golden rule missing …`. Затем `golden` добавил 376 правил; повторный `verify` вернул exit 0,
`verify: 0 problems`. См. [verify-before-golden.log](2026-09-29-p03-design/verify-before-golden.log),
[golden.log](2026-09-29-p03-design/golden.log), [verify-after-golden.log](2026-09-29-p03-design/verify-after-golden.log).
Зависимость проверки от правил не меняется при запуске Rector.

**Последствие:** правильный перенос нарушает первый обязательный post-apply критерий и останавливает сухой прогон.
**Принятое требование:** P03.2 Validation — сухой прогон с `verify: 0 problems`; Execution Rules B10 — однозначный runbook.
**Владелец:** дизайн P03.2. Согласовать порядок во всех носителях: создать правила до проверки их наличия;
либо отдельно определить структурный и окончательный режимы `verify`. Добавить контроль порядка команд на чистой фикстуре.

## A3 — Major / issue: R5 пропускает доступ к чужому Internal через namespace alias

**Место:** `artifacts/P03-design/scripts/module-layout-gate.py:58–69,146–151` (`parse`, lookup в owner);
P03.1 Implementation Rules / Validation.

Парсер сохраняет импортированный namespace, но не разрешает последующие qualified names через его alias:

```php
namespace CoreX\Search\Data;
use CoreX\Search\Index;
final class Consumer {
    public function run(): object { return new Index\Internal\Driver(); }
}
```

Здесь Data корневого модуля использует `Index\Internal\Driver` другого модуля пакета. В `refs` попадает лишь
`CoreX\Search\Index`; такого класса в owner нет, поэтому R5 не видит зависимость.

**Воспроизведение:** этот файл в валидном дереве из штатной тестовой фикстуры получил **0 нарушений**.
Контроль с прямым импортом `use CoreX\Search\Index\Internal\Driver` получил R5.
См. cases `namespace-alias` и `full-import-control` в [gate-reproductions.json](2026-09-29-p03-design/gate-reproductions.json).

**Последствие:** CI пропускает новую межмодульную зависимость, запрещённую D57; baseline её тоже не содержит.
`package-graph-gate` эту внутрипакетную границу не проверяет.
**Принятое требование:** D57 п.5 / R5 — отсутствие ссылок в Internal другого модуля, кроме composition roots.
**Владелец:** дизайн P03.1. Разрешать namespace aliases и относительные qualified names до поиска owner;
проверить объявленную поддержку PHP-синтаксиса негативными контролями. Пересчитать оба эталона после уточнения анализатора.

## A4 — Major / issue: группа Internal/Laravel получает полномочия Laravel-моста

**Место:** `module-layout-gate.py:145` — `composition = root_entry or 'Laravel' in inner`.

Проверка признаёт composition root по наличию сегмента `Laravel` где угодно внутри модуля.
Но `Index/Internal/Laravel/Uses.php` — реализация внутри Internal, а не мост `Index/Laravel/` непосредственно под модулем:

```php
namespace CoreX\Search\Index\Internal\Laravel;
use CoreX\Search\Internal\Hydrator;
final class Uses {}
```

**Воспроизведение:** валидная фикстура с этим файлом получила **0 нарушений**, несмотря на прямой импорт
Internal корневого модуля. См. case `laravel-nested-in-internal` в `gate-reproductions.json`.

**Последствие:** перемещение реализации в группу с именем `Laravel` снимает защиту R5 без изменения зависимости.
**Принятое требование:** D57 п.1 — мосты непосредственно под модулем; п.5 — исключение для composition root / Laravel-моста.
**Владелец:** дизайн P03.1. Определять Laravel-мост по первому сегменту пути внутри модуля.
Сохранить позитив для `<Module>/Laravel/**` и добавить негатив для `<Module>/Internal/Laravel/**`.

## A5 — Minor / issue: R1 допускает дополнительные providers в корне ядра

**Место:** `module-layout-gate.py:125–131`, вычисление `root_entry`.

`name.endswith('ServiceProvider.php')` разрешает любой provider непосредственно в `packages/core/src/`.
Подброшенный `CoreX\ExtraServiceProvider` получил **0 нарушений**; case `unknown-kernel-root-provider` в `gate-reproductions.json`.

**Принятое требование:** D57 п.1 и докстринг R1 — в корне ядра только `CoreServiceProvider.php` и закрытый список модулей.
**Последствие:** будущий корневой provider ядра проходит гейт вопреки принятой раскладке.
**Владелец:** дизайн P03.1. Для корня kernel проверять точное разрешённое имя; package-root и module providers сохранить.
Это ограниченный дефект новой проверки, существующего дополнительного provider не обнаружено.
