# Аудит CoreX: качество, расширяемость и границы ответственности

Дата: 2026-09-14. Основа: HEAD `5e396e7210fc17e1dc0e6917e70bef10b74becab` **плюс текущее изменённое и untracked-дерево**. Это аудит существующей реализации, а не только последнего tenancy-диффа. Код не исправлялся; файл создан по запросу владельца.

## Вывод для владельца

Переписывать CoreX целиком не требуется. Типизация, небольшие DTO, разделение контрактов и реализаций, композиция Actions, реестр сущностей и адаптер Stancl дают хорошую основу. Однако сейчас нельзя считать базу готовым универсальным ядром: обнаружены дефекты изоляции и авторизации, опасный default экспорта, а также публичные точки расширения, которые не участвуют в выполнении.

Главная проблема — не синтаксис. Аккуратно оформленный интерфейс не помогает потребителю, если его не вызывает рабочий код. И отсутствие слова Flex не означает независимость от продукта: обязательные embedding-параметры, SaaS-статусы и политика удаления уже являются связью с конкретным типом платформы.

Рекомендуемый путь: исправить поведенческие дефекты, восстановить обещанные extension seams, затем отделить политику продукта от механизмов и упростить крупные реализации. Массовая замена классов, тотальная «Action/Repository-архитектура» и новые интерфейсы на каждый метод не нужны.

Для правил использованы `AGENTS.md`, `docs/dev-doctrine.md`, навыки `task:task-review`, `quality:artifact-review`, `php:code-style-spatie`, `php:production-readiness-checklist`. Старые планы рассматриваются как контекст: запланированный stub не объявляется законченной реализацией.

Ссылки `path:line` ниже относятся к этому снимку дерева. Severity: Blocker — нельзя принимать соответствующий путь использования; Major — существенный дефект; Minor — ограниченный дефект/улучшение. Confidence отделена от тяжести. «Статически» означает подтверждённую цепочку в коде, а не выполненный destructive/concurrency experiment.

## Подтверждённые находки

### T01. Экспорт по умолчанию фиктивный, но разрешает DROP

**Blocker · issue · high · code · correctness/data safety.**

`packages/tenancy/src/Provisioning/Internal/StanclTenantDatabaseLifecycle.php:57` выбирает `nullWriter()`, который возвращает путь и `size_bytes=0`, ничего не записывая. Затем экспорт получает `ready`; `drop()` проверяет только этот статус. `packages/tenancy/src/TenancyServiceProvider.php:97` создаёт default lifecycle без writer. `AccountLifecycle.php:244` допускает последующий purge.

Сценарий: штатная цепочка grace → requestExport → purge с default binding считает резервную копию готовой и допускает удаление БД без копии. Подтверждено статически; DROP не выполнялся. Комментарий о scope-excluded real writer объясняет происхождение stub, но не делает безопасным его production default.

Исправление: при отсутствии writer бросать явное исключение до `ready`; выделить проверяемый export driver и подтверждение сохранённого артефакта. Тест: default не выдаёт `ready`, purge запрещён; успешный драйвер подтверждает доступный архив. Не подменять тестовым writer production binding.

### T02. Очистка pending-пула гоняется с выдачей аккаунта

**Blocker · issue · high · code · correctness/race safety.**

`packages/tenancy/src/Provisioning/Internal/PendingPool.php:141` читает pending-строки, затем выполняет DROP и DELETE по id без повторной проверки состояния. `pullPending()` защищает выдачу блокировкой, но cleaner в ней не участвует.

Сценарий: cleaner прочитал A=pending; signup зарезервировал A и начал активацию; cleaner удаляет БД A. Это возможное чередование операций, не выполненный destructive test. Исправление: атомарно резервировать pending-строку под очистку (CAS/lock и отдельное состояние), затем выполнять восстановимый внешний DROP. Одной транзакции вокруг DROP недостаточно: PostgreSQL не разрешает DROP DATABASE внутри неё.

### T03. Вложенный runFor теряет исходный workspace

**Major · issue · high · code · tenant isolation.**

`packages/tenancy/src/StanclTenancyManager.php:68` восстанавливает workspace в `finally` callback. Но `vendor/stancl/tenancy/src/Tenancy.php:113` после callback восстанавливает исходного tenant; его bootstrapper revert вызывает `setWorkspace(null)` (`packages/tenancy/src/Bootstrappers/WorkspaceContextBootstrapper.php:74`).

Сценарий: A/workspace W → runFor(B) → возврат в A без W. WorkspaceScope при null перестаёт сужать выборку. Исправление: восстанавливать workspace после завершения всего Stancl run, включая исключение. Тестировать разные tenant и ненулевой внешний workspace.

### T04. Изменение статуса не инвалидирует host cache

**Major · issue · high · code · authorization/cache consistency.**

`packages/tenancy/src/Lifecycle/AccountLifecycle.php:155` и другие переходы обновляют `root_accounts` через query builder. `Models/Account.php:55` инвалидирует resolver cache через model events, которые при таком UPDATE не вызываются. `Http/Middleware/AccountStatusGate.php:27` доверяет статусу уже загруженной модели; host cache по конфигу хранится 300 секунд.

Сценарий: host разрешён и закэширован при active, затем suspend; следующий запрос получает старый active до истечения cache. Исправление: явная after-commit инвалидация всех доменных ключей либо согласованный свежий access-state. Тест должен сначала прогреть resolver, затем выполнить реальный lifecycle transition.

### T05. FSM проверяет состояние вне атомарного перехода

**Major · issue · high · code · race safety.**

`packages/tenancy/src/Lifecycle/AccountLifecycle.php:149` читает currentStatus и проверяет FSM до транзакции; UPDATE внутри ограничен только id. Аналогично activate/startGrace/requestExport.

Сценарий: два вызова читают active; первый переводит в grace, второй записывает suspended на основании уже устаревшего active. Формально запрещённый переход принимается. Исправление: читать/проверять под row lock внутри транзакции либо CAS `WHERE status=<expected>` с обработкой нулевого affected count. Регрессия — два соединения и управляемое чередование.

### T06. Purge фиксирует terminal state до внешнего DROP

**Major · issue · high · code · recovery/idempotency.**

`packages/tenancy/src/Lifecycle/AccountLifecycle.php:266` коммитит deleted и журнал, затем вызывает physical drop. При ошибке DROP запись уже deleted; повторный purge отвергается FSM deleted → deleted. Домены обновляются ещё позже.

Исправление: восстановимая операция удаления с идентификатором/промежуточным состоянием и идемпотентным retry; терминальное состояние только после завершения необходимых шагов. Проверить failure injection между каждым внешним эффектом и записью состояния.

### M01. ModuleManifest::listens не регистрирует подписчиков

**Major · issue · high · code · extension contract; doctrine §4.**

`packages/core/src/Modules/ModuleManifest.php:175` только сохраняет `$listeners`. В compiler, compiled payload и provider нет потребителя этого поля. Поиск по runtime src находит только property/setter.

Сценарий: потребитель декларативно подключает listener через разрешённый доктриной путь; событие отправляется, listener не вызывается. Исправление: довести manifest → compiled artifact → runtime registration, определить поведение для inactive modules и исключить дубли при повторном boot. Тестировать вызов реального listener, а не наличие массива.

### M02. ModuleActivationGate не участвует в enable

**Major · issue · high · code · extension/authorization.**

`packages/core/src/Modules/Contracts/ModuleActivationGate.php:20` обещает gate с tenant/module/edition. `Lifecycle/DatabaseModuleLifecycle.php:115` выполняет enable без его вызова, хотя binding существует.

Сценарий: приложение подменило gate на deny по лицензии/политике, но модуль всё равно включается. Исправление: проверять gate на mutation boundary до миграций/hooks, включая cascade; негативный тест через публичный `ModuleLifecycle`.

### M03. Lifecycle удаляет чужие listeners Laravel

**Major · issue · high · code · extension correctness.**

`packages/core/src/Modules/Internal/Lifecycle/DatabaseModuleLifecycle.php:645` вызывает `forget(MigrationStarted::class)` и `forget(MigrationEnded::class)`. Это удаляет все подписки на тип события, включая подписки приложения.

Проверка ревьюером на реальном Illuminate Dispatcher без БД: внешний listener до вызова — 1, после — 0. Исправление: один постоянно зарегистрированный listener с ограниченным контекстом claim-операции либо собственный изолированный dispatcher; не очищать глобальное событие целиком. Тест сохранности чужих listeners при успехе и исключении.

### M04. Отсутствующий registry блокирует собственную compile-команду

**Major · issue · high · code · deployment/DX.**

`packages/core/src/Modules/ModulesServiceProvider.php:226` в booted безусловно вызывает `compiled()`. `Registry/CompiledModuleRegistry.php:178` в production при отсутствующем файле бросает исключение с советом запустить compile. Artisan bootstrap происходит до выполнения команды.

Сценарий: первый production deploy без cache не может выполнить указанную repair/compile команду. Исправление: узкий bootstrap-путь для построения артефакта; сохранить fail-fast для обычного runtime. Не отключать проверку во всём console режиме. Тест — production application и отсутствующий compiled file.

### M05. Циклические зависимости модулей проходят compile

**Major · issue · high · code · correctness.**

`packages/core/src/Modules/Compiler/RegistryCompiler.php:61` проверяет requires, но не DAG. `Lifecycle/DatabaseModuleLifecycle.php:137` рекурсивно включает зависимости; состояния enabled ещё нет и visiting guard отсутствует.

Проверка ревьюером без БД: A requires B / B requires A успешно компилируются. Сценарий cascade enable ведёт к неограниченной рекурсии. Исправление: выявлять циклы при compile с цепочкой A → B → A; защитить runtime от некорректного старого cache.

### C01. Audit job может пережить rollback бизнес-транзакции

**Major · issue · high · code · after-commit side effects.**

`packages/core/src/Audit/QueuedAuditLogger.php:54` dispatch-ит job без afterCommit; `RecordAuditEntry` не требует after-commit dispatch. При внешней очереди и настройке after_commit=false observer ставит событие в очередь до коммита модели.

Сценарий: изменение модели затем rollback; worker записывает аудит фактически не состоявшегося изменения. Исправление: зафиксировать семантику committed audit и dispatch после успешного outer commit. Для строгой гарантии доставки отдельно оценить outbox; не вводить его автоматически ради стилевого рефакторинга.

### Q01. Publish-тесты загрязняют общий Testbench при исключении

**Major · issue · high · code/testing · isolation.**

`tests/Feature/MigrationPublishTest.php:76` публикует в общий `database_path`, а cleanup находится только в конце успешного теста (:91–99; второй тест :121–125). Ошибка assertion/DDL оставляет PG-миграции для следующего SQLite запуска. Такой загрязнённый каталог обнаружен в текущей среде; происхождение конкретного прошлого прогона не установлено.

Исправление: отдельный app/database path на тест, восстановление в finally/tearDown даже при ошибке. Не удалять все `.php` в общем migration directory: этот cleanup потенциально затрагивает чужие fixtures. Тестировать намеренно падающий publish-прогон и последующий чистый SQLite-прогон.

### T07. Pending доступен раньше готовности его БД

**Major · issue · high · code · concurrency/recovery.** `packages/tenancy/src/Provisioning/Internal/PendingPool.php:165` создаёт Account со status=pending, а затем вызывает provision. Другой signup уже может выбрать эту строку. При ошибке клонирования она остаётся pending без готовой БД. Нужен непубличный building-state с переводом в pending только после успеха и восстановлением после ошибки. Регрессия: задержанный/падающий provision одновременно с claim.

### T08. IdentitySyncer смешивает время источника и время доставки

**Major · issue · high · code · consistency.** `packages/tenancy/src/Identity/Internal/DatabaseIdentitySyncer.php:68` сравнивает source updated_at с tenant synced_at, но в :92 записывает локальное now. v1 прочитана в t0, v2 появилась в t1, запись v1 закончилась в t2: v2 затем пропускается, потому что t1 ≤ t2. Check/updateOrCreate также не защищены от stale overwrite двумя sync. :109 отмечает root-связь синхронизированной.

Исправление: хранить применённую версию/время источника отдельно от времени доставки и условно применять только более новый snapshot. Новый `ManagementIdentityHydrator` содержит более строгую реализацию, но runtime binding всё ещё ведёт в DatabaseIdentitySyncer; наличие нового класса не закрывает дефект. Тест: задержанная доставка v1 после появления/применения v2.

### T09. Memo impersonation хранится в singleton

**Major · issue · high, условно для повторно используемого container · code · request isolation.** `packages/tenancy/src/TenancyServiceProvider.php:219` регистрирует `DatabaseImpersonationService` singleton; `Impersonation/DatabaseImpersonationService.php:41` хранит `$resolved/$memoState`, :180 кеширует результат. Для long-lived HTTP worker первый null/grant может попасть в следующий запрос; reset в пакете не найден. Текущий deployment на Octane не утверждается.

Исправление: request-scoped service/reset в поддерживаемом worker lifecycle. Проверить два запроса в одном worker в обоих порядках normal → impersonated и impersonated → normal. Не считать два отдельных Testbench application таким тестом.

### T10. Acceptance invitation неатомарен и неверно считает quota

**Major · issue · high · code · data integrity.** `packages/tenancy/src/Models/Invitation.php:84` проверяет старую модель, затем отдельно count, create membership и update invitation. Два приглашения при одном свободном месте оба проходят лимит; ошибка последнего UPDATE оставляет half-write. :96 считает всех участников, включая неактивных, вопреки комментарию о active member count.

Исправление: reload/lock invitation и общий quota-resource, атомарный acceptance, согласованный active predicate. Блокировки только разных invitation недостаточно для общего лимита.

### T11. Конфиг provisioning pipeline игнорируется

**Minor · issue · high · code · extension/config honesty.** `packages/tenancy/config/tenancy.php:55` объявляет pipeline; `src/TenancyServiceProvider.php:292` жёстко передаёт `[CreateDatabaseFromTemplate::class]`. Пользовательский step не выполняется. Либо использовать заявленный конфиг и проверить кастомный pipeline, либо убрать ложное обещание расширения.

### T12. Root publish-path расходится с central workflow

**Minor · issue · high · code/docs · responsibility.** `packages/tenancy/src/TenancyServiceProvider.php:254` публикует root migrations в общий `database/migrations`, хотя соседняя инструкция требует `database/migrations/root`. После publish указанного каталога нет, обычный migrate видит control-plane DDL. Нужен согласованный отдельный target и проверка результата publish. Publish-only как подход здесь разумен.

### T13. Forbidden activateFromPool уже расходует pool

**Minor · issue · high · code · authorization ordering.** `packages/tenancy/src/Lifecycle/AccountLifecycle.php:59` вызывает pullPending перед impersonation guard. Запрещённый вызов уже зарезервировал аккаунт или создал БД. Guard должен выполняться первым. Отдельно legacy entrypoint не получает автоматически idempotency/компенсации нового `ClaimAccountSignup`; свести пользовательский сценарий к одной реализации после проверки совместимости.

### M06. Блокировка одного модуля не защищает граф зависимостей

**Major · issue · high · code · concurrency.** `packages/core/src/Modules/Internal/Lifecycle/DatabaseModuleLifecycle.php:121`, :201 блокируют только изменяемый модуль; `ensureDependencyEnabled():380` и `enabledDependents():400` не сериализуют граф. T1 начинает enable A, видит B enabled; T2 disable B не видит ещё не закоммиченный A и выключает B; T1 включает A. Получается enabled A с disabled dependency.

Исправление: простой tenant/DB-scoped lifecycle lock для редких административных операций либо упорядоченные locks всего затронутого графа. Тест: enable dependent против disable dependency на двух соединениях. Сценарий подтверждён статически, не конкурентным прогоном.

### M07. ModuleEnabled приходит до обязательных feature flags

**Major · issue · high · code · completion/recovery.** `packages/core/src/Modules/Internal/Lifecycle/DatabaseModuleLifecycle.php:169` после коммита сначала отправляет ModuleEnabled, потом определяет manifest flags. Listener видит неполную установку; при его ошибке или ошибке define состояние уже enabled, а повторный enable на :125 выходит без восстановления.

Исправление: обязательные данные установки до события в согласованной транзакции; если это projection, нужны явные retry/reconciliation и соответствующее обещание события. Проверить listener, читающий flag, и failure injection.

### M08. Список сущностей выполняет повторные SQL-проверки epoch

**Minor · issue · high · code · performance.** `packages/core/src/Modules/Registry/ArrayEntityRegistry.php:67` проверяет activity для каждой entity; `ModulesServiceProvider.php:282` на каждый lookup выполняет hasTable и count всей `mod_lifecycle_log`, даже при тёплом enabled-cache. Сто сущностей могут дать около 200 запросов только для epoch. Это оценка по цепочке вызовов, не benchmark.

Исправление: один snapshot activity для операции `all(ctx)`, дешёвый version token вместо полного count. Не вводить вечный process-cache ценой потери tenant isolation/актуальности. Тестировать количество запросов и смену tenant/version.

### C02. DB PubSub пропускает сообщения при обратном порядке commit

**Major · issue · high · code · delivery correctness.** `packages/core/src/Messaging/Internal/DatabasePollPubSub.php:53` вставляет в текущую транзакцию; :92 читает id > cursor. T1 получает id=10 и задерживает commit; T2 коммитит id=11; subscriber двигается до 11; T1 коммитит 10 — это сообщение уже никогда не выбирается. Sequence id не является порядком commit.

Исправление: определить требуемую гарантию доставки и реализовать ordered publication либо подтверждения доставки, выдерживающие этот сценарий. Просто заменить id на timestamp недостаточно. Проверка двумя publisher connections и subscriber; текущие последовательные тесты не доказывают этот случай.

### A01. Scope memo не включает идентичность ролей и tenant/workspace

**Major · issue · high · code · authorization.** `packages/auth/src/Access/DefaultAccessChecker.php:171` включает только версии ролей (:174), без role IDs, account, workspace и panel. При смене workspace набор ролей меняется, но версии могут совпасть; метод возвращает ранее вычисленный более широкий scope.

Исправление: канонический key из всех входов политики, включая отсортированные пары roleId/version и контекст. Тестировать same principal, разные workspace/роли одной версии и смену набора assignments без изменения версии самой роли.

### A02. Удалённая роль продолжает влиять на scope

**Major · issue · high · code · authorization/soft-delete.** `packages/auth/src/Access/DefaultAccessChecker.php:120` читает assignments без отсечения soft-deleted `aut_roles`, затем matrixQuery объединяет scopes этих role IDs. Сценарий: живая narrow role даёт permission, удалённая broad role всё ещё расширяет scope. Исправление: получать только действующие роли согласованно с grant authority; тестировать смесь живой и удалённой роли.

### A03. Проверка записи и фильтр списка используют разную нормализацию scope

**Major · issue · high · code · authorization consistency.** `packages/auth/src/Access/DefaultAccessChecker.php:107` передаёт scope прямо в matches; `DefaultScopeResolver::apply` использует ScopeAvailability. Для entity без соответствующих capabilities результат record-check отличается от результата list-query.

Исправление: одна функция effective scope/capability normalization на обоих путях. Регрессия должна сравнивать доступность записи через list-query и `canOnRecord`, включая отсутствие capability и несогласованный schema/manifest. Не менять правило нормализации молча: его смысл — часть публичного поведения.

### A04. Защита системной роли обходится изменением самого флага

**Major · issue · high · code · integrity.** `packages/auth/src/Models/Role.php:67` возвращает текущее `is_system`; оно изменяемо и находится в fillable (:40). Загруженной системной роли присваивают false, после чего guard считает её обычной. Проверка ревьюером без БД подтвердила original=true / guard=false.

Исправление: защищать по persisted/original state и отдельно запрещать снятие системности; учитывать updating/deleting/related writes. Тест обычного `$role->is_system=false; $role->save()` без seed bypass.

### K01. Перенос задачи обходит семантику её завершения

**Major · issue · high · code · authorization/domain invariants.** `packages/tasks/src/Actions/MoveTaskToStage.php:78` ставит Done и completed_at напрямую. `CompleteTask.php:53` отдельно вызывает authorizeComplete, запрещает Cancelled и отправляет TaskCompleted; путь move этого не делает.

Сценарий: host разрешил move, запретил complete; перенос в auto_status=Done всё равно завершает задачу. Отменённая задача тоже может завершиться, подписчик TaskCompleted ничего не узнаёт. Исправление: единая внутренняя операция перехода с согласованной политикой/event semantics. Не копировать весь CompleteTask в MoveTaskToStage. Проверить запрет completion через оба публичных входа.

### F01. Сделка принимает стадию другой воронки

**Major · issue · high · code · relational integrity.** `products/flex-crm/src/Actions/MoveDealToStage.php:22` associate(stage) не сравнивает pipeline IDs. Deal сохраняет pipeline A со stage B. Исправление: проверка принадлежности под согласованной транзакцией/lock, отказ без частичного обновления. Текущие 8 CRM-тестов этот случай не проверяют.

### F02. Повторная конвертация лида создаёт дубли

**Major · issue · high · code · idempotency.** `products/flex-crm/src/Actions/ConvertLead.php:29` создаёт contact/company/deal, не проверив persisted Converted и не заблокировав lead. Даже последовательный повтор создаёт новый contact и перезаписывает ссылку конвертации. Исправление: lock/reload и определённое повторное поведение — вернуть существующий результат или явную ошибку; тестировать retry и конкуренцию.

### F03. Activity morph ID фиксирован на ULID при UUIDv7 default

**Major · issue · high · code · ID compatibility.** `products/flex-crm/database/migrations/2026_06_14_000160_create_crm_activities_table.php:19` использует `ulidMorphs('subject')` — char(26); default CoreX ID — UUIDv7 (36 символов). SQLite не доказывает совместимость длины с PostgreSQL. Сценарий на PG: LogActivity для default subject получает ошибку слишком длинного значения.

Исправление: использовать согласованный IdColumns morph helper/выбранную ID-стратегию и additive migration для уже установленных таблиц. Проверить PG insert и чтение relation для поддерживаемых стратегий ID.

### R01. Старый grant может снять более новый revoke в reference PairStore

**Major · issue · high · reference code, НЕ подключённая runtime-уязвимость · fencing correctness.** `packages/tenancy/src/Membership/Internal/Persistence/PairStore.php:107` разрешает regrant при совпадении appliedOperationId; `invalidate():131` меняет epoch/denied, сохраняя operation markers.

Сценарий: admit(A) → apply(A) → invalidate(barrier) → regrant(A) → commit(A). Старый snapshot вновь открывает пару после revoke. Исправление: связать admitted operation с captured epoch/fence либо инвалидировать старую operation при barrier. Проверять указанное чередование, а не только invalidate → commit.

`packages/tenancy/tests/Feature/MembershipRuntimeRegistrationTest.php:11` явно закрепляет отсутствие runtime registrations. Поэтому это препятствие будущему adoption прототипа, а не доказанный обход работающей защиты. Не подключать reference классы автоматически, чтобы «устранить dead code».

### A05. Инвалидация role matrix не привязана к outer commit

**Major · issue · high · code · cache consistency.** `packages/auth/src/Matrix/DatabaseRoleMatrixCompiler.php:74` вызывает bump после внутреннего `DB::transaction`, который может быть лишь savepoint внутри внешней транзакции. Другой запрос уже видит новую версию, но старую committed matrix; внешний commit больше не меняет token. При rollback token тоже меняется. `ScopeMapVersion.php:36` дополнительно делает неатомарный read + write, теряя параллельные bump.

Исправление: after-commit invalidation с безопасным version token и сохранённым account context. Проверить внешний commit, rollback и конкурентные bump. Наличие tenant salt в ScopeMapVersion полезно, но не устраняет A01 в другом локальном memo.

### K02. Повторный move меняет completed_at

**Minor · issue · high · code · retry semantics.** `packages/tasks/src/Actions/MoveTaskToStage.php:78` при повторе той же Done-stage снова присваивает now и отправляет событие. Retry меняет дату завершения и повторяет автоматизацию. Исправить вместе с K01: определить same-stage no-op и сохранять completed_at без нового status transition.

### F04. CRM не включён в стандартный module lifecycle

**Major · issue · high для стандартного discovery-пути · code · integration.** `products/flex-crm/composer.json:6` задаёт library без module manifest/extra.corex.module. `CrmServiceProvider.php:23` автоматически грузит миграции и напрямую регистрирует entities с owner `flex/crm`. Discovery ищет `type=corex-module`; фильтр active entities требует активного owning module.

Следствие: в стандартной композиции установленная CRM-библиотека не становится discoverable/управляемым модулем и не получает обычную active permission surface. Исправление: manifest/lifecycle как у Tasks либо явно поддержанный library-mode с согласованной активностью. Само имя `flex/crm` корректно и не требует обратного переименования в CoreX.

Не рекомендую поручать одной модели команду «почисти весь CoreX по аудиту»: такая постановка смешивает безопасный ремонт, смену политики продукта и изменение публичного API. У каждого набора должен быть свой проверяемый результат. После исправлений повторный аудит нужен по изменённым границам и интеграционным сценариям, а не ещё один проход по всем комментариям.

Практический критерий готовности универсального ядра: минимальный Laravel consumer без Flex и без embedding-полей может подключить core/modules; запретить активацию через свой gate; получить свой manifest listener; заменить нужный transport/policy; вложенно переключить tenant/workspace и вернуть исходный контекст; корректно пережить rollback/retry. Именно эти сценарии должны стать примерами и проверками пакетов.
