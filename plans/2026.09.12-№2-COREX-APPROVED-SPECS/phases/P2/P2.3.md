### P2.3 — Integrity gate перед provisioning/pool/activation/wave writes

**Intent:** Enforce verified template integrity before every affected provisioning or activation write and migration-wave admission.

**Why:** RAG:— Current provisioner savesparams first; PendingPool.cloneOne createsaccount first, pullPending updatesstatus; wave.runBatch writesrunning before validating target; clone-manager-only guard is too late.

**Scope Included:** Earliest gate in provisioner, pool clone/pull, clonejob/manager, activation/startTrial, migrationwave admission; template drift/lock/queue recheck and idempotency; stale candidates denied without mutation.

**Scope Excluded:** Live rollout/template remediation/destructive pendingclear; billing/table moves; new wave schema/public Contracts; global quarantine write on denial; bypass via approved ready mode without separateowner decision.

**Implementation Rules:** TEMPLATE-SCHEMA/TEMPLATE-SEAL gates inherited; exact sidecar source/lock binding required. Runtime writes under held verified admission only; if shared asynchronous proof expires, job re-verifies rather than reuse stale token. Centraltransactions cannot rollback CREATE DATABASE: reconcile retry existence with matching trustedaccount/template metadata, never assume anyexistingDB is correct. No src/Contracts signatures altered.

**Code Guidance:** 1. Provisioner читает account/template/expected manifest, берёт общий template lock и проверяет triple hash до params save/TenantCreated. Clone manager самостоятельно re-verifies до backend termination/quarantine, CREATE/GRANT/ALTER. Queue job проверяет повторно после задержки, включая существующую DB перед no-op.
2. PendingPool.cloneOne проверяет cluster/template/manifest до Account.create, params/counter/event/DDL. Pull берёт candidate row lock и template lock, читает actual pending DB catalogue и bound manifest; status claim только после проверки. Pool DB соответствует semantic golden hash, а не только template_version row.
3. ActivateFromPool и direct startTrial проверяют actual account DB/manifest/version/module/embedding до slug/owner/status/domain/event writes. Lock удерживается сквозь этапы либо каждый этап re-verifies; прямой вызов lifecycle не обход проверки pool.
4. Wave admission проверяет immutable target sidecar/trust/template/target catalogue до batch running и target-state writes. Target change — новая wave identity. Per-account migration использует pinned artifacts и existing DDL lock; result catalogue проверяется до current_version/status ok. Ошибка после допущенной migration может записать truthful failed state; zero-write относится к admission rejection до разрешённой mutation.
5. Stale template/pool shell локально исключается/denied; rejection path не запускает clear/DROP/quarantine writes. Maintenance quarantine — отдельная operator операция. Connection/serializer/signature failure не мутирует state.
6. Concurrency fixture меняет template только через общий operator lock и доказывает block/reverify; golden read backend закрыт перед clone. Retry не создаёт вторую DB/counter/event и не принимает unrelated existing DB; physical CREATE вне transaction требует durable state reconciliation.

**Validation:** V-EARLIEST-WRITES: ready wrong/missing hash, stale pool/wave, mid-build, untrusted manifest и verifier errors сохраняют params/accounts/status/counters/domain/events и дают zero DDL/backend termination для каждого entrypoint. V-RACE: два pool claims — один owner; drift между check/use и queue delay обнаружен; template reader закрыт до clone. V-POSITIVE: valid build→pool→claim→activation и admitted wave succeed; retry без extra DB/counter/event; ok только после matching resulting hash. V-QUALITY-CODE: tenancy integration, root D34, arch, D98 и bounded independent review earliest-write/locking seam. No Contracts delta; privileged operator invariant указан.

**Deliverables:** findings/P2.3-write-seam-proof.md: per-entrypoint earliest-write/callsite map, zero-write/race/queue/idempotency receipts, exact isolated DB/tool/source fingerprints и residual operator invariant. Rollback: остановить affected provisioning/activation/waves, сохранить metadata/account DBs; ready-only contingency только отдельно утверждённым режимом, без автоматического DROP/rebuild.
