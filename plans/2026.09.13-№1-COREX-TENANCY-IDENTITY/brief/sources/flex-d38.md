## Решение

Владелец уточнил старт: понятные последовательные шаги, Nuxt + Naive UI, отраслевые решения пока только запускаемые каркасы без нового функционала. Дополнительно явно потребовал утвердить **всю БД до реализации**: таблицы, столбцы, связи и владельцы (CoreX/Flex/vendor) в отдельном файле плана.

Прежние P9.1–P9.6 не исполнялись и переопределены без потери done-фактов. Порядок теперь: P9 подготовка и DB gate → P10 техническая основа backend/Nuxt/Naive UI и две solution shells → P11 авторизация и профиль → P12 базовые задачи → P13 проверка поставки. Сначала минимальный backend, затем ранний UI; далее каждая функция проводится backend → frontend → проверка, не откладывая весь frontend до конца backend.

`schema/DATABASE_SCHEMA.md` — один документ схемы для рассмотрения владельцем, с полями и связями, картой источников, scope/ownership и версиями. Старый FROZEN v1.2 не является согласием на новую объединённую схему. **P9.3 требует явного утверждения владельцем конкретной версии и SHA-256 документа.** Ни каркасы приложения, ни Composer/npm изменения, ни миграции не выполняются до этого gate. Исследование/план/проверки без изменения runtime разрешены. Изменение утверждённой схемы требует новой версии и явного согласования дельты.

Строительные отчёты, отраслевые таблицы `cns_*`, отдельные бизнес-процессы УК и shared-data интеграции отложены. `solutions/construction` и `solutions/property-management` в P10 имеют независимые Laravel/Nuxt roots, health endpoint, общий UI shell и собственные env/locks, **без отраслевых сущностей и фиктивных бизнес-данных**. Общая auth в P11 может быть переиспользована — это базовый функционал.

## Контроль владельца

Один видимый item за один цикл работы: короткое сообщение о цели → реализация → проверка → результат, ограничения и следующий item. Между завершёнными items — контрольная точка в чате для правок владельца; десятки items не исполняются скрытой цепочкой. Это запрошенный владельцем режим наблюдения, а не повторное разрешение на каждую команду. На DB gate требуется именно ответ владельца; время ожидания и молчание не считаются утверждением.

## Почему

В прежней P9 слишком крупный шаг соединял scaffold, login, API и задачи, а отраслевой пилот преждевременно включал отчёты. Разделение даёт отдельные проверяемые результаты и явный порядок выбора библиотек. Наличие неполного DB-каталога по ссылкам не заменяет рассмотрение всех физических столбцов и связей.
