## 2. Authority and principal binding

Central alone creates/grants/revokes/regrants membership and writes its durable ledger. A tenant-side removal command may request a central revoke after the consumer's permission check; it cannot itself write root tables or assert a grant. The central API authenticates the service principal and checks its registered account/product/capabilities on every operation, including when its access JWT is still valid. A valid service token is not positive human membership.

Account must agree across initialized trusted caller/job context, certificate registration, verified token claims, requested resource and request/response identifiers. The account supplied in a body, header, URL, event or queue message is only a value to cross-check. An A certificate/token cannot operate on B, including when identity UUID is equal. Product/client scope comes from authenticated central registration, not X-CoreX-* headers.

For client_credentials, the JWT subject is the service, not the acting human. Central must ignore acting_identity for authorization: forging/removing/changing it cannot increase account or operation scope. Audit records distinguish authenticated service principal, certificate fingerprint, target identity/account, correlation/request ID, central result/commit reference, and claimed acting identity with its provenance. Do not present the claimed actor as independently central-authenticated. Tenant permission evidence can authorize the tenant call locally; central uses the service's own account-scoped capability policy. Exact consumer policy and central registration records remain inputs.

Identity association is by UUID only. Shared phone/email never merges or rekeys identities. Missing/invited/pending/blocked/deleted membership or missing/deleted local user is deny. Profile updated_at/synced_at cannot determine membership freshness. Tenant profile hydration/legacy management sync must not bypass the membership lease or credential fence; root management bookkeeping has a named management-only caller.

## 3. OAuth, certificates and keys

The intended access JWT validation profile is RFC9068: protected typ=at+jwt, alg allowlist RS256, nonempty kid, required iss/aud/sub/client_id/iat/exp/jti, and the RFC8705 cnf.x5t#S256 certificate binding. Account/product/capabilities are additional explicitly registered profile fields; their exact wire claim names remain deployment/API inputs. Reject missing, ambiguous, mismatched, expired or untrusted fields. RSA keys are at least2048 bits. Do not confuse ID tokens, access tokens and trigger envelopes.

Use validated HTTPS issuer metadata and its token_endpoint; if published, use mtls_endpoint_aliases.token_endpoint. Send client_id and grant_type=client_credentials with the registered certificate. The authoritative resource server checks the certificate actually used by TLS against the token binding and the active account-scoped registration. Reverse-proxy certificate forwarding is trusted only with an exact authenticated edge/backend contract that strips caller-supplied certificate headers. No bearer-only or shared-secret fallback. Token acquisition/rotation failure produces deny/unavailable, never root write or cached positive membership.

**Certificate registration recommendation (design proposal, not observed deployment):** PKI tls_client_auth with one exact registered URI SAN per account-scoped client, plus an accepted-fingerprint/serial registry at both AS and resource server. It supports renewal under a stable subject while enforcing the ten-minute retirement. The actual CA, SAN, client_id, registry, provisioner, enrollment interface and permissions are unknown. An owner-proved self_signed_tls_client_auth registration is possible but must be explicitly bound rather than silently substituted; client certificate JWKS is separate from AS signing JWKS. OAuth standards describe registration metadata; they do not imply a live dynamic registration endpoint.

Certificate lifecycle: new key/certificate is issued and registered for the same account at day20. Overlap starts when the new registration is accepted by both AS and resource server; after600s the old registration/fingerprint is rejected at both, even though its X.509 notAfter may be ten days away. Re-establish TLS using the new certificate and mint a new token; the old certificate-bound token does not transfer to the new certificate. Connection reuse/resumption must not let an already open TLS connection bypass retirement. Define instant of retirement and distributed registry activation proof; failed renewal cannot extend overlap or accepted lifetime. Emergency compromise has a separately bound retirement path; never infer instant registry invalidation from JWT TTL.

Signing lifecycle: publish a new unique kid/public key to the actual JWKS and all serving edges before counting the300s prepublication period. Start signing only afterward; never reuse kid for different keys. Cache maximum300s, no stale-key grace that silently exceeds policy. At an unfamiliar kid perform one bounded/refetch attempt under shared rate control, then deny if unresolved. Equality of cache TTL and prepublication does not prove zero fetch/CDN latency: the activation barrier and bounded refetch must be qualified. Old public key remains available until600s after the last signature it actually produced; later retry envelopes use the current signing key. Private retirement stops signing. Emergency key compromise must reject affected signatures rather than retain trust as an ordinary rollover.

JWT skew30 applies to token/envelope validation only, not the lease or certificate acceptance overlap. Token expiration can therefore have a validation tolerance tail; it is not the revoke deadline mechanism. Enforce exp-iat≤300, no future issuance beyond30s, trusted time and strict boundary semantics. Optional nbf cannot extend lifetime. No refresh token is issued or stored for this service grant; new access is another authenticated client_credentials request.

## 4. Signed trigger, delivery and authoritative pull

Design proposal for trigger wire profile: compact JWS JWT, RS256, protected distinct typ=corex-membership-trigger+jwt, no remote key URL from the message. Use exact locally trusted issuer/event audience/key set. Signed claims include event_id, delivery-attempt jti, schema/profile version, identity UUID, account UUID, product, event kind, central commit reference, audit actor/reason enum, occurred_at, iat and exp. TTL≤300s; no PII or free-text reason. This is a custom trigger profile, not a claim of RFC8417 SET conformance. Exact event kind/reason vocabulary/claim schema/audience are still inputs, not accepted public DTOs.

Validate signature, type, issuer, audience, lifetime, account/product routing and schema before dispatch. A forged trigger must cause no account projection write. A valid old/duplicate/reordered trigger may at most schedule a current pull; it cannot use event kind, occurred_at or commit reference as authority to change users.is_active. Replayed envelopes never renew freshness. Coalesce per pair without starving reconciliation; conflicting content for one stable event_id is a protocol error.

Central ledger commit and durable notification/recovery record must be tied so a crash cannot permanently lose a revoke trigger. Logical event_id/commit reference stay stable for retries. A300s envelope cannot be replayed over24h: retry re-signs a new short-lived delivery envelope with new iat/exp/jti, preserving the logical event. An expired envelope is rejected; after retry exhaustion reconciliation continues independently. A delivery receipt does not mean a local projection/cleanup commit; acknowledgment and pending retry state must survive crash boundaries. Dedup must not acknowledge failed refresh or suppress necessary cleanup; exact durable storage and retention are deployment inputs.

Authoritative pull is an authenticated request for the bound identity/account. It must observe every ledger commit completed before the central read begins, including through failover; a stale replica, CDN cache,304 from an old representation or saved response is insufficient. Commits during a read may fall on either side of its snapshot. Return a consistent state with durable per-pair membership revision and **revocation/credential generation** (or equivalent durable revoke-history watermark). Every revoke advances the generation; it is not reset by regrant, restore or failover. Event commit references are opaque triggers; the returned revision/generation provides authoritative ordering.

A boolean active response alone misses revoke→regrant completed between polls. Even if the latest state is active, the advanced generation must invalidate all older sessions/remember credentials. Missing state is deny; authenticated current nonactive/deleted state is deny. Exact response fields, ledger persistence, failover fencing and no-reset proof are not discovered yet. No revision column or new table is authorized here.

## 5. Serialization, lease and the60s proof

Serialization covers lock acquisition, pull, state validation, projection/fencing/cleanup application and lease publication for the entire identity/account pair across all processes/hosts. Never pull before the lock and later apply that saved response. A timed-out/crashed/expired-lock holder cannot overwrite a later deny/regrant; deployment must supply durable fencing/transaction comparison. Legacy sync, login hydration and reconciliation obey the same authority boundary. The5s apply budget includes required local commit work; the5s pull deadline includes token/metadata/key cache misses, network/TLS and response verification needed by that pull. Deadline exhaustion gives no positive lease.

Record local conservative monotone t0 immediately before issuing the pull request, after serialization admission; t0 is no later than the central read start. A successfully verified active snapshot may publish a positive lease ending at **t0+45s** only after its fenced local application commits. Never anchor at response arrival, local apply end, event time or profile time. A new authoritative read with unchanged revision can renew from its new t0; cached/replayed responses cannot. An active snapshot received after its lease has already expired grants no access.

Every new authorization decision checks: trusted account/identity, currently live local user, committed valid credential generation, current positive authoritative lease, and consumer permission. Recheck for each later decision in long requests/jobs/connections; a cached Auth::user() is insufficient. At expiry deny immediately, before an attempted network refresh or asynchronous cleanup. Missing cache/DB/context, uncertain time, process restart, time rollback, suspend/resume without a qualified conservative elapsed clock, clock-store loss, or fencing loss gives deny until a new pull. A persisted wall-clock expiry is not trusted across these failures. JWT skew30 never extends45s. Cloud local-password fallback cannot bypass a revoked cloud membership; boxed authentication remains a separate deployment profile.

Let tr be the central revoke commit instant, with no subsequent authoritative regrant. Any positive snapshot that can miss that revoke began reading before tr, hence t0≤read_start<tr and lease_expiry=t0+45s<tr+45s. Any read beginning at/after tr includes the revoke and cannot grant. Thus the lease path denies by tr+45s (stronger than the required tr+60s), including during central/network/event outage, provided local time/check enforcement meets this contract. A grant event or profile sync cannot prolong this window. A later authoritative regrant changes the authority state but never validates old credentials.

Healthy recovery: reconciliation admits and starts a read for each relevant pair within30s of any instant, including queue/coalescing/lock wait; pull5s + apply5s gives local application by tr+40s. The cadence must measure read-start admission, not merely enqueue or cron wakeup. Tail delivery p99.9≤10s is a monthly SLO, not a hard bound; it cannot prove the universal revoke requirement. Event healthy path delivery10+pull5+apply5 gives20s for that99.9% cohort only, with scheduling accounted in delivery/application measurements.

## 6. Local session and remember lifecycle; FE-60

Revocation or lease expiry independently disables access. A fenced tenant-local transaction marks the UUID user inactive, records the known authoritative revoked-through generation and a durable local credential deny barrier, invalidates remember credentials and removes that user's invalidated-generation database sessions. Lease expiry is local denial, not an invented central revoke: advance a durable local credential epoch without fabricating a central ledger revision. Bind credentials to both central revoke generation and local invalidation epoch (or an equivalent non-resetting fence). A later active pull with the same central generation still cannot revive credentials invalidated on expiry. Credentials in other accounts are untouched. If these stores cannot be atomically fenced together, a durable deny barrier must become visible first and fresh login remain blocked until the cleanup barrier commits. Failures retry with deny preserved; acknowledgments cannot skip unfinished work.

Regrant may set is_active=true only from a fresh authoritative pull and only after its prior-generation deny/cleanup fence is durable. It requires a new login and newly minted session/remember credential bound to the current generation; it never restores old session rows, recaller tokens, cached principals or leases. A delayed request authenticated before revoke must fail its final session/remember write after the generation advances, including after regrant. Checking only is_active at save time is insufficient because it may already be true again. Stale login/OIDC callback and profile hydration face the same fence. Tombstones/fences survive regrant, restart and restore; exact retention/storage and any DDL approval are pending.

The stock Laravel database session handler can INSERT a removed session during a late request save. The final-write check and insert/update must therefore share a transaction/fence with revocation, closing the check-then-write race; an application middleware check alone does not prove it. Login credential checks, saved-session restoration, remember restoration/issuance, browser/API requests, PAT/OAuth authorization, websocket connect/reconnect/subscription/message decisions, queues/scheduled commands and other consumer entrances each need an exact active/lease/generation binding. For unsupported remember-me, prove every old recaller rejected and no new credential issued; do not add remember_token to the frozen schema by inference. Existing optional PrincipalUserProvider disables remember-me but does not prove all deployed guards use it.

**FE-60 (explicit bounded local-fault envelope, qualification still pending):** central pull/network/event delivery may be unavailable indefinitely. Each relevant local pair's lease-expiry scan/dispatch, scheduling pauses and serialization/fence admission together complete within5s of the conservative45s expiry bound. Tenant DB recovery/connection wait plus the fenced invalidation/session cleanup transaction and its durable commit together complete within10s after that admission. Those5+10 seconds include all retries, lock waits, process failover and backlog; they are not added once per retry. Existing in-flight work cannot save an old generation after the committed fence. The clock and authorization entrance requirements of §5 hold. Then45+5+10=60s from tr bounds completion; the healthy reconciliation path additionally has20s residual margin after its40s apply bound.

FE-60 is a precise proposed operational acceptance envelope, not evidence that the deployment satisfies it. An outage/backlog exceeding either local budget, unavailable tenant DB beyond that window, unbounded scheduler pause or lost durable credential fence is outside physical-cleanup60 coverage and must be reported as such. Authorization still denies on lease expiry independently of physical deletion, when the local enforcement/clock assumptions hold. During DB uncertainty fail closed; never promise a physical DELETE against an unreachable database. Recovery first reapplies deny/fences and cleanup before fresh login. This fault envelope does not weaken the new-authorization deny60 target or create an outage allow mode.

## 7. Observability and acceptance scenarios

Monthly delivery SLO: denominator is all committed logical membership events destined for an account over a UTC calendar month; late/missing/failed delivery is counted, not dropped from samples. Measure central commit→first validated durable receiver admission; track receiver admission→fenced apply→credential/session cleanup separately. p99.9≤10s is the percentile of this population; no commits means no-data, not GREEN. Bind synchronized timestamp error/measurement method and per-account tail/backlog visibility before claiming results. Retry horizon24h runs from the original commit and does not replace reconciliation. Reconciliation30 is a maximum read-start interval for every authorization-relevant pair, including disconnected event receivers; define inventory/capacity so no pair is omitted.

For future isolated implementation verification, retain two account DBs and independent concurrent workers. Required cases:

1. Membership-only revoke/regrant with unchanged profile; missing/pending/deleted deny; UUID collision/shared phone never merge; tenant caller never writes root bookkeeping.
2. Wrong certificate, registration/client/product/account/resource, absent cnf, wrong typ/alg/kid/issuer/audience/expiry and forged actor cannot gain scope. Correct TLS certificate possession alone cannot bypass retired registration. Closed/resumed/open old TLS connection after overlap is rejected.
3. Unknown-kid refresh/activation barrier; publication latency, cached JWKS, rotation90d and retention from last actual signature; key compromise fail closed. Certificate day20 renewal and retirement600s independently of notAfter.
4. Valid signed old grant/revoke only pulls; invalid/expired envelope writes nothing; retries beyond300s use fresh signatures with stable logical ID; dedup after failure still completes cleanup.
5. Last pre-revoke read paused for5s, apply paused5s: expiry remains t0+45. Revoke committed before read begins always appears; stale replica/cache/failover cannot produce lease. Serialization and expired-lock holders never overwrite current authority.
6. Event loss and central outage: deny≤tr+60 without pull success; exact expiry boundary no JWT skew; cache loss/restart/time rollback/suspend invalidates trust. Reconciliation30 includes real lock/queue admission.
7. Rapid revoke→regrant hidden between polls still advances credential generation; old session/remember/OIDC callback/profile writes rejected. Pause a request before final save, revoke, cleanup, regrant, then resume its save: no old authenticated session INSERT.
8. FE-60 boundary run with dispatch5s and DB recovery/commit10s, starting from worst45s lease expiry; cleanup≤60 and B untouched. Over-budget fault truthfully marks cleanup breach while new auth denies. Crash before/after projection, fence, DELETE and ack converges safely.
9. Each listed browser/API/websocket/job entrance executes active/lease/generation checks at every new decision; no long-lived connection or cached principal escapes. Regrant permits only fresh authentication after cleanup/fence completion.

These are acceptance requirements, not executed tests or production proof. No implementation tests run for this document-only change. Future risk-appropriate package/root lint/PHPStan/Pest/PG/architecture/mutation receipts remain those declared in P4; PG isolation/preflight applies before destructive fixtures. Public API/DDL and dependency choices must first be explicitly released.

Recommend the explicit PKI registration + fingerprint retirement and durable per-pair credential generation because subject-only PKI rotation cannot enforce600s retirement and active-only snapshots cannot detect an intervening revoke.
