```php
// packages/core/src/Storage/ExportArchiveRef.php

        public string $storagePath,
        public int $sizeBytes,
        public \DateTimeImmutable $createdAt,

```

`StorageCapabilities` is an explicit proposed extension to B33 §4; owner approval is pending. `usageBytes()` reports nonnegative logical durable bytes, excludes ephemeral files and generated archives, and is not a transactional quota or billing writer. `exportArchive()` returns only after a complete bounded archive exists; `storagePath` is a relative reference in an owning export store, never credentials or a public URL. Exact limits proposed for local archive: 10,000 files / 1 GiB uncompressed input / 60 seconds, configured by trusted deployment only. Limit exceeded or unavailable capability throws `CoreX\Storage\StorageCapabilityUnavailable` (`packages/core/src/Storage/StorageCapabilityUnavailable.php`, extends `RuntimeException`); failed IO throws `CoreX\Storage\StorageOperationFailed` (same directory, extends `RuntimeException`). A failed/partial archive is removed, never returned as success. Unsupported cloud archive may use a separately approved owning archive adapter; until qualified, capability is false and export throws. Archive support does not imply backup/restore/move support.

Proposed implementations/configuration: `packages/core/src/Storage/LocalTenantStorage.php`, `packages/core/src/Storage/ScopedFilesystem.php`, `packages/core/src/Actions/Storage/ExportStorageArchive.php`, `packages/core/config/corex.php` storage section, core provider binding; `packages/tenancy/src/Storage/ContextTenantStorage.php`, tenancy provider/config bindings. Boxed context is the current resolver's constant account UUID `00000000-0000-7000-8000-000000000000`, `workspace=null`, no Stancl. Proposed trusted roots: `storage_path('app/corex/durable')` and `storage_path('app/corex/ephemeral')`; separate export root `storage_path('app/corex/exports')`. Cloud durable prefix `tenants/{TenantContext.account.id}/`; ephemeral root `storage_path('app/corex/ephemeral/{account-id}')`. Reject absolute paths, `..` segments, NUL/control characters and escaping symlink paths for every read/write/list/copy/move operation. Validate source and destination. Adapter captures account and root when acquired and checks current context on **each operation**; a retained A handle used under B fails rather than silently switching or reading A. Do not claim Flysystem's path normalization or `DISALLOW_LINKS` alone proves all symlink/stream isolation. Raw tenant `Storage::disk()` and underlying adapter access are forbidden; trusted driver construction is the scoped boundary exception.

Proposed Action `packages/tenancy/src/Actions/ClaimAccountSignup.php` implements this contract. Key is opaque nonempty ASCII, maximum 128 bytes; digest is lowercase SHA-256 of a caller-defined canonical **immutable mechanical request**, including cluster/template, never email, payment or role policy. IDs are canonical UUIDs. The trusted central caller validates permission and retries with the same key/digest; matching committed key returns the same accountId even after crash, never claims another pool row. A reused key with different immutable inputs throws `CoreX\Tenancy\Provisioning\ClaimConflict` (`ClaimConflict.php`, final DomainException); no available qualified template/pool throws `ClaimUnavailable` (final RuntimeException). Replayed means reservation exists, not full provisioning/saga completed.

Reservation plus key/input binding must commit atomically in root connection; unique conflict rolls back the losing reservation and rereads the winner. Never catch unrelated unique errors as replay. Template integrity is required before earliest claim/save/clone. No paid signup endpoint or saga `resume/compensate/replenishPool` API is added here. Pool return, tombstone retention/key reuse and uncertain external outcome need P3.1/P6.25 decisions; no automatic key release on compensation. The blueprint's partial expression index is only a P3.1 SQL candidate. P3.1 owns exact DDL/version/predicate/backfill/deployment tests and must decide tombstone policy before P3.2 dispatch.

Negatives: two concurrent same-key callers obtain one account; different keys never same reservation; key/digest mismatch fails; crash before/after commit; stale template; compensation/retry same durable key; tombstone/reuse; unique error unrelated to signup remains an error. No implementation or DDL proof is claimed.

## 5. Ordering, projection and sessions — CENTRAL-TRUST, PROJECTION-OWNER, SESSION-BINDING

Proposed no-new-DDL ordering strategy: authenticated event is an invalidation hint; queued account-local projector rereads an authoritative current MembershipSnapshot through approved central transport. Serialize refreshes for identity+account with the existing approved cache lock facility across jobs; read snapshot inside lock, update target local user status atomically before releasing. Delayed grant therefore observes latest revoke, not old payload. Duplicate hints are safe; profile `updated_at/synced_at` must not gate membership refresh. Snapshot must have source-owner-qualified freshness/consistency; cached or eventually stale reads do not prove safety. Cross-worker locking, account switch/cleanup and revoke-vs-in-flight request race require concrete tests. A failed read cannot reactivate a user; preserve inactive state and deny entry while authority is unresolved. These are proposed semantics requiring qualification; lock backend/deployment and failure policy are not silently selected.

Alternative source-issued monotonic revision with durable per-membership watermark is **not approved**: there is no established storage field. If central cannot supply authoritative serialized reread, prepare exact watermark schema/cache protocol and normative decision; do not repurpose profile timestamp or add columns in P4.3. Envelope version is opaque unless central separately specifies ordering. `occurredAt` is audit time, never sufficient ordering proof.

Status proposal: active only when identity/account are valid, membership exists, central says active and no applicable deletion. Missing, deleted, blocked, pending or unknown is inactive. Regrant requires fresh current active authority and re-enables the existing same UUID without merging contacts. Existing `DatabaseIdentitySyncer` reads/writes root sync bookkeeping and must stay management-only; it cannot become the tenant event subscriber. Proposed tenant-only Action path `packages/tenancy/src/Actions/ApplyMembershipProjection.php`; subscriber/job `packages/tenancy/src/Jobs/RefreshAccountMembership.php`. Only target tenant `users` and sessions are written; root bookkeeping belongs to management adapter. Deployment/caller qualification remains pending.

Session proposal `packages/tenancy/src/Jobs/RevokeAccountMembershipSessions.php`: account context initialized and released in `finally`; mark same-UUID local user inactive, delete only target account's database sessions with matching `user_id`; never shared session store or other-account rows. Event intake/queue/retries must achieve ≤60 seconds from authenticated central occurredAt to full deletion under declared clock tolerance. This measures full path, not just a synchronous DELETE duration. Guard denies inactive/deleted/missing user on next authenticated request, including restored cookie/session, remember-me, API and applicable websocket entrypoints. SSO immediate membership check remains central-owned regardless of this job's completion.

Actual consumer guard name, provider, session connection/table, queue, worker SLA, clocks, account binding and exact middleware/Action paths are **unknown**, not fabricated from CoreX primitives. `CoreX\Auth\Identity\PrincipalUserProvider` offers source-level active/deleted filtering but not consumer deployment or private compatible-install proof. Session fixture must supply two isolated account DBs and queue timing; no default tenancy→auth dependency. Exact qualification can select public consumer adapter without private auth implementation proof, or separately satisfy IMMUTABLE-PRIVATE.

Negatives: stale grant after revoke; duplicate event; forged actor/account/audience; missing/deleted/pending membership; profile unchanged block/regrant; same phone/different UUID; collision never merges; target-only session delete; expired/reused event; failed snapshot/worker; concurrent refresh and revoke; stale remember-me; ≤60s end-to-end. No auth/security implementation is reviewed or accepted by this documents-only item.

## 6. Switcher version recovery — SWITCHER-AUTHORITY

Preserve B34 no-DDL central Redis INCR, TTL300 seconds and current-client product filtering. Adapter only consumes accounts/version through `CentralApiClient`; no tenant root-membership reads, central Redis INCR, recovery server or SSO authority. Proposed fresh-recompute boundary when central version is missing: bypass any old list key, issue fresh authoritative active-membership query, and publish version/list as one qualified protocol. It must also cover concurrent revoke/regrant and subsequent INCR. `MAX(updated_at)` of active rows alone may repeat a prior version after removing the newest row; counter restart can similarly reach an old numeric key. Therefore no stale list is adopted merely because recovered version matches it.

Request central owner to prove: retain old list keys, lose only counter, revoke newest membership (including zero-active case), recompute, then regrant and INCR while old keys survive. Every reachable response must be freshly recomputed/current for this recovery contract, with product and identity bound. Existing key lacking product dimension must prove the token/client product cannot cross-hit another product's list; proposed product-scoped key change is separate normative decision if needed. This packet neither replaces canonical fallback with a random version nor adds a version column. If source cannot satisfy no-old-list-hit with canonical fallback, resolve disagreement before P5.1. Menu is never access authority; central authorize still denies immediately and returns 403 without account details.
