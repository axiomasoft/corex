## 1. API and caller boundary

Preserve existing PendingPool, ProvisionParams and TenantDatabaseProvisioner interfaces and signatures. Adopt only after exact contract-owner/major/tenancy CHANGELOG approval the P1.2 candidate `Contracts/ProvisioningClaim::claim(ClaimRequest): ClaimResult`, `Provisioning/ClaimRequest(requestKey, clusterId, templateId, requestDigest)`, `ClaimResult(accountId, replayed)` and Action `Actions/ClaimAccountSignup.php`. DTOs final readonly, strict types; new interfaces in Contracts. No new endpoint or package. Invalid request fails before writing; `ClaimConflict` rejects incompatible or tombstoned/ambiguous binding; `ClaimUnavailable` denotes no qualified reservable pool/template or unavailable producer. Transient transaction/connection faults remain explicit failures with uncertain commit handled by durable replay, never a false success.

This protocol selects **qualified pool reservation only**. The Action never calls existing `PendingPool::pullPending()` as a pre-step: it commits separately and can invoke `cloneOne()`, so wrapping its returned account with a later key save leaves an interruption gap. Existing pool helpers retain their ordinary semantics; only this approved Action is the keyed claim entrypoint. Empty/locked/unqualified pool returns ClaimUnavailable without creating an account or database. Synchronous empty-pool fallback is P6.25 work after a separately qualified durable same-key reservation/resume contract; callers must not bypass failure via unkeyed pullPending. This deliberate bounded choice does not claim the blueprint's full saga/latency acceptance.

Only the named, account-management-authorized central paid provisioner **FLEX-2 P6.25** may invoke the Action on the root management connection. Central owner must supply actual caller file/symbol, authenticated service/queue binding, request-key generation and storage, immutable digest algorithm, retry lifetime, compensation/purge policy and proof no HTTP/tenant/MCP path can directly call it. Logical ownership alone is not a discovered caller. D40 forbids CRM registration/create/grant/accept endpoints; billing/payment/owner roles, slug/domain writer and lifecycle policy stay outside L0. Public/API major, fixture DDL rights and caller authorization are independent gates.

Digest is caller-defined canonical immutable mechanical request including cluster/template IDs. Proposed concrete binding for approval: UTF-8 canonical JSON object with keys `cluster_id`, `template_id` (lowercase canonical UUIDs), sorted keys and no whitespace, no final LF; lowercase SHA-256. If caller requires additional immutable inputs, it must version and freeze the exact canonical payload before adoption; do not silently drop them. Compare stored digest **and** explicit cluster/template IDs on every replay. A key cannot migrate to another cluster/template by retry. Existing result `replayed=true` means committed reservation exists, not clone/seed/payment/lifecycle completion.

## 2. Producer boundary before earliest mutation

APPROVED-SPECS P2 owns template-integrity proof. P1.1 inspected readiness only; no portable current GREEN producer packet is supplied by this plan. Before P3.2 mutation, obtain actual producer journal terminal result/ref, approved seal/trust/DDL fixture, template ID/version, artifact digest and integrity evaluator's exact source hashes; requalify every relevant same-file delta. Missing/stale/mismatched proof denies claim/save/clone with zero mutation. Existing `readyTemplateFor()` only tests `status='ready'` and is insufficient.

Before a fresh reservation, evaluate approved integrity and lock/recheck the exact active cluster/template qualification in the root transaction. Bind selected pool row to cluster, template version and qualified artifact/embedding metadata; approved producer supplies actual mapping and invalidation semantics. No guessed root_templates FK or new JSON proof fields are installed by this proposal. Proof cannot change unnoticed between validation and save; qualification must bind locked producer metadata to the inspected sealed artifact. Later clone checks again through its own producer integration.

Read-only replay of a committed live binding can return the same accountId without claiming/cloning or rewriting status, even if the old template is no longer current. Any further mutation/clone requires current qualified producer proof. Admission of P3.2 as a whole still needs TEMPLATE-READY; this distinction prevents a template rotation from remapping an existing key. A pool row inconsistent with request/proof is skipped; no qualified row means failure, never fallback to another template.

## 3. Transaction lock, claim and uniqueness

Root DB, explicit **READ COMMITTED** transaction, all steps on the same transaction connection. Acquire **transaction-scoped** advisory lock first, then cluster/template qualification locks in fixed order, then one pool/account row. Proposed lock bigint: SHA-256 of ASCII bytes `corex:signup:v1:` concatenated with exact requestKey; take first eight digest bytes in big-endian order, interpret as signed two's-complement 64-bit integer, bind as a decimal string to `pg_advisory_xact_lock(CAST(:lock_id AS bigint))`. Never include requestDigest in the lock key: conflicting requests must serialize together. Hash collision causes extra serialization only; compare exact request keys for identity. Other root writers must adopt compatible ordering or prove isolation from these rows. Set a trusted finite transaction/lock timeout; no indefinite request wait.

Transaction-level advisory locks release at transaction end; session-level locks survive transaction rollback. PgBouncer transaction pooling releases the server connection at transaction end and does not support session advisory locks. The proposed lock fits that lifetime; it must remain inside the explicit transaction. [PostgreSQL 16 locking](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS), [PgBouncer feature matrix](https://www.pgbouncer.org/features.html). No Redis/session advisory lock or network clone occurs inside this claim transaction.

1. Validate trusted caller/request and key policy before opening a mutating transaction. Begin; acquire keyed transaction lock as a separate statement. Under READ COMMITTED a subsequent statement sees a winner committed while lock acquisition waited; do not use a stale pre-lock snapshot.
2. Read **all** root_accounts with `data->>'signup_key' = :request_key`, including soft-deleted rows; lock matching rows in UUID order. No implicit Eloquent SoftDeletes scope. One live compatible binding returns original accountId/replayed=true without status/template/key updates. Tombstoned, partial, incompatible or multiple bindings fail closed before any pool claim. Compare using qualified index/key collation semantics.
3. If no binding exists, require current producer integrity, lock/recheck active cluster and exact template metadata in deterministic order, then select one undeleted `status='pending'` row in that cluster/version, ordered by UUID, `FOR UPDATE SKIP LOCKED`. Exclude every row with any signup-binding member, including partial/orphan JSON. No same-row claim by different keys. No eligible row: rollback and ClaimUnavailable.
4. In **one UPDATE on the same transaction**, change pending→provisioning and merge all four §3 JSON members, preserving unrelated `data` keys and existing metadata; predicate confirms pending, undeleted and unbound. Exactly one affected row required. There is no save-before-key or key-before-reservation commit. Validate the account's cluster/template/embedding match; do not relocate or clone it.
5. Commit; only then return `ClaimResult(original accountId, replayed=false)`. The index is final race enforcement, not replaced by advisory/row locking. No external side effects in transaction callback, including queued clone dispatch on an uncertain commit.

If UPDATE raises **23505 for root_accounts_signup_key_uq specifically**, rollback the **whole losing transaction**, releasing its pool reservation; start a fresh READ COMMITTED transaction, reacquire the same keyed lock and reread all exact-key bindings. Compatible winner returns replayed=true; incompatible winner conflicts; no winner is bounded retry/failure, never fabricated success. Never query an aborted transaction, silently swallow unrelated slug/db uniqueness failures, or allocate a second account on response loss. Actual driver error extraction must prove constraint/index identity rather than treating every 23505 as signup replay.

Deadlock 40P01 / serialization 40001 / approved lock-timeout faults retry the whole transaction with the **same** key and immutable request, proposed maximum three attempts with bounded jitter; unchanged inputs only. Connection loss around commit is uncertain: reconnect and run the same exact-key protocol, never assume rollback. On timeout/exhaustion report retryable/uncertain failure; central caller retains its durable request and retries later. Advisory lock is coordination; partial index plus approved all-writer/tombstone policy is the stated enforcement boundary, not a claim of uniqueness across physical purge.

## 4. Fault and saga ownership matrix — V-REPLAY

| Fault boundary | Package invariant / observable test | P6.25 saga responsibility |
|:--|:--|:--|
| Invalid/conflicting key or inputs before claim | Zero new binding/row/status change; ClaimConflict/validation failure | Reuse exact immutable request; decide user/payment outcome |
| Two same-key transactions | Both return one accountId; one fresh/one replay; one reserved row | Durable key passed to every retry |
| Same key, different digest/cluster/template | Losing request conflicts before pool reservation | Do not reinterpret one key as another signup |
| Different keys, overlapping pool | Distinct reserved accountIds; row locks prevent double reservation | Pool capacity/replenishment |
| After row selection, before atomic UPDATE | Process failure rolls back; row remains pending/unbound | Retry same key |
| After UPDATE/key save, before commit | Full rollback restores status/data; no externally successful reservation | Retry same key; no clone from uncommitted result |
| Unique race from writer without advisory coordination | Losing transaction rolls back; named signup constraint reconciles winner only | Admit compatible writer/lock protocol; investigate bypass |
| Commit succeeded, return/ACK lost | Replay finds original accountId; no extra pool claim or clone | Durable retry record, no new key on network failure |
| Missing/stale integrity before first write | Zero mutation; ClaimUnavailable | Obtain approved producer proof, never ready-only bypass |
| No qualified/unlocked pool row | Zero account creation/clone; ClaimUnavailable | Approved replenishment/synchronous fallback, durable recovery before any external call |
| After reservation, before clone/activation | Replay returns reservation, not completion; no Action clone | Resume original account, verify outcome/current template proof |
| Clone call interrupted/remote outcome unknown | Claim replay never creates another account/database | Reconcile deterministic database identity and sealed artifact; do not assume existence means complete |
| Slug/owner/domain step fails | Package binding remains intact; no key clearing/transfer | Own transaction/422/lifecycle compensation with same logical account identity |
| Profile sync or vertical seed fails | Same durable claim result; no package seed/DROP | Idempotent sync/seed, bounded retries/DLQ and separately authorized reset |
| Compensation callback repeats/crashes | Same live accountId and binding; zero extra clone/claim | Journal/reconcile compensation; never return keyed row to general pool |
| Tombstone / restoration / purge / key reuse | retain-deny; reject ambiguous/malformed binding; restoration collision fails | Explicit retention/reuse/epoch decision and authoritative record before purge |
| Unrelated unique violation / retry exhaustion | Original error/explicit uncertain failure, never replay success | Operational diagnosis; durable retry instead of unkeyed fallback |

B33 §3.2's return-to-pool and DROP+new-bolvanка compensation must be reconciled with durable key identity by **P6.25 owner**, not implemented mechanically here. Proposed policy: a committed keyed row never goes back into the general pool; any physical database reset/reclone retains its logical accountId and key, with separately approved irreversible resource handling. If central instead requires replacement accountIds, it must provide a durable logical-request→result routing contract and amend this proposal before P3.2. The two-field ClaimResult cannot honestly encode a full resume/compensation saga. Existing provisioner refires TenantCreated and mutates metadata; that source observation proves neither full integrity nor crash-safe clone completion.
