## Exact mapping

The test-owned `membership_pair_references` table uses `(account_id uuid,
identity_id uuid)` as its primary key. Each of `revision`,
`revoke_generation`, `local_epoch`, `operation_fence`, and nullable
`application_fence` is `numeric(20,0)` with an explicit `0 <= value <=
18446744073709551615` check. `operation_id` and `barrier_id` are nullable UUIDs;
`denied` is a non-null boolean.

PHP validates canonical unsigned decimal input (`0` or nonzero non-padded
digits through unsigned64 max) before binding it to SQL. It rejects negatives,
fractions, exponents, non-finite values, noncanonical leading zeroes, and
overflow; PHP integers and floats are never used for these counters. SQL
increments `operation_fence` and `local_epoch` in the database, rather than in
PHP. Comparison uses decimal length then byte comparison after validation.

`admit()` serializes a pair row with `FOR UPDATE`; replaying the same operation
UUID returns its existing F. A different operation atomically increments F while
leaving a still-committed AF untouched. `commit()` has a CAS on the stored
operation UUID and cannot commit while denied. `invalidate()` records a barrier,
increments E once for that barrier, sets `denied`, and clears AF. `restore()` is
closed without a nonrollback witness, refuses a witness below any persisted
R/G/E/F high-water mark, clears AF, and remains denied.

The fixture is created and dropped by `PairStoreFixture` only. There is no
production migration, table registration, config, service binding, or runtime
consumer.
