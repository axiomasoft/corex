# B-01 — Глобальный Blueprint экосистемы Flex (v1, на утверждение)

> Синтез R-00..R-08. Статус: **draft → чекпойнт с пользователем**.
> Детали каждого домена — в соответствующем R-отчёте; здесь — решения уровня экосистемы.

## 1. Философия и деплой-модели

Экосистема = «Битрикс-модель, сделанная правильно»: одно модульное ядро, продукты = наборы модулей, маркетплейс, но — строгая типизация (PHPStan 8), composer-обновления, прозрачность вместо магии, MCP для разработчиков, open-core как воронка доверия.

**Два деплой-режима одной кодовой базы (новое требование):**

| Режим | Кто | Tenancy |
|---|---|---|
| **Cloud SaaS** | FlexCRM, FlexStore (cloud-first) | DB-per-account + внутренние workspace (D1) |
| **Boxed / self-hosted** | FlexCMS (всегда), FlexCRM/FlexStore (перспектива) | single-account: та же схема БД, tenancy-слой выключен, TenantContext = константа |

Следствие: **ни один модуль не хардкодит облако** — всё через `TenantContext{account, workspace}` (value-object ядра) и `AccountConnectionResolver` (интерфейс; boxed-реализация тривиальна). Это же — эскейп-хатч для Citus/shared-режимов в будущем (R-05).

### 2.3 Extension model (ревизия принципа «события — единственный extension point»)

Гибрид (R-04, урок Flarum): **события для поведения + узкий ярус ~8 типизированных extenders для структуры**: `Extend\Entity`, `EntityField`, `Api`, `Filament`, `Menu`, `Permissions`, `Routes`, `Workflow`. Новый extender — только через RFC (вечный контракт ядра). WP-hooks отвергнуты. Capabilities-флаги сущностей (`commentable`, `documentable`, `attributable`) декларативно подключают спутники Chatom/Vaulter/attributes — это и есть «панель на сущности» (§5).

**Терминология структурных единиц (D14, маппинг на Битрикс):** **пакет** (composer-единица дистрибуции) → **модуль** (единица активации в аккаунте, аналог модуля Битрикса; один пакет = один модуль) → внутри модуля: обычные Laravel-провайдеры + **компоненты** (аналог компонентов Битрикса: класс + параметры + шаблоны с 3-уровневым переопределением app → тема → пакет на нативных view namespaces). Компонентный примитив — общеэкосистемный (нужен и commerce-витрине, и CMS) — граница пакета решается в B-10/B-17 (кандидат: отдельный corex/components).

## 3. Конвенции БД (обновление)

| Конвенция | Решение |
|---|---|
| PK | **UUIDv7** (ревизия ADR-003; нативный uuid-тип PG 16 байт, time-sortable — PK-курсоры пагинации, read-state чатов) |
| Префиксы | ≤3 симв + `_`: `com_ crm_ tsk_ wfl_ mod_ fld_ cht_ vlt_ ai_ cms_ aut_ wsp_ med_ ntf_ sys_ vrt_ pnl_ ie_`; корневая БД: `root_` |
| Деньги | bigint minor units + currency (ADR-005 без изменений); NUMERIC для количеств (14,3) |
| Безопасность схемы | partial unique WHERE deleted_at IS NULL; timestamps на ВСЕХ таблицах включая справочники (инвалидация кешей); CHECK-констрейнты на enum-строках |
| Деревья | ltree (+parent_id для FK/UI): категории, подразделения, workspace |
| Фасеты/поиск | 3 слоя: нормализованный источник истины → jsonb+GIN проекция (та же транзакция) → Meilisearch (dirty-флаги, листинги и facet counts) |
| Min PG | PG 16+ (NULLS NOT DISTINCT, производительность ltree/GIN); финализировать в ADR |
| MySQL | слой совместимости отложен; запасные паттерны зафиксированы в R-отчётах (напр. materialized ancestors вместо ltree) |

## 4. Tenancy end-to-end (детализация D1)

```
id.flex.ru (центральный IdP, OIDC)          корневая БД (root_)
        │                                    аккаунты/домены/ячейки, root_identities,
        ▼                                    тарифы/подписки (billing), фичефлаги,
*.flexcrm.ru ──► ячейка PG                   control-plane миграций, lifecycle-аудит,
(wildcard TLS,   (PgBouncer transaction      каталог маркетплейс-шаблонов
 CNAME custom)    mode, ~700 БД soft-limit,
                  pgBackRest)
                        │
                        ▼
              acc_<uuid> БД аккаунта: все mod_/crm_/com_/… таблицы
              внутри: wsp_workspaces (ltree, type=company|partner) → workspace_id-скоуп
```

- **Провижининг**: `CREATE DATABASE … TEMPLATE golden` + pending-пул преднарезанных БД → signup за секунды.
- **Миграции парка**: expand-contract, волны internal→canary→all через root_migration_batches; lazy-миграции маркетплейс-модулей.
- **Тариф — атрибут аккаунта**, не workspace. Модули включаются **per-account**; workspace получает feature-флаги.
- **Free tier**: нет; **трайл 14–30 дней с полноценной БД → экспорт → grace → DROP** (решение чекпойнта).
- **Мультипродукт**: одна БД аккаунта, FlexCRM/FlexStore = наборы модулей (решение чекпойнта); эскейп-хатч выноса витринной нагрузки — реплики/кеш, не вторая БД.
- Бэкапы per-ячейка, restore аккаунта через PITR-lab; РФ-ЦОД (ФЗ-152).
- Cross-tenant аналитика: MVP nightly-агрегаты в root_; позже CDC→ClickHouse.

## 5. Спутники: контракт «панель на сущности»

Единый паттерн (R-08): корневой объект панели (канал, хранилище) морфится `panelable_type/id` на любую сущность из EntityRegistry; доступ двухуровневый — gate 1 = AzGuard-право на родителя, gate 2 = participant-роль панели (только расширяющие переопределения). Реализации: Chatom (комментарии к задаче/сделке, обсуждения), Vaulter (файлы/документы сущности; грант-модель vlt_grants по семантике Google Shared Drives, локальная модель документа — сервисная UUID/org_id-модель **упраздняется**), activity-панели. Vaulter-коллаборация: **Hocuspocus-sidecar** (JWT-auth от Laravel, персистенция webhook'ом; Reverb+y-websocket отвергнут — нет серверного Y.Doc для PHP).

Маркетинговая логика: открытые пакеты = воронка доверия и комьюнити («чего нет у Битрикса»), продукты и вертикали = монетизация, маркетплейс = экосистемный ров.

## 7. Маркетплейс (v1-контур)

- **Два tier'а** (урок Shopware, ревизия по HubSpot R-18b/п.11-12): verified-модули (авторевью: PHPStan 8, testbench, запрещённые API, префиксы D9 → входят в образ SaaS, тенант включает per-account) и внешние apps (webhooks + scoped-токены) — v2. Второй, добровольный слой сертификации verified-модулей (порог по установкам + validity period, аналог HubSpot certified apps) — v1.1/v2, не блокирует v1-листинг.
- Дистрибуция платных пакетов: **свой composer-репозиторий + license key как composer-credential** (Anystack/Spark-паттерн; РФ-эквайринг, 54-ФЗ). Private Packagist — только референс.
- **Комиссия сегментирована по типу актива, не единая ставка** (ревизия по HubSpot R-18b/п.11 — у HubSpot 0% на App Marketplace, 20% только в Solutions Partner Program на перепродаже подписок, у нас нет аналога перепродажи подписки): verified-модули — **без отдельной комиссии**, монетизация через тариф аккаунта (код входит в образ SaaS, площадка не берёт долю с продажи самого модуля); внешние платные apps — **комиссия 20–25% остаётся** (Statamic 25% = рыночный верх) как единственный монетизационный рычаг вокруг чужого, не ревьюженного кода; студийные внедрения (FlexCMS) — revenue share на услугу, не на код (MIT).
- Editions standard/pro в манифесте модуля с первого дня.
- **MCP-сервер для авторов модулей** (ревизия по HubSpot R-18b/п.13 — заявка «без аналогов» не подтвердилась: HubSpot Developer MCP Server, GA весна 2026, даёт похожий набор docs/scaffold/validate/deploy/sandbox/analytics): интроспекция EntityRegistry/extension points, scaffold-генераторы, песочница с эфемерной tenant-БД, пре-ревью `module.lint`, статистика продаж. Реальный дифференциатор — **единый реестр между dev-tooling и рантаймом** (ModuleRegistry/EntityRegistry — те же контракты, что использует прод, а не отдельный слой), **локальная офлайн-песочница** (template-клон тенантской БД, не сетевой вызов к облачному тестовому аккаунту), и **работает для boxed-инсталляций** (у HubSpot self-hosted нет вообще).

## 8. Агентный слой

- Агент = RBAC-principal (роль через role_target); права запуска = intersection(инициатор, роль агента); автономные запуски — роль + сервисный run_as.
- Один ToolRegistry → внутренний AgentRuntime + MCP-сервер FlexCRM; тулзы workflow-уровня (`crm_deal_get_context`, `wfl_process_diagnose`), генерация per-entity CRUD из EntityRegistry; auth v1 — Sanctum PAT, v1.1 — OAuth 2.1 PKCE.
- Голос: SpeechKit streaming → LLM-экстракция типизированных команд с confidence → resolver → риск-тирное подтверждение.
- AI-шаг workflow: input_map + ссылка на версию агента + output_schema + раздельные failure_routes (semantic/technical).
- Вертикали поставляют агентов секцией `agents:` манифеста.

## 9. Вертикали (подтверждено рынком, R-02)

Двухуровневые: **пресет-манифест YAML** (сущности/поля/воронки/процессы/роли/агенты/сиды; идемпотентный installer; Б24 «Готовые CRM»-класс) и **composer-приложение с кодом** (Salesforce managed package-класс) для сложных отраслей. Иерархия: базовая CRM → отраслевые (строительство, УК, недвижимость, …) → до ~20 решений; деактивация без потери данных.
