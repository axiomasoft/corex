## P2-Q3

**Запрос (повтор).** Explain in prose first, do not start with a table. What
fields belong in a shared-database table ownership catalog for a modular
monolith: owning capability, writers versus readers, PII class, retention and
restore policy, upgrade strategy, and why a shared name prefix must not imply a
single owner. Shopify engineering componentization and Spring Modulith
documentation. Name primary-source URLs.

**Статус.** success (первая попытка — timeout MCP `-32001`; повтор успешен)

**Смысловые утверждения.**

A shared-database ownership catalog is the missing governance layer between “we
use one PostgreSQL database” and “we have modular boundaries.” Shopify’s
componentization: components retained a single deployable application and could
use a shared database, but each component was expected to have a public
interface and exclusive ownership of its associated data. Cross-component Active
Record associations and data coupling were treated as violations.

The catalog should distinguish capability ownership from team ownership.
“Owner” does not mean “the only process that ever executes SQL.” It means that
one capability owns the table’s meaning and decides its schema, invariants,
mutation semantics, and lifecycle. Writers and readers are different risks and
need separate declarations.

A reporting module may be a reader but must not UPDATE source data. If another
capability needs state changed, it should call the owner’s application API or
submit a command/event.

Do not put only `contains_pii: true`. Use a class (public / internal /
pii_direct / pii_indirect / sensitive / credentials / regulated) and field-level
annotations where classification differs inside a table.

Retention must be executable: clock, duration, disposition, named mechanism,
evidence. Restore fields matter for PII: backups can resurrect erased data.
“We have PITR” is not a restore policy.

Default upgrade pattern: expand → migrate/backfill → switch consumers →
contract. The catalog captures who may migrate, who might break, and how
compatibility ends.

A shared prefix is a naming convention, not a bounded context. Prefix-alike
tables can belong to different capabilities (source, snapshot, reporting,
legacy map, outbox). Prefix drift is expected; the catalog must name the owner
independently.

Make the catalog part of delivery: a PR that creates or substantially changes a
table updates the catalog; CI checks owner match; exceptions expire.

- https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity
- https://docs.spring.io/spring-modulith/reference/fundamentals.html
- https://docs.spring.io/spring-modulith/reference/documentation.html

## P2-Q4

**Запрос.** Explain in prose first, do not start with a table. How Laravel config
files and Symfony Config component document each configuration key: owner
package, PHP type, default, secret flag, deployment versus runtime mode, whether
the value is reloadable, validation at boot, typed options objects, and
deprecated aliases. Official Laravel 12 and Symfony 7 documentation. Name
primary-source URLs.

**Статус.** success

**Смысловые утверждения.**

Laravel 12 primarily uses executable PHP arrays in `config/*.php`. The key name,
package/file ownership, default expression, and comments form the documentation.
Symfony 7’s Config component lets a package define a formal configuration tree
(node types, defaults, validation, deprecations). Neither framework provides a
universal built-in metadata field for secret, deployment/runtime, or reloadable;
those properties must be expressed by convention or your own schema layer.

Laravel: public key is `file.nested.path`; owner is inferred from the file.
Types are represented by PHP values and casts. `env()` second argument is the
default input if the variable is absent. Typed accessors (`Config::string` /
`integer` / `boolean` / `array`) validate on retrieval; they are not a centrally
inspectable schema.

Laravel has no generic per-key `secret: true`. Secrets are signaled by env
names, comments, and keeping values out of committed files. `config:show`
redaction is not automatic from key metadata.

After `php artisan config:cache`, Laravel does not load `.env` on requests;
`env()` should be called only inside configuration files. Cached configuration
is deployment-time immutable per PHP process. Long-lived workers do not see
source-config changes until recycle.

Symfony Config Definition validates merged configuration at container/config
compilation. `setDeprecated()` exists on nodes. OptionsResolver is complementary:
array-shaped input boundary; a readonly options object is built separately after
resolve.

Laravel has no universal config-key deprecation registry. Aliases must be
implemented deliberately and tested under `config:cache`.

**Первичные источники.**

- https://laravel.com/docs/12.x/configuration
- https://symfony.com/doc/7.0/components/config/definition.html
- https://symfony.com/doc/7.0/components/options_resolver.html
- https://symfony.com/doc/7.4/configuration.html

## P2-Q5

**Запрос.** Explain in prose first, do not start with a table. Architecture
fitness functions and package quality scorecards: typical measurable axes such
as public API control, hidden framework coupling, test isolation, configuration
surface, data ownership, worker safety, and backward-compatibility checks.
Primary sources from Neal Ford architecture fitness functions and PHP/Laravel
package quality practice. How to keep a scorecard from becoming a KPI. Name
primary-source URLs.

**Статус.** success

**Смысловые утверждения.**

An architectural fitness function is an objective check of one or more
architectural characteristics. It can be a test, static analysis, metric,
monitor, log, or periodic review. Name the properties that must not be
accidentally destroyed, and make their state observable.

Do not start with scores. For each row fix: architectural intent, checkable
rule, verification mechanism, threshold and reaction, context.

The most dangerous transformation of a scorecard is from engineering feedback
into a ranking of people, teams, or PRs. Then metrics are gamed. Prefer
thresholds and evidence over a total. Do not use an arithmetic mean: a missing
migration test cannot be compensated by excellent documentation. Use categories
(blocking / required-before-release / warning / informational). Measure the
system, not author productivity. Exceptions need owner, reason, review date.

SemVer itself does not verify compatibility; a fitness function comparing a
supported tag to HEAD does. Configuration is also API. Worker safety is about
at-least-once and idempotency, not “whether jobs exist.”

Laravel Testbench is the foundation for package install-like tests, not a reason
to boot the framework for every unit check.
