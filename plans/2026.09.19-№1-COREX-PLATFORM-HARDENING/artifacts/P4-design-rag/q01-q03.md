# P4-Q1 … P4-Q3 — захват ответов

## P4-Q1 — собственный интерфейс часов или `psr/clock`

**Статус:** success. Ответ начат прозой.

Для библиотеки на PHP в 2026 году следует зависеть от `psr/clock` и типизироваться против
`Psr\Clock\ClockInterface`, а не публиковать собственный эквивалентный интерфейс. PSR-20 —
завершённый стандарт PHP-FIG с намеренно крошечным контрактом; он даёт потребителю свободу
подставить реализацию Symfony, Lcobucci или собственную без адаптеров.

Собственный интерфейс оправдан только тогда, когда абстракция намеренно **не** «прочитать
текущее стенное время»: бизнес-календарь, инъектируемая таймзона тенанта, монотонный источник
истёкшего времени, симуляция расписаний, операции сверх `now()`. Не вводите локальный
`ClockInterface` только ради возможности замокать `now()` — именно эту задачу PSR-20 и
стандартизирует.

Контракт состоит из одного метода:

```php
namespace Psr\Clock;

interface ClockInterface
{
    public function now(): \DateTimeImmutable;
}
```

Возврат — именно `\DateTimeImmutable`, не Unix-int, не изменяемый `DateTime`, не Carbon и не
произвольный `DateTimeInterface`. Следствия: результат неизменяем; несёт таймзону; для
epoch-секунд вызывается `->getTimestamp()`; для долей секунды — `format('U.u')`. Спецификация
намеренно не добавляет отдельных методов timestamp/точности. Политику таймзоны из PSR-20
выводить нельзя: реализация может быть настроена на UTC, системную или прикладную зону. Для
долговечных бизнес-данных здравый дефолт — хранить моменты в UTC, а явную зону передавать
только при интерпретации локальных правил.

Реализация, которая сама предоставляет часы, объявляет виртуальный пакет:

```json
{ "provide": { "psr/clock-implementation": "1.0" } }
```

Официальный пакет прямо говорит, что `psr/clock` — только интерфейс, не системная реализация,
и документирует виртуальный пакет `psr/clock-implementation` для реализаций.

Экосистемное принятие значимо: Symfony Clock (`NativeClock`, `MockClock`, `MonotonicClock`),
`lcobucci/clock` (`SystemClock`, `FrozenClock`; собственный `Lcobucci\Clock\Clock` —
исторический контракт, поэтому для нового интероперабельного кода граница — именно PSR-20).
Practical qualification: PSR-20 стандартизирует только чтение гражданского времени; фабрику
часов, sleep, продвижение фейкового времени, политику таймзоны и монотонное время он не
стандартизирует.

Паттерны тестов. Минимальный — анонимная реализация с одним замороженным моментом
`[листинг сокращён]`. Symfony `MockClock` стартует с заданного момента и стоит, пока явно не
вызовут `sleep()`/`modify()`; в отличие от настоящего `sleep()`, продвижение мгновенно —
подходит там, где поведение само зависит от прохождения времени (expiry, backoff, grace,
cooldown, расписания). `lcobucci/clock` даёт пару `FrozenClock` / `SystemClock::fromUTC()`.

Laravel и Carbon. `Carbon::setTestNow()` — статический глобальный override времени Carbon, а не
замена инъекции часов. Он влияет на «сейчас» Carbon, и на нём построены помощники Laravel:
`travel()`, `travelTo()`, `travelBack()`, `freezeTime()`, `freezeSecond()`, которые управляют
временем, возвращаемым `now()` и `Illuminate\Support\Carbon::now()`. Closure-форма
(`$this->travelTo($at, fn () => …)`) восстанавливает нормальное время по выходе из замыкания.

Архитектурная ловушка названа прямо: если сервис получил `NativeClock`/`SystemClock`, заморозка
Carbon его не затрагивает; и наоборот — инъекция замороженного PSR-часов не меняет стороннего
пакета, который внутри зовёт `Carbon::now()`. Прагматичная схема для Laravel-приложения:
инъекция PSR-20 в собственных доменных сервисах; реальная реализация в production и
замороженная в тестах; `travel*` — только там, где предметом теста является само поведение
Laravel/Carbon/глобальных хелперов; если тест обязан покрыть оба мира — настраивать оба
согласованно и всегда восстанавливать статическое состояние Carbon.

Первичные источники: `https://www.php-fig.org/psr/psr-20/`,
`https://www.php-fig.org/psr/psr-20/meta/`, `https://packagist.org/packages/psr/clock`,
`https://packagist.org/providers/psr/clock-implementation`,
`https://symfony.com/doc/current/components/clock.html`,
`https://github.com/lcobucci/clock`,
`https://laravel.com/docs/12.x/mocking#interacting-with-time`,
`https://github.com/briannesbitt/Carbon`.

## P4-Q2 — версионирование payload'а, пересекающего durable-границу

**Статус:** success. Ответ начат прозой.

Payload, пересёкший durable-границу (очередь, outbox, чекпойнт, event store, запись повтора), —
не «DTO, сериализованный для удобства». Его прочитает код, развёрнутый недели или годы спустя,
и он может быть переигран при отказе. Его JSON-форму, семантические инварианты и байтовое
представление надо трактовать как версионированный протокол.

Безопасный дефолт: у каждого сохранённого конверта есть явная версия формата; каждый читатель
валидирует ожидаемую структуру **до** побочных эффектов; каждая поддерживаемая историческая
версия детерминированно приводится к одному текущему внутреннему представлению. Не «делать
так, чтобы заработало» через дефолты там, где отсутствие значения меняет смысл: это
превращает повреждение данных или ошибку раскатки producer/consumer в правдоподобную, но
неверную работу.

Версия должна лежать в самой durable-записи — не в версии деплоя, не в имени очереди, не в
имени класса, не в эвристике «какие поля присутствуют». Конверт стабилен, а ревизия схемы
отделена от имени бизнес-события и от ревизии потока/агрегата `[листинг сокращён: пример
конверта с полями type, format_version, event_id, occurred_at, payload]`.

Явный конвейер приёма: строгий разбор JSON; отказ на дублирующихся именах членов, битом
Unicode, недопустимых числовых формах и любом неверном конверте; требование `type` и
`format_version` с проверкой типов и значений; выбор декодера/апкастера по паре
(`type`, `format_version`); **отказ на неизвестной версии — не интерпретировать её как
«вероятно, последняя»**; валидация всех обязательных полей и семантических ограничений именно
той исторической версии; апкаст к текущему каноническому сообщению; валидация и результата;
вывод ключа идемпотентности из строго определённого канонического входа; и только затем —
доменная логика или внешний эффект. Джоб с будущей версией уходит в карантин/dead-letter с
сырыми байтами, ID записи, идентичностью producer'а и причиной, а не в обычную обработку с
угаданной семантикой.

Почему «fail closed». `$currency = $payload['currency'] ?? 'USD';` опасен: отсутствие ключа
может означать баг producer'а, частично записанную или усечённую запись, смену сериализатора,
чужое событие в этом потребителе или будущую версию, чьи поля непонятны. Обработать это как
USD — изменить финансовый факт. Если исторически v1 действительно означала «валюта всегда
KZT», это знание кодируется в апкастере `V1 → V2`, а не в `?? 'KZT'` у конечного потребителя.
То же — про частичную сборку объекта: нельзя схлопывать «отсутствует», `null`, «пусто» и
«невалидно» на этапе десериализации, у них разный бизнес-смысл.

Апкастер — чистое преобразование на чтении, между сырым историческим payload'ом и текущими
обработчиками. Marten описывает это как middleware между десериализацией и логикой
приложения. Предпочтительна цепочка мелких соседних миграций, а не одна непрозрачная функция
«любое старое → v7»: соседние преобразования обозримы, тестируемы и сохраняют ответ на вопрос
«когда появилось это семантическое правило». Апкастеры обязаны быть чистыми (без сети, часов,
БД, случайных ID и изменяемой конфигурации), детерминированными и идемпотентными; нельзя
дозаполнять старое событие «текущим профилем клиента» — это переписывание истории на реплее.
Исходные байты сохраняются; нормализованная форма — производная read-модель. Каждая
историческая фикстура тестируется против финальной текущей формы. Счётчики по паре
(`type`, `format_version`) мониторятся, чтобы видеть, когда старые формы перестали приходить.

Хеширование и идемпотентность. Порядок ключей JSON семантически незначим, но хеш считается по
байтам: `{"invoice_id":"inv_123","currency":"KZT"}` и `{"currency":"KZT","invoice_id":"inv_123"}`
дают разные отпечатки. Для любого хеша, подписи, контент-адреса или отпечатка идемпотентности
надо зафиксировать точную последовательность байт. Ровно для этого существует RFC 8785 (JSON
Canonicalization Scheme): строгая ECMAScript-сериализация примитивов, ограничения I-JSON,
детерминированная рекурсивная сортировка свойств, UTF-8. Детали строже, чем «отсортировать
ключи»: свойства объектов сортируются рекурсивно; массивы сохраняют порядок элементов
(канонизируются только объекты внутри них); пробелы опускаются; имена свойств сравниваются как
последовательности кодовых единиц UTF-16, а не по локали; числа сериализуются по
ECMAScript/IEEE 754, NaN и бесконечности недопустимы; дублирующиеся имена свойств запрещены.

Не хешировать весь транспортный конверт, если не каждое его поле входит в логическую
идентичность: `attempt`, `queued_at`, трассировочные ID, метаданные доставки и
перегенерированный message id меняются между повторами и убивают идемпотентность. Включать
надо то, что меняет наблюдаемый эффект: получателя, вид действия, сумму, валюту, ревизию
бизнес-объекта.

Оговорка по RFC 8785: это не `json_encode()` с `ksort()`. Спецификация ограничивает JSON до
I-JSON и определяет совместимость примитивов с ECMAScript, что влияет на точность целых и
формат чисел с плавающей точкой; значения за пределами диапазона IEEE 754 double рекомендуется
представлять строками. Для PHP это означает: строки для minor units денег, ISO-8601 для
времени, строки для UUID и больших идентификаторов; не использовать PHP-специфичную
сериализацию объектов как durable-контракт; выбирать реализацию JCS с тестами соответствия, а
не предполагать, что `ksort()` + `json_encode()` реализуют RFC 8785 (особенно по Unicode-порядку
и числовым краям).

Первичные источники: `https://www.rfc-editor.org/rfc/rfc8785.html`,
`https://www.rfc-editor.org/info/rfc8785/`, `https://martendb.io/events/versioning.html`,
`https://martinfowler.com/eaaDev/EventSourcing.html`.

## P4-Q3 — что сбрасывается между единицами работы в долгоживущем процессе

**Статус:** success. Ответ начат прозой.

В долгоживущем Laravel-процессе PHP-процесс и большая часть загруженного графа приложения
переживают переход от одной единицы работы к следующей. Laravel/Octane сбрасывает выбранное
framework- и lifecycle-состояние; он **не** делает каждый запрос или джоб эквивалентом
свежего PHP-FPM-процесса. Безопасная модель: новая единица работы получает новый lifecycle
scope, но не новый процесс, не новую статическую память и не автоматически чистый контейнер.

Что сбрасывается. Биндинг, зарегистрированный через `scoped()`, кешируется не дольше одного
цикла запроса/джоба и отбрасывается на старте следующего. Это правильное время жизни для
изменяемого контекста тенанта, per-job correlation-контекста, аккумулятора и unit-of-work.
На уровне контейнера `forgetScopedInstances()` очищает внутренний кеш scoped-экземпляров; он
**не** снимает биндинги, не пересобирает приложение, не очищает обычные singleton-экземпляры,
не восстанавливает конфигурацию и не трогает статические свойства PHP. Полезное различение:
регистрация `scoped()` живёт весь срок воркера; объект, созданный из неё, очищается на границе
цикла; на следующей единице работы та же регистрация создаёт свежий объект.

Octane заявляет автоматический сброс своего first-party framework-состояния и держит
sandbox/reset-цикл вокруг каждой операции. Это намеренно **не** гарантия восстановления
произвольного состояния вашего кода, singleton'ов пакетов, статических переменных, глобалей и
состояния внешних клиентов. Конфигурируемый список `octane.flush` — opt-in механизм для
конкретных экземпляров контейнера, а не универсальный рубильник.

Что не сбрасывается. `singleton()` означает, что после первого разрешения контейнер всегда
возвращает тот же объект; это несовместимо с хранением изменяемого tenant/request/job-состояния
внутри singleton'а. Если singleton впервые разрешён при активном тенанте A, он хранит тот
`CurrentTenant` навсегда — даже если сам `CurrentTenant` был `scoped` и позже корректно
очищен, singleton по-прежнему держит старую ссылку `[листинг сокращён]`.

Документация Octane специально предостерегает от инъекции контейнера приложения, HTTP-запроса
или репозитория конфигурации в конструктор объекта, переживающего запросы, — особенно
singleton'а. Захваченный request несёт старые заголовки, ввод и query-параметры в будущие
запросы; singleton, держащий прежний config-репозиторий, может не увидеть изменённых значений.
Альтернатива из документации — resolver-замыкание, получающее текущий экземпляр в момент
использования, либо отказ от singleton-времени жизни вовсе.

Статические свойства никогда не scoped: это обычная память процесса. Octane приводит пример
статического массива, растущего с каждым запросом; документация очередей даёт парную оговорку —
статическое состояние, созданное или изменённое приложением, между джобами не сбрасывается.
`config()->set()` — мутация живого состояния процесса; `forgetScopedInstances()` не откатывает
этот ключ, и следующий тенант может его унаследовать. `app()->instance(Foo::class, $foo)` кладёт
объект в обычный кеш экземпляров: он «всегда будет возвращаться при последующих обращениях к
контейнеру» и не превращается в scoped только потому, что вызван во время запроса;
`forgetInstance()` убирает только сам экземпляр и не отменяет объекты, уже захватившие ссылку.

Надёжная граница тенанта: сделать контекст явным lifecycle-сервисом и гарантировать teardown в
`finally` независимо от успеха `[листинг сокращён: CurrentTenant::set/require/clear и
TenantUnitOfWork::run с try/finally]`. Для HTTP — middleware, для очередей — job middleware
вокруг `$next($job)`; критично, что обычный код после `$next($job)` **не** выполнится при
исключении — нужен именно `finally`.

Регрессионный тест. Сильнейшая форма — два последовательных прогона в одном объекте приложения:
намеренно загрязнить каждую категорию, дать тенанту A упасть, затем доказать, что тенант B
стартует чисто `[листинг сокращён: тест с LegacyTenantSdk::$tenantId, config(), instance(),
исключением в A, forgetScopedInstances() и проверками в B]`. Сигнал улучшается разделением на
три вида проверок: позитивная (объекты A и B из `scoped()` различны по идентичности —
`assertNotSame`), негативные регрессии (singleton, захвативший контекст; статическое свойство;
`instance()`-override; мутация конфига) и проверка ветки с исключением. Ключевое требование:
B обязан инспектировать состояние **до** того, как его собственный инициализатор что-либо
запишет, иначе реализация, которая течёт и затем маскирует утечку перезаписью, пройдёт тест
ошибочно. Для очередей `Queue::fake()` доказывает поведение диспетчеризации, а не поведение
переиспользуемого демона: тестировать надо middleware/обёртку напрямую двумя исполнениями в
одном тестовом приложении.

`https://laravel.com/docs/12.x/queues`, `https://laravel.com/docs/12.x/container`,
`https://api.laravel.com/docs/13.x/Illuminate/Container/Container.html`,
`https://github.com/laravel/octane`.
