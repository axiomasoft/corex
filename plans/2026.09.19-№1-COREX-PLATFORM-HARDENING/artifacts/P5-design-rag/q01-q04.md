## P5-Q1 — Механика relay транзакционного outbox на PostgreSQL

**Запрос (попытка 2, успешная):** `Answer in prose, no tables. Transactional outbox on
PostgreSQL: should the relay claim rows with SELECT FOR UPDATE SKIP LOCKED in a short
transaction that commits the lease before network publishing, or hold the lock during
publishing? Which outbox columns and partial indexes are needed, how is per-key ordering
affected by SKIP LOCKED, how are backoff, dead-letter and retention handled, and why is
the duplicate window between publish and mark-published unavoidable? Name primary-source URLs.`

**Ответ (захват).**

Короткая транзакция захвата, которая сохраняет lease, коммитит его, и только потом
публикует вне транзакции БД. Не держать `SELECT … FOR UPDATE` во время I/O к брокеру.

`FOR UPDATE SKIP LOCKED` подходит для конкурентных потребителей очереди: PostgreSQL
прямо описывает его как приём для queue-подобных таблиц — заблокированные строки
пропускаются, а не ожидаются. Но блокировки строк, взятые `FOR UPDATE`, действуют
только до конца транзакции. Удержание их через сетевой вызов ставит длительность
транзакции БД в зависимость от задержки брокера, зависаний DNS/TLS, повторов и
отказов; это увеличивает конкуренцию за блокировки, дольше удерживает MVCC-снапшоты
и состояние блокировок строк, усиливает давление на deadlock-детектор и пул
соединений и может блокировать обслуживание или операционное восстановление.

Долговременный lease меняет алгоритм с «я владею, потому что держу блокировку» на
«я владею до записанного срока». Воркер атомарно захватывает ограниченный батч,
немедленно коммитит, публикует свои арендованные строки, затем отдельной короткой
транзакцией записывает успех или состояние повтора. Если воркер умер, другой воркер
может перезахватить строки с истёкшим lease.

Это даёт масштабируемую доставку at-least-once. Это не даёт и само по себе не может
дать сквозной exactly-once между PostgreSQL и независимым брокером. Исходное описание
паттерна transactional outbox делает то же замечание: relay может опубликовать
сообщение и упасть до того, как запишет этот факт, что приводит к повторной публикации.

### Рекомендованный поток захвата

Таблица `outbox_events` со `status = 'pending' | 'publishing' | 'published' | 'dead'`.
Полезный приём PostgreSQL — одна короткая транзакция с CTE:

```sql
WITH candidates AS (
  SELECT id FROM outbox_events
  WHERE (status = 'pending'    AND available_at     <= clock_timestamp())
     OR (status = 'publishing' AND lease_expires_at <= clock_timestamp())
  ORDER BY available_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT $1
)
UPDATE outbox_events AS o
SET status = 'publishing', lease_owner = $2,
    lease_expires_at = clock_timestamp() + $3::interval,
    attempt_count = o.attempt_count + 1, last_attempt_at = clock_timestamp(),
    updated_at = clock_timestamp()
FROM candidates WHERE o.id = candidates.id
RETURNING o.*;
```

Далее:

- Сгенерировать уникальный идентификатор экземпляра relay (например, UUID на старте процесса).
- Выполнить запрос захвата в транзакции и немедленно закоммитить.
- Опубликовать каждое возвращённое событие, передавая неизменяемый id строки outbox как
  message ID / deduplication ID брокера.
- По подтверждению брокера отметить именно свою арендованную строку:

```sql
UPDATE outbox_events
SET status = 'published', published_at = clock_timestamp(),
    lease_owner = NULL, lease_expires_at = NULL, last_error = NULL,
    updated_at = clock_timestamp()
WHERE id = $1 AND status = 'publishing' AND lease_owner = $2;
```

- При известной временной ошибке вернуть ту же арендованную строку в `pending`, снять
  lease, сохранить ошибку и выставить `available_at` по расписанию повторов.
- Если процесс потерял lease во время очень долгой публикации — **не** делать вывод, что
  публикация провалилась. Завершать такую строку небезопасно, пока владение не совпадает:
  её могли перезахватить и повторить. Это ещё одна причина, по которой потребитель обязан
  дедуплицировать по неизменяемому event ID.

Предикат `lease_owner` не даёт старому воркеру, восстановившемуся с опозданием, затереть
результат нового владельца. Для брокеров с потенциально долгим подтверждением выбирают
lease длиннее максимальной ожидаемой задержки публикации плюс jitter, либо продлевают
lease под тем же предикатом `id, status, lease_owner`.

### Схема и колонки

Практичный реляционный outbox несёт неизменяемую идентичность события, поля маршрутизации
и порядка, состояние публикации и операционную историю:

```sql
CREATE TABLE outbox_events (
  id uuid PRIMARY KEY, topic text NOT NULL, event_type text NOT NULL,
  event_version integer NOT NULL DEFAULT 1,
  aggregate_type text NOT NULL, aggregate_id text NOT NULL,
  ordering_key text NOT NULL, sequence_no bigint NOT NULL,
  payload jsonb NOT NULL, headers jsonb NOT NULL DEFAULT '{}'::jsonb,
  created_at timestamptz NOT NULL DEFAULT clock_timestamp(),
  status text NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending','publishing','published','dead')),
  available_at timestamptz NOT NULL DEFAULT clock_timestamp(),
  lease_owner uuid, lease_expires_at timestamptz,
  attempt_count integer NOT NULL DEFAULT 0, last_attempt_at timestamptz, last_error text,
  published_at timestamptz, dead_at timestamptz,
  updated_at timestamptz NOT NULL DEFAULT clock_timestamp(),
  UNIQUE (ordering_key, sequence_no)
);
```

Назначение групп полей:

- `id` — неизменяемый глобально уникальный ID события. Передаётся брокеру и потребителям.
  Это основной ключ дедупликации.
- `topic`, `event_type`, `event_version` — назначение у брокера и стабильная эволюция
  контракта события.
- `aggregate_type`, `aggregate_id` — трассируемость и естественное бизнес-владение.
- `ordering_key` — фактическая область сериализации. Часто это `aggregate_type || ':' ||
  aggregate_id`, но может быть тенант, аккаунт, заказ, диалог или другой доменный ключ.
- `sequence_no` — монотонная последовательность внутри `ordering_key`, назначаемая в той же
  бизнес-транзакции. Делает контракт порядка явным и независимо проверяемым.
- `payload`, `headers` — неизменяемое тело и метаданные, включая trace/correlation/causation,
  tenant ID, данные схемы/версии.
- `status`, `available_at` — планирование и жизненный цикл.
- `lease_owner`, `lease_expires_at` — долговременное исключительное владение после того, как
  короткая транзакция захвата закончилась.
- `attempt_count`, `last_attempt_at`, `last_error` — политика повторов, наблюдаемость и
  диагностика оператора.
- `published_at`, `dead_at` — отметки финального состояния и границы retention.

Бизнес-изменение и вставка в эту таблицу обязаны происходить в одной транзакции PostgreSQL.
Это и есть инвариант transactional outbox: вместо попытки атомарной записи в БД и брокер —
атомарно сохранить бизнес-состояние и долговременное намерение опубликовать в той одной
системе, которая участвует в транзакции.

Если используется естественная последовательность агрегата, её выдача обязана быть
транзакционной: либо инкремент версии агрегата под блокировкой строки в составе бизнес-
обновления, либо `UNIQUE (ordering_key, sequence_no)` с повтором при конфликте. Не
использовать «часы» как последовательность порядка.

### Частичные индексы

Индекс горячего пути должен покрывать только строки, которые relay может захватить, а не
всю удержанную историю опубликованного. Частичные индексы PostgreSQL индексируют только
строки, удовлетворяющие предикату.

```sql
CREATE INDEX outbox_claim_pending_idx ON outbox_events (available_at, id) WHERE status = 'pending';
CREATE INDEX outbox_reclaim_expired_lease_idx ON outbox_events (lease_expires_at, id) WHERE status = 'publishing';
CREATE INDEX outbox_retention_published_idx ON outbox_events (published_at, id) WHERE status = 'published';
CREATE INDEX outbox_retention_dead_idx ON outbox_events (dead_at, id) WHERE status = 'dead';
```

Если захват использует комбинированный предикат, PostgreSQL может выбрать bitmap-комбинацию
двух горячих индексов. `payload` в обычный ключевой индекс не кладут: он крупный, повышает
write amplification и делает горячий индекс менее кеш-дружелюбным. `INCLUDE` оправдан только
при измеренной выгоде index-only scan; relay обычно всё равно нуждается в полной строке.

Для больших объёмов рассматривают партиционирование по времени: retention тогда — это
отцепление/удаление старых партиций, а не массовые DELETE.

### Порядок и SKIP LOCKED

SKIP LOCKED даёт параллелизм, а не гарантию глобального или по-ключевого порядка. PostgreSQL
прямо предупреждает, что пропуск заблокированных строк даёт несогласованное представление;
именно поэтому приём работает для очереди — но это значит, что воркер может пропустить более
раннее заблокированное событие и взять более позднее.

Для одного ключа порядка возможно: события A-41 и A-42 оба готовы; воркер 1 захватывает
A-41; воркер 2 с SKIP LOCKED пропускает A-41 и захватывает A-42; воркер 2 публикует A-42
первым, либо воркер 1 падает и A-41 ждёт истечения lease.

`ORDER BY ordering_key, sequence_no` этого не чинит: он задаёт порядок кандидатов внутри
одного оператора, но SKIP LOCKED разрешено обходить строки, удерживаемые другой транзакцией.
Удержание блокировки на время публикации тоже не даёт надёжной внешней гарантии порядка: оно
лишь блокирует или обходит конкурентов в БД, пока первый публикатор жив; оно не управляет
подтверждением брокера, повторами, конкурентностью потребителя, партиционированием брокера
и падением после публикации.

Варианты осознанного выбора области порядка:

- порядок не критичен для бизнеса — простой арендованный батч; потребители обязаны терпеть
  и переупорядочивание, и дубли;
- порядок обязателен по агрегату/ключу — разрешать не более одного «в полёте» события на
  `ordering_key`; захватывать только наименьший незавершённый `sequence_no` ключа и
  сериализовать по ключу (keyed dispatcher/shard, advisory transaction lock либо отдельная
  таблица `outbox_key_heads`, обновляемая в короткой транзакции захвата);
- партиционировать сообщения брокера по тому же `ordering_key` и обеспечить сохранение
  порядка в обработке потребителя; порядка одного relay недостаточно;
- класть `sequence_no` в сообщение: потребители могут отвергать устаревшие события,
  буферизовать пропуски или применять только монотонные по версии переходы.

Более простая операционная альтернатива — детерминированный шардинг: хешировать
`ordering_key` в фиксированный шард relay и держать по одному активному воркеру на шард. Это
сохраняет поведение «единственный писатель на ключ» без гонки между воркерами, ценой
балансировки и возможных горячих ключей.

### Повторы, dead letters, retention

Повторы — сохранённое состояние, а не in-memory цикл. Падение relay не должно терять
информацию об отказе и не должно сбрасывать поведение повторов. Для попытки n — ограниченный
экспоненциальный backoff с jitter (например, множитель в диапазоне 0.5–1.5). Сохраняются:
`attempt_count`, `last_attempt_at`, `last_error` (санитизированный и ограниченный по длине),
`available_at` (сейчас плюс вычисленная задержка) и, по желанию, `failure_code` /
`failure_class` — transient, permanent, validation, authorization, serialization,
broker-unavailable и т. п.

Явные постоянные ошибки отличаются от транспортных. Некорректный payload события,
запрещённое назначение или нарушение контракта обычно не следует повторять сто раз. Но
объявлять событие мёртвым только из-за временного таймаута брокера нельзя.

После исчерпания бюджета повторов или заданного возраста строка атомарно переводится в
`dead` с `dead_at`. Два распространённых решения: держать её в той же таблице со
`status = 'dead'` (проще всего, поддерживает осмотр и повтор) либо вставлять снимок в
отдельную `outbox_dead_letters` и помечать/удалять активную строку в той же транзакции
(изолирует горячие индексы relay от истории отказов).

Dead-lettering обязан быть наблюдаемым: алерт на новые dead letters, показ event ID, ключа
порядка, идентичности агрегата, числа попыток, последней ошибки и correlation/trace. Нужен
одобряемый оператором повтор. Для строго упорядоченных по ключу потоков dead letter может
блокировать последующие события этого ключа; молчаливый пропуск нарушает контракт порядка.

Retention наступает только после терминального исхода и после срока, достаточного для
аудита, повтора, отставания потребителя и расследования инцидента. Типовая политика:
хранить опубликованные записи в течение объявленного горизонта сверки; хранить мёртвые
дольше или архивировать; удалять/архивировать малыми батчами или, лучше, истечением
партиций; **никогда** не удалять только на том основании, что брокер подтвердил публикацию —
диагностика и повтор на стороне потребителя могут ещё потребовать исходного события.

Потребитель обязан вести inbox/дедупликацию по `event_id` — обычно уникальное ограничение
вида `(consumer_name, event_id)` — в той же локальной транзакции, что и бизнес-эффект.
Руководство AWS по transactional outbox тоже рекомендует идемпотентных потребителей,
отслеживающих обработанные сообщения, потому что дублирующая доставка возможна.

### Почему дубли неустранимы

У relay две независимо долговременные системы: PostgreSQL, где он сохраняет
`published_at` / `status = 'published'`, и брокер, где сообщение становится видимым или
подтверждается. Ни одна обычная локальная транзакция PostgreSQL не может атомарно
зафиксировать оба исхода. Неустранимый неоднозначный интервал:

```text
relay публикует E ── брокер принял E ── relay падает ── отметки в БД нет
```

После перезапуска PostgreSQL по-прежнему считает E неопубликованным. Повтор — единственный
безопасный выбор, если доставка ценна, но он может продублировать E.

Обратный порядок хуже:

```text
relay помечает E опубликованным ── PostgreSQL коммитит ── relay падает ── публикации не было
```

Теперь E потеряно навсегда, если только отдельный процесс сверки его не обнаружит — а тому
нужна долговременная внешняя наблюдаемость и у него та же проблема распределённого коммита.

Удержание блокировки строки во время публикации этого окна не устраняет: падение завершает
транзакцию и снимает блокировку; PostgreSQL откатывает неподтверждённую отметку, тогда как
брокер мог событие уже принять. Документация PostgreSQL по блокировкам строк указывает, что
`FOR UPDATE` предотвращает конфликтующий доступ только до конца текущей транзакции.

Дубли можно уменьшить идемпотентными продюсерами или окнами дедупликации брокера, но
полагаться на них как на универсальную границу корректности нельзя: повтор может случиться
после горизонта дедупликации брокера, в другой сессии продюсера или после неопределённого
подтверждения. Долговременный прикладной ответ — неизменяемый `event_id`, проброшенный
сквозь всю цепочку, плюс идемпотентная обработка у потребителя.

**Первичные источники:** microservices.io (Transactional Outbox) · PostgreSQL
`sql-select` (locking clauses), `explicit-locking`, `indexes-partial`, `sql-createindex`,
`indexes-ordering`, `indexes-multicolumn` · AWS Prescriptive Guidance (Transactional outbox).

## P5-Q2 — Inbox идемпотентного потребителя

**Запрос:** `Answer in prose, no tables. Idempotent consumer inbox table: why must the
INSERT ... ON CONFLICT DO NOTHING deduplication row and the business effect be committed in
one transaction, and what breaks if they are split? Is a preceding SELECT check instead of a
unique constraint a race? What is the correct primary key (consumer name plus message id),
how is inbox retention bounded without reopening the duplicate window, and how should a
consumer behave when it sees a duplicate — acknowledge without re-applying? Name
primary-source URLs.`

**Ответ (захват).**

Отметка inbox и бизнес-обновление потребителя обязаны быть частью одной локальной транзакции
БД, чтобы иметь один исход: либо оба стали долговременными, либо ни одно. Таблица inbox — не
кеш «виденных» сообщений, а долговременное доказательство того, что соответствующий бизнес-
эффект закоммичен.

### Атомарность отметки и эффекта

Для сообщения с идентичностью `(consumer_name, message_id)` потребитель должен: начать
транзакцию; попытаться вставить свою заявку в inbox; если строка вставлена — применить все
локальные изменения бизнес-состояния в той же транзакции; закоммитить один раз; и только
после коммита подтвердить/удалить сообщение у брокера.

Для PostgreSQL арбитром конкуренции служит уникальное ограничение или первичный ключ, а
результат определяется тем, вернул ли `INSERT … RETURNING` строку:

```sql
CREATE TABLE consumer_inbox (
  consumer_name text NOT NULL, message_id uuid NOT NULL,
  processed_at timestamptz NOT NULL DEFAULT clock_timestamp(),
  PRIMARY KEY (consumer_name, message_id)
);
```

```sql
BEGIN;
WITH claimed AS (
  INSERT INTO consumer_inbox (consumer_name, message_id) VALUES (:consumer_name, :message_id)
  ON CONFLICT (consumer_name, message_id) DO NOTHING
  RETURNING 1
)
SELECT EXISTS (SELECT 1 FROM claimed) AS claimed;
-- если claimed = true: локальные доменные записи здесь же
COMMIT;
```

Составной первичный ключ важен: одно опубликованное сообщение обычно должно независимо
потребляться несколькими логическими потребителями. `billing-projection` и `email-notifier`
не должны подавлять друг друга только потому, что увидели один `message_id`. Это ровно ключ
«subscriber ID + message ID» из паттерна Idempotent Consumer.

### Что ломается при разделении

**Отметка закоммичена первой, эффект — позже.** Потребитель вставляет и коммитит строку
inbox, применяет бизнес-обновление во второй транзакции и падает между ними. При повторной
доставке он находит строку inbox, решает, что сообщение уже обработано, и подтверждает дубль.
Бизнес-эффект не был закоммичен никогда: платёж не проведён, проекция не продвинулась, счёт
не обновлён. Это **потерянный эффект**, и доставка at-least-once его не чинит — собственная
запись дедупликации теперь отбрасывает каждый повтор.

**Эффект закоммичен первым, отметка — позже.** Повтор не видит отметки и применяет эффект
снова: двойное списание, дублирующая проводка, счётчик, увеличенный дважды, дублирующее
исходящее событие. Это **дублирующий эффект**.

Единственная транзакция устраняет оба разрыва: до коммита ни отметка, ни изменение не
долговременны, и повтор может безопасно захватить и выполнить; после коммита долговечны оба,
и повтор видит конфликт ключа и безопасно ничего не делает; при неопределённом исходе коммита
из-за потери соединения повтор всё равно безопасен, потому что первичный ключ решает, успела
ли закоммиченная транзакция заявить сообщение.

Подтверждение брокеру неизбежно остаётся вне этой транзакции БД, если только брокер и БД не
участвуют в настоящей распределённой транзакции. Поэтому падение после коммита БД, но до
подтверждения, вызывает нормальную повторную доставку — и закоммиченная строка inbox
превращает её в безвредный no-op.

### Почему `SELECT` первым — гонка

Да. Предварительный `SELECT` — хрестоматийная гонка time-of-check/time-of-use, если только
уникальность, обеспеченная БД, всё равно не арбитрирует финальную вставку. Два воркера,
получившие одно сообщение при уровне Read Committed по умолчанию:

```text
Воркер A: SELECT … → строки нет
Воркер B: SELECT … → строки нет
Воркер A: применяет эффект
Воркер B: применяет эффект
```

Оба чтения законно не видят закоммиченной строки, потому что обычный `SELECT` видит только
строки, закоммиченные до начала этого оператора. PostgreSQL документирует, что Read Committed
— уровень по умолчанию и что каждый `SELECT` получает снапшот на момент начала оператора.

Даже если оба затем попытаются вставить отметку: без уникального ограничения вставятся обе
отметки и закоммитятся оба эффекта; с ограничением, но **после** эффекта, проигравшая вставка
сообщит о проблеме уже после того, как дубль применён; с ограничением и вставкой-заявкой
**до** эффекта в той же транзакции применить эффект разрешено только той транзакции, что
получила долговременную заявку.

`SELECT … FOR UPDATE` сам по себе задачу «строки нет» не решает: блокировать нечего.
Serializable-изоляция способна обнаружить часть аномалий, но требует дисциплины повторов и не
заменяет объявления самого инварианта. `ON CONFLICT` специально построен на уникальном
индексе или ограничении как арбитре; `DO NOTHING` подавляет конфликтующую вставку.

Чтение остаётся полезным для диагностики или получения сохранённых метаданных обработки, но
оно не должно быть решением о применении эффекта.

### Корректное поведение при дубле

При конфликте вставки потребитель должен считать сообщение уже успешно закоммиченным этим
логическим потребителем и подтвердить его, не применяя локальную бизнес-логику снова:

```text
получено сообщение → begin → попытка вставки в inbox
  → вставлено: применить локальные изменения, commit, подтвердить брокеру
  → конфликт: rollback / no-op commit, подтвердить брокеру
```

Не перезапускать доменный обработчик при конфликте. Не переиздавать побочные эффекты только
из-за повторной доставки. И не подтверждать брокеру до коммита локальной транзакции: падение
после раннего подтверждения может потерять единственную доставку.

Оговорка: «подтвердить при дубле» предполагает, что ключ inbox означает «эффект закоммичен» —
именно поэтому атомарная транзакция не подлежит обсуждению. Если реализация старая и
разделённая, конфликт недостоверен, и нужна сверка, а не слепое подтверждение.

Дубль следует отличать от неуспешной попытки: постоянная ошибка валидации требует явного
решения (dead-letter, статус «отклонено», операционный процесс); временный отказ до коммита —
rollback, снимающий заявку и позволяющий повтор; удалённый побочный эффект (HTTP, письмо,
платёж) локальной транзакцией не откатывается — в ту же транзакцию кладут локальную outbox-
команду/событие, а отправитель и получатель тоже делаются идемпотентными. Inbox даёт
атомарность только для состояния, управляемого той же транзакцией БД.

### Retention без повторного открытия окна дублей

Retention inbox — горизонт корректности, а не просто уборка. Удаление строки inbox означает,
что более поздняя повторная доставка того же сообщения перестанет распознаваться как дубль.

Поэтому отметку хранят не меньше максимального времени, в течение которого именно этот
`message_id` может появиться снова, включая: retention брокера и периоды redrive/DLQ-повтора;
окна повторов и visibility timeout; длительность повтора/replay у продюсера и его outbox;
ручной replay/backfill и процедуры восстановления после аварии; дрейф часов и запас
безопасности.

Если правдоподобной конечной верхней границы повтора назвать нельзя — удалять по TTL
единственное свидетельство дедупликации нельзя: такая уборка осознанно заново открывает окно
дублей.

Практически безопасные варианты: хранить строки inbox неограниченно, если объём и экономика
позволяют (партиционировать по `processed_at` ради обслуживания, но сохранять партиции);
использовать конечный «контракт повтора», задокументированный для продюсеров, операций
брокера, политики DLQ и человеческих runbook'ов, и хранить сверх этого горизонта с
консервативным запасом; опереться на доменный инвариант идемпотентности, который остаётся
навсегда (проводка с уникальным `external_event_id`, переход заказа по неизменяемой версии),
и тогда inbox — операционная оптимизация, а не единственный барьер. Идентичности сообщений
обязаны быть безопасно неймспейснуты: `message_id` глобально уникален в своём домене повтора,
иначе ключ обязан включать дополнительную область (`producer_id` / поток событий).

Опасная короткая дорога — TTL семь дней при том, что сообщения хранятся, повторяются или
восстанавливаются дольше. На восьмой день старое сообщение снова становится «новым» и может
применить эффект повторно.

**Первичные источники:** postgresql.org `sql-insert` (ON CONFLICT), `transaction-iso`
(Read Committed) · docs.aws.amazon.com SQS standard queues at-least-once ·
microservices.io Idempotent Consumer (ключ `(subscriberId, messageID)`).

## P5-Q3 — Конверт сообщения: CloudEvents 1.0 и версионирование контракта

**Запрос:** `Answer in prose, no tables. Message envelope design: what does the CloudEvents
1.0 specification require as core context attributes (id, source, specversion, type, plus
optional time, subject, dataschema), why must the event type be a stable contract name rather
than a serialized class name, and how do correlation id and causation id differ and get
propagated? How is event schema version carried — in the type name, a separate version
attribute, or a dataschema URI — and what are the accepted compatibility rules for evolving
an event contract? Name primary-source URLs.`

**Ответ (захват).**

CloudEvents 1.0 стандартизует транспортно-нейтральный конверт события, а не схему доменного
payload'а и не семантику процесса. Он требует четырёх контекстных атрибутов — `id`, `source`,
`specversion`, `type` — и допускает `time`, `subject`, `dataschema`. Correlation и causation —
метаданные приложения, обычно переносимые как extension-атрибуты CloudEvents по
задокументированному соглашению организации.

### Обязательные атрибуты

- `id` — непустая строка, идентифицирующая экземпляр события. Пара `source` + `id` обязана
  уникально идентифицировать каждое отдельное событие. Повторная доставка того же события
  может сохранять ту же пару, что даёт потребителям надёжное основание для inbox/дедупликации.
  Не перегружать его идентификатором агрегата, процесса или корреляции.
- `source` — непустая URI-reference, идентифицирующая контекст, в котором произошло событие.
  Определяется продюсером; рекомендуется абсолютный URI. Достижимым HTTP-адресом быть не обязан.
- `specversion` — версия спецификации **конверта** CloudEvents, а не версия схемы события.
  Для CloudEvents 1.0 значение — `1.0`; патч-релизы это значение не меняют.
- `type` — непустая строка, описывающая род бизнес-события. Предназначена для подписки и
  маршрутизации, наблюдаемости, применения политик и диспетчеризации у потребителя.
  Спецификация рекомендует reverse-DNS-префикс, закрепляющий владение семантикой, например
  `com.acme.billing.invoice.issued.v1`.

Запрошенные необязательные атрибуты:

- `time` — метка RFC 3339 момента наступления. Если фактический момент недоступен, продюсер
  может использовать другое время, но все продюсеры одного `source` обязаны применять единое
  правило.
- `subject` — идентификатор объекта или подресурса в области `source`, полезен для фильтрации
  на стороне брокера без десериализации `data`. Глобально уникальным не является и трактуется
  только в контексте `source`.
- `dataschema` — абсолютный URI схемы, которой соответствует `data`. CloudEvents указывает,
  что несовместимые изменения схемы должны получать другой URI.

В эксплуатационных конвертах также задают `datacontenttype` (обычно `application/json`).

### `type` — контракт, а не имя класса

Имя класса вида `App\Domain\Billing\Events\InvoiceIssued` описывает артефакт реализации. Оно
меняется при реорганизации неймспейсов, разделении монолита на модули или сервисы,
переименовании классов, смене языка, замене сериализатора, введении генерации кода или
переносе пакета контрактов. Ни одно из этих изменений не обязано менять бизнес-факт, на
который опираются потребители. Публикация имени класса поэтому превращает внутренний рефакторинг
во внешне наблюдаемое ломающее изменение.

Контрактное имя говорит, что произошло в домене и кто владеет смыслом:

```text
com.example.billing.invoice.issued.v1
com.example.crm.lead.converted.v1
```

Такое именование делает событие переносимым между воркерами очередей, потребителями на других
языках, аналитическими конвейерами, webhook'ами и будущими границами сервисов. Оно также
работает для фильтрации у брокера и правил авторизации, не привязывая инфраструктуру к системе
типов продюсера.

Полезное правило: `type` отвечает «какого рода это бизнес-факт»; `id` — «какое именно
опубликованное событие»; `subject` — «о какой сущности в области продюсера»; `data` — «что
именно произошло, с какими деталями».

### Correlation и causation

Ни `correlationid`, ни `causationid` не являются обязательными или необязательными
**ядровыми** атрибутами CloudEvents 1.0. CloudEvents допускает extension-атрибуты, которые
обязаны соблюдать общие правила именования и типов; базовая спецификация намеренно оставляет
их смысл расширению или контракту приложения.

Два идентификатора выражают разные отношения графа:

- **Correlation ID** идентифицирует более широкое бизнес-взаимодействие, сагу, процесс или
  трассируемую единицу работы. Один correlation ID могут разделять многие события, включая
  параллельные ветви. Отвечает на вопрос «к какому сквозному бизнес-потоку это относится».
- **Causation ID** идентифицирует непосредственное предшествующее событие, прямо вызвавшее
  новое. Обычно указывает на идентичность предыдущего события — в идеале на пару
  `(source, id)`, а не только `id`, потому что CloudEvents гарантирует уникальность лишь для
  пары. Отвечает на вопрос «какое событие непосредственно привело к этому».

`[листинг сокращён: пример саги OrderPlaced → PaymentAuthorized / InventoryReserved →
OrderConfirmed с общим correlationid и разными causationid]`

**Правило проброса.** Когда потребитель обрабатывает входящее событие и выпускает новое
семантическое событие: сгенерировать свежий `id`; задать собственный `source`; скопировать
входящий `correlationid` без изменений (или сгенерировать новый, если начинается новый
процесс); задать `causationid` равным идентичности непосредственного входного события;
по желанию отдельно сохранить контекст распределённой трассировки (W3C Trace Context /
CloudEvents distributed tracing extension), поскольку трассировка, причинность и бизнес-
корреляция — связанные, но не тождественные вещи.

При простой пересылке события новое логическое событие не создаётся: конверт сохраняется
целиком, включая `id`, `source`, correlation и causation. Если событие семантически
преобразуется в новый факт — это новое событие с новыми `source`/`id` и записанной причинностью.

### Версионирование схемы

Единого обязательного поля «версия схемы события» в CloudEvents нет. `specversion` — только
версия конверта. Политика версионирования payload'а намеренно оставлена продюсеру; релевантны
`type` и `dataschema` с разными ролями.

Устойчивый подход: делать `type` границей совместимости — сохранять его неизменным при
обратно совместимой эволюции и менять при ломающей; использовать `dataschema` как
информационный указатель на точную схему конкретного сообщения; избегать отдельного атрибута
`schemaVersion`, если нет конкретной операционной причины. Если отдельный атрибут версии всё
же вводится, это частное расширение, а не стандартные метаданные CloudEvents, и оно не должно
противоречить `type` и `dataschema`.

Вкладывать мажорную версию контракта в `type` (например, `…invoice.issued.v1`)
распространено и понятно: это делает маршрутизацию по ломающим версиям явной. CloudEvents
прямо разрешает продюсеру включать версию или дату в `type` либо не включать; это политика
продюсера, а не требование стандарта.

URI `dataschema` могут называть точные неизменяемые схемы (`…/invoice-issued/1.0.0.json`,
`…/1.1.0.json`, `…/2.0.0.json`). Это хорошо для валидации, генерации кода, инструментов
повтора, аудита и контрактных тестов потребителя, и позволяет одному логическому `type`
оставаться стабильным сквозь совместимые ревизии payload'а.

### Правила совместимости

CloudEvents не определяет универсальных правил совместимости уровня JSON/Avro/Protobuf.
Управляющее указание тем не менее ясно: потребители данного `type` должны ожидать только
обратно совместимых изменений, если изменение явно не сигнализировано; совместимые изменения
обычно сохраняют `type`, несовместимые — обычно его меняют. Продюсерам рекомендуется
публиковать и старые, и новые события на время миграции.

Для JSON-данных прагматичная политика обратной совместимости для потребителя:

- **Совместимо:** добавить новое необязательное поле; добавить необязательный вложенный
  объект; добавить значение перечисления, только если потребители явно спроектированы
  терпеть неизвестные значения; ослабить ограничение валидации без изменения смысла;
  опубликовать ревизию схемы, принимающую все старые сообщения.
- **Ломающе:** удалить или переименовать поле; изменить тип поля; сделать необязательное
  поле обязательным; изменить единицы, семантику валюты, трактовку часового пояса, точность,
  семантику nullability, владение или смысл существующего поля; изменить перечисление так,
  что старые потребители его отвергают; переиспользовать поле под другой смысл при том же имени.
- **Потенциально ломающе на практике:** добавление поля, когда потребители используют строгое
  декодирование JSON, `additionalProperties: false`, исчерпывающий pattern matching или
  проекции БД, отвергающие неизвестные ключи. «Аддитивно» совместимо только если фактический
  контракт потребителя это терпит.

Для ломающего изменения вводится новый `type` (`…issued.v1` → `…issued.v2`), оба публикуются
в течение окна вывода из эксплуатации, потребители мигрируются осознанно, а для повтора и
долгоживущих подписчиков сохраняется апкастер или двойная публикация. Критическое различие:
`dataschema` преимущественно информационен и не должен использоваться, чтобы спрятать
ломающее изменение за неизменившимся `type`.

`v1.0.2/cloudevents/primer.md` · github.com/cloudevents/spec · asyncapi.com specification v3.0.0.

## P5-Q4 — Доменное событие против интеграционного; реестр публикации; форма payload'а

**Запрос (попытка 2, успешная):** `Answer in prose, no tables. Domain event versus
integration event versus command in a modular monolith: why is an internal domain event a poor
published contract, what is the Published Language argument for explicitly translating it into
an integration event, and why should that promotion be a declared registry entry rather than
automatic? What should an integration event payload carry — full state, thin identifier, or
delta? Name primary-source URLs.`

**Ответ (захват).**

Команда просит конкретную модель попытаться выполнить работу; доменное событие фиксирует
бизнес-факт для участников внутри того же ограниченного контекста/модуля; интеграционное
событие — сознательно спроектированный, долговременный и версионированный факт, публикуемый
через границу модуля. В модульном монолите граница логическая, а не сетевая, — но обращаться
с ней следует как с настоящей, если модули должны оставаться независимо эволюционируемыми или
в перспективе извлекаемыми. Руководство Microsoft по DDD делает то же различение: доменные
события — внутрипроцессные уведомления внутри домена, интеграционные распространяют
закоммиченные изменения в другие ограниченные контексты или внешние приложения.

### Три рода сообщений

Команда имеет повелительную семантику («зарезервировать места для брони B-482»): выражает
намерение, адресована владельцу/обработчику и может быть отвергнута. Обычно маршрутизируется
одному ответственному прикладному сервису или границе агрегата.

Доменное событие имеет фактическую семантику прошедшего времени в локальной модели
(`BookingConfirmed`, `StudentEnrolled`, `InvoiceMarkedOverdue`). Оно означает, что доменная
модель решила: этот факт произошёл.

Интеграционное событие — тоже факт в прошедшем времени, но выраженный в публичном контракте
обмена (`education.enrollment.confirmed.v1`). Оно сообщает другим модулям только то, на что
они вправе опираться, в терминах, понятных без импорта внутренностей публикатора. Публиковать
его можно только после фиксации исходной транзакции; иначе потребители могут отреагировать на
факт, который был откатан.

Связь не «другой транспорт для того же класса», а намеренный перевод, иногда агрегация: одно
внутреннее изменение может дать ноль, одно или синтезированное из нескольких доменных событий
публичное событие. Microsoft прямо отмечает, что преобразование доменного события в
интеграционное — или агрегация нескольких — допустимая операция границы.

### Почему доменное событие — плохой опубликованный контракт

Во-первых, оно раскрывает внутренние понятия и детали жизненного цикла. Модуль может
отрефакторить одно бизнес-действие из `EnrollmentApproved` в `EnrollmentPaymentCaptured` плюс
`SeatAllocated`, сменить агрегат, процесс, конечный автомат, порядок валидации или соглашение
об именовании. Это валидные локальные рефакторинги. Если потребители подписаны прямо на эти
объекты, ваш приватный рефакторинг становится инцидентом совместимости.

Во-вторых, payload доменных событий часто содержит графы объектов, value objects, ORM-
ориентированные формы, локальные ID и поля со случайным, а не контрактным смыслом. Пример на
PHP/Laravel — сериализация модели Eloquent или богатого доменного объекта в сообщение очереди.
Вы случайно публикуете поля, приведения, связи, правила тенантности и локальный словарь,
которые нижестоящий код начинает считать стабильными.

В-третьих, различается временнáя семантика. Локальное доменное событие может подниматься
внутри транзакции, чтобы другая локальная логика участвовала в той же границе согласованности.
Интеграционное событие обязано описывать закоммиченный исход и доставляться надёжно, обычно
через outbox.

В-четвёртых, один доменный факт не обязательно релевантен снаружи: внутреннее
`EnrollmentStatusChanged` может срабатывать на каждый переход, тогда как биллингу нужно лишь
«появилась оплаченная запись». Публикация каждого локального перехода создаёт связность,
лишний трафик, раскрытие приватных данных и зависимость потребителей от топологии процесса
продюсера.

Наконец, интеграционному контракту нужны операционные метаданные, которых у локального
доменного события часто нет: стабильное имя события, версия схемы, message ID, момент
наступления, correlation/causation, ключ тенанта или партиции и явные ожидания по
доставке/повтору/идемпотентности.

### Published Language: перевод на границе

Паттерн DDD Published Language утверждает, что ограниченные контексты должны общаться через
хорошо документированный общий язык обмена, а не через приватную внутреннюю модель любой из
сторон. Переводят обе стороны. Это не лишняя церемония DTO, а антикоррупционная граница в обе
стороны.

`[листинг сокращён: пример внутреннего EnrollmentStateTransitioned с value objects против
опубликованного education.enrollment.confirmed.v1 из шести скалярных полей]`

Получателю не нужно знать, что подтверждение внутренне стало результатом пятишагового
конечного автомата, удержания кредита и конкретной конструкции агрегата. Он получает
стабильный бизнес-факт, который согласился потреблять.

Published Language особенно ценен в модульном монолите: он сохраняет автономию модулей до
разделения процессов. Реализация может сегодня быть внутрипамятным диспетчером и общей
PostgreSQL, но семантический контракт всё равно должен быть явным. Если позже внутрипроцессный
подписчик заменяется на outbox плюс брокер, контракт и его потребители не требуют
концептуальной переделки.

Следствие: интеграционные события именуются по внешне осмысленным бизнес-фактам, а не по
механике персистентности. `EnrollmentConfirmed` или `InvoiceOverdue`, а не
`EnrollmentRowUpdated`, `EnrollmentStatusColumnChanged` или `EnrollmentAggregateSaved`.

### Почему повышение обязано быть объявленным

Не превращать каждое доменное событие в интеграционное автоматически. Автоматическое
повышение делает «внутреннее событие» молчаливым синонимом «публичного API» и уничтожает то
самое различение, которое вам нужно.

Объявленный реестр повышений делает публикацию видимым архитектурным решением.

`[листинг сокращён: две формы реестра — карта класс→публикатор и именованная запись
EventPromotion(source, mapper, audience, schemaVersion)]`

Точная форма кода менее важна, чем свойства, которые она обеспечивает:

- **Намеренное раскрытие.** Кто-то обязан подтвердить, что факт публичен для другого модуля,
  назвать аудиторию и выбрать имя контракта.
- **Обозримость.** Архитектурное ревью отвечает на вопрос «какие факты модуля публикуются» без
  археологии через grep.
- **Избирательное раскрытие.** Маппер может опустить внутреннее состояние, чувствительные
  персональные данные, атрибуты безопасности, промежуточные вычисления и ID реализации.
- **Семантическое преобразование.** Отображение может переименовать факт, свернуть несколько
  локальных событий, обогатить из закоммиченного состояния или не выпустить ничего.
- **Версионирование и вывод из эксплуатации.** Реестр может держать `v1` и `v2` одновременно,
  знать подписчиков и определять путь ухода.
- **Операционная политика.** Запись — естественное место для темы/потока outbox, ключа
  партиции, владения, ожиданий retention/replay и гарантий доставки.
- **Тестируемость.** Каждое зарегистрированное событие можно покрыть контрактным тестом и
  утверждать, что незарегистрированные доменные события границу модуля не пересекают.

Реестр кладут в прикладной/интеграционный слой, не в агрегат и не в механизм автообнаружения
слушателей. Агрегат поднимает внутренние доменные события; проектор/публикатор прикладного
уровня отображает явно зарегистрированные в записи outbox в той же транзакции БД; диспетчер
доставляет эти записи после коммита.

### Payload: состояние, идентификатор или дельта?

Универсально правильной формы нет. По умолчанию — целевой самодостаточный бизнес-факт с
минимумом стабильных полей, нужных потребителям. Это не «прислать весь агрегат» и не
«прислать только непрозрачный ID» рефлекторно.

**Снимок состояния** несёт ориентированное на потребителя представление состояния,
релевантного событию. Применяется, когда нижестоящие обязаны самостоятельно строить read-
модель, реагировать без синхронного обратного вызова, переживать простой продюсера или
повторять события для восстановления проекции. Это обычно сильнейший вариант для автономии
между модулями. Но «полное состояние» должно означать полное **контрактное** состояние,
нужное потребителям, а не сериализованный агрегат или строку БД.

**Тонкий идентификатор** несёт идентичность и почти ничего больше. Применим, только когда
потребитель обязан намеренно обратиться к каноническому источнику через стабильный API, его
операция всё равно некорректна без актуальных авторитетных данных, и дополнительная синхронная
зависимость приемлема. Его преимущества — малый размер, меньше дублирования, меньше раскрытия
приватных данных. Но он создаёт рантайм-связность: «потребитель» не может обработать факт, если
API продюсера недоступен, изменён, медленен, не авторизован или ограничен по скорости. Он также
усложняет повтор: воспроизведение старого события с выборкой текущего состояния больше не
говорит, что было истинным в момент события. Событие «только ID» часто — замаскированная
команда «сходи возьми моё текущее состояние», а не полезная запись истории. В модульном
монолите оно вдобавок соблазняет модули читать чужую БД напрямую, что полностью обходит границу.

**Дельта** говорит ровно, что изменилось. Применима, когда семантика действительно такова,
сам факт изменения и есть бизнес-факт, объём или чувствительность данных делают снимки
неуместными, и потребители ведут состояние по порядку. Дельты труднее потреблять надёжно:
нужны корректная база, стратегия порядка/версии, обработка дублей и механизм восстановления.
Пропущенная дельта может испортить проекцию.

**Практический дефолт для долгоживущего модульного монолита:** держать доменные события
внутренними; публиковать только объявленные и отображённые интеграционные события из outbox
после коммита; использовать Published Language; предпочитать ориентированный на потребителя
снимок релевантного состояния для обычной межмодульной интеграции; тонкие ID — только там, где
явная и приемлемая зависимость обратного запроса существует; дельты — только там, где дельта
сама осмысленна и у потребителей есть машинерия порядка, идемпотентности и восстановления;
включать в конверт как минимум неизменяемый message ID, стабильный `type` плюс версию, момент
наступления, продюсера/модуль, бизнес-идентичность, ключ тенанта/партиции при необходимости,
correlation/causation при трассировке процессов и политику схемы/версии; предполагать
доставку at-least-once, пока не доказано иное.

Ключевой проверочный вопрос: может ли публикующий модуль отрефакторить свои агрегаты, таблицы,
ORM-объекты и внутреннюю таксономию событий, не заставляя этого потребителя измениться? Если
да — у вас, вероятно, интеграционное событие. Если нет — вы, вероятно, случайно опубликовали
доменное.
