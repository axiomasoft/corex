# P6-Q4 — fitness function направления зависимостей

**Query:** Answer in prose, no tables. Architectural fitness functions for
internal dependency direction inside one PHP package: how should an
allowed-dependency matrix be enforced, and why must a gate include a planted
negative test that names the offending file? Contrast Pest Arch, Deptrac, PHPat,
and a stdlib source scan of use statements. Cite ThoughtWorks evolutionary
architecture fitness functions, PHPUnit/Pest arch docs. Name primary-source
URLs.

**Status:** success

Treat direction as an executable contract: a named-area allow-list matrix, run
in CI, deny-by-default. ThoughtWorks: a fitness function is an objective
integrity check of an architectural characteristic.

A green tool run is not proof the gate works. Config can match no files, use
the wrong regex, or become permissive. A planted illegal fixture must fail
nonzero and name the planted filename (and preferably the forbidden FQCN).
That tests the enforcement mechanism, not production code.

Pest Arch is terse for simple `not->toUse` rules; in this monorepo it was
already rejected as vacuous on path packages (LayerTest). Deptrac/PHPat express
the matrix well but add a dependency. A `token_get_all` / `use`-scan is
dependency-free and has excellent diagnostics; it does not see FQCN without
`use`. Label it honestly as an import scan, or extend it (as P3.2 already does
for the package graph).

# P6-Q5 — shared kernel vs capability

**Query:** Answer in prose, no tables. DDD shared kernel versus capability
modules: which of money (currency VO plus Eloquent cast), feature flags,
append-only audit log, hierarchical settings, and organisational departments
typically belong in a platform foundation versus a bounded capability? What
litmus questions decide foundation membership? Cite Evans DDD shared kernel,
Microsoft .NET architecture modular monolith, Drupal core versus modules. Name
primary-source URLs.

**Status:** success

A Shared Kernel is an explicitly agreed subset of the model, not “common code”.
Evans’s default is restraint.

Money: a small currency primitive may be foundation; financial policy
(rounding, tax, settlement) is capability-owned. An Eloquent money cast is
infrastructure around that primitive, not a reason to pull billing into the
kernel.

Feature flags: evaluation/plumbing is platform; flag names, defaults and
sunsets are capability-owned.

Audit log: append-only envelope, actor, tenant, retention plumbing is
platform; event vocabulary and payload schema are capability-owned. Do not
conflate audit, domain events, and an event-sourced store.

Hierarchical settings: the resolution engine (global → tenant → user) can be
platform; setting keys that carry invariants belong to the capability.

Organisational departments: usually an Organisation capability. Foundation
should keep an opaque id, not the full aggregate. HR cost centres, sales
territories and academic faculties are not the same concept.

Litmus for foundation: same meaning, same invariants, stable for years,
independent of one workflow, ≥2 real consumers, low semantic volatility, clear
governance. If modules only need an id or an event, do not share the model.
