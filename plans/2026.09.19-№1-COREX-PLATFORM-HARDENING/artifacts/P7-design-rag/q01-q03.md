# P7-Q1 — typed Options vs config()

**Query:** Answer in prose, no tables. In a PHP Laravel package, how should typed
configuration objects be built so services remain testable without a container?
Contrast: a factory Options::fromArray(array $config) that never calls config(),
versus reading config() inside the factory or inside domain services. Where may
config() be called (service provider, console command) and why not in middleware
or repositories? How does Symfony OptionsResolver relate to a readonly PHP DTO,
and is OptionsResolver a substitute for the typed object? Cite Laravel package
development docs, Laravel config repository, Symfony OptionsResolver 7 docs.
Name primary-source URLs.

**Status:** success

Build configuration as an immutable, framework-agnostic boundary object: read
Laravel configuration once at the composition root, validate/normalize it,
construct a readonly DTO, and inject that DTO into services. The DTO factory
should accept only explicit data — `Options::fromArray(array $config)` — and
must not call `config()`.

That separation lets the same services run in ordinary PHPUnit tests, workers,
commands, and non-Laravel adapters without booting a Laravel application or
mocking global helpers. Laravel’s package provider is the framework integration
point: providers bind services and register/publish configuration.

`config()` is a Laravel global helper that resolves configuration through the
application/container. If `fromArray` called `config()`, the factory would
require a booted app, hide its dependency, and make a configuration snapshot
timing-dependent. A useful test is `BillingOptions::fromArray([...])` with no
Laravel base test class.

Calling `config()` belongs at a Laravel edge. The service provider is the main
location: merge defaults, publish, obtain the array, create Options, bind
services. Prefer the injected `Illuminate\Contracts\Config\Repository` in the
provider closure. A console command is another acceptable boundary; it should
not push `config()` into the use case. Middleware and repositories are the
wrong place: middleware is per-request infrastructure, a repository is
persistence mapping, and both become hidden service locators if they look up
package-wide configuration.

Symfony OptionsResolver is an input-resolution and validation mechanism, not a
replacement for the typed object. The resolver answers whether a loosely typed
array is complete and valid. The readonly DTO answers what stable named
configuration the rest of the application receives. Returning the resolved
array leaves consumers coupled to string keys.

# P7-Q2 — secret redaction

**Query:** Answer in prose, no tables. How should a PHP object holding a secret
prevent accidental leakage via string interpolation, (string) cast, var_dump,
print_r, exception traces, and logs? Cover __toString, __debugInfo, and PHP 8.2
SensitiveParameter. Why is a reveal() method named explicitly? What does
SensitiveParameter attribute actually hide and not hide? Cite php.net manuals
for __toString, __debugInfo, SensitiveParameter. Name primary-source URLs.

**Status:** success

Treat a secret as a capability-bearing value, not as an ordinary string. Its
default representation should be redacted; obtaining the bytes should require
an explicit `reveal()`.

PHP invokes `__toString()` for echo, `(string)`, concatenation, interpolation
and many `sprintf('%s')` paths. Return a stable `[REDACTED]` placeholder; do
not throw from `__toString()`. `__debugInfo()` supplies the properties shown
by `var_dump()`; without it, private plaintext appears. `json_encode()` does
not use `__debugInfo()`; do not implement `JsonSerializable` to return
plaintext. Consider blocking `serialize()`.

`reveal()` is a review signal: grepping `->reveal()` inventories plaintext
crossings. It is not cryptographic protection.

`#[SensitiveParameter]` redacts a parameter in PHP-generated backtraces via
`SensitiveParameterValue`. It does not prevent ordinary code from reading,
copying, interpolating or logging the actual string, does not redact a
property merely because the constructor parameter was annotated, and does not
hide a value put into an exception message. Put the attribute on the concrete
method that receives the secret. Use both layers: object redaction plus
backtrace redaction plus a logger denylist.

# P7-Q3 — boot fail vs diagnose command

**Query:** Answer in prose, no tables. Should invalid application configuration
fail at process boot or only when a diagnose CLI command runs? Symfony compiled
container and Laravel config:cache: when is a bad value detected? What should a
config validation command print (effective driver, adapter availability,
accumulated violations) and what must it never print (secret values)? Cite
Symfony configuration validation, Laravel artisan config:cache / config:show.
Name primary-source URLs.

**Status:** success

Invalid configuration that makes the process unable to operate safely should
fail during boot or deployment-time warm-up, not only when a diagnostic
command runs. Web workers, queue consumers and schedulers may never run the
command.

Two complementary layers: boot validation for deterministic configuration-only
invariants (unknown driver, invalid enum, missing required non-secret,
structurally incompatible options, selected adapter absent from the installed
codebase); a diagnose command for a complete report of effective configuration,
available adapters and all detected violations. Runtime readiness checks for
environment-dependent reachability. Do not fail every artisan command because
a remote system is temporarily unavailable.

Symfony validates the configuration tree when `ContainerBuilder::compile()`
runs. Laravel `config:cache` materializes files; it is not a semantic-validation
framework. Application-owned checks must run on the boot path of workers.
`config:show` and `about` inspect values; they do not substitute for owned
validation. Avoid `env()` outside `config/*.php`.

The command should print metadata: effective driver identifier (not DSN),
whether the configuration cache is enabled, adapter registered/present,
required extension present or missing, accumulated violations with stable
codes, exit non-zero on errors. It must never print passwords, API keys,
tokens, private keys, complete DSNs, raw environment values, or serialized
config arrays. Safe alternatives: key name plus `configured`/`absent`, optional
non-reversible fingerprint. Redact at the reporting boundary, including
throwables and JSON.
