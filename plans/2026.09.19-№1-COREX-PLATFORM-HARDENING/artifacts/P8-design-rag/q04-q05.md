# P8-Q4 — proving bindings unchanged

**Query:** Answer in prose, no tables. After moving Laravel container bindings
from one ServiceProvider into helper registrars, how can a test prove the
resolved abstract, concrete class, and lifetime (singleton versus scoped
versus transient bind) are unchanged? Mention Application::getBindings,
isShared, forgottenBinding, scoped, and dumping bound abstracts. What is
insufficient (only asserting class exists)? Cite Laravel container source or
docs. Name primary-source URLs.

**Status:** success

A regression test should compare the container contract, not the files that
implement it. For every affected abstract assert: it remains explicitly bound;
it resolves to the same concrete; its lifetime is unchanged.

Laravel exposes registration records through `Application::getBindings()` and
sharing through `isShared()`. Ordinary `bind()` is transient; `singleton()` is
shared across the application; `scoped()` is shared only within the current
request/job lifecycle.

`isShared()` cannot distinguish singleton from scoped: both are shared. The
behavioral probe is `forgetScopedInstances()`: a scoped service yields a new
instance after the call; a singleton does not. Do not assert
`$bindings[$abstract]['concrete']` equals a class-string: Laravel converts
class-string bindings into closures. Prove the resolved object instead:
`assertInstanceOf`, `assertSame` / `assertNotSame`.

`class_exists` is insufficient: the class can exist while the abstract is
unbound, rebound, or has changed lifetime. A single `assertInstanceOf` on
`app($abstract)` is only a partial check: transient and singleton both pass
it.

Dump application-owned abstracts during migration as a diagnostic, then keep
behavior-focused assertions. Do not snapshot the entire framework binding
array: it varies with Laravel version and test bootstrapping.

# P8-Q5 — provider-size fitness function

**Query:** Answer in prose, no tables. Architectural fitness functions that
fail CI when a Laravel ServiceProvider subclass grows past a measured
binding-count threshold. Why must the gate count only classes extending
ServiceProvider, not internal registrar helpers? Why include a planted
negative test that names the offending file? Contrast observational versus
blocking. Cite ThoughtWorks fitness-function-driven development and Pest PHP
arch testing. Name primary-source URLs.

**Status:** success

A ServiceProvider binding-count gate is a fitness function: it detects when
the application-composition boundary is becoming a god provider and fails CI
before that structure becomes entrenched. The threshold should be based on a
measured baseline. The failure must report the exact provider file and
observed count.

Count only subclasses of Illuminate\Support\ServiceProvider. A provider is the
public composition boundary Laravel loads. An internal helper that registers
many related bindings is a narrow implementation technique, not a second
composition root. Penalizing helpers measures syntax, not role: it pressures
developers to scatter a cohesive group, makes extraction look like a
violation, and is easy to game by moving calls into traits or closures.

The invariant is not “no PHP class may contain more than N container calls.”
It is “each Laravel-recognized composition root stays below an agreed budget.”
Count source-level calls in the provider, not the transitive total of helpers
it invokes.

A planted negative test that creates an over-budget provider fixture must
fail and name the offending file. Without it a green gate can mean broken
discovery, a matcher that no longer sees bindings, or a swallowed exception.
The path, not merely the class name, survives rename and namespace ambiguity.

Observational mode publishes the metric and does not fail the build; use it
to choose a threshold. Blocking mode fails CI. A ratchet is often least
disruptive: no provider may increase above its checked-in baseline, and any
provider at or below the global limit must remain at or below it. ThoughtWorks
frames fitness functions as continuous architectural conformance in the
delivery pipeline.
