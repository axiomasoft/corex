## Q1

**Запрос:** `Shopify API version format YYYY-MM, support window length, and publicApiVersions statuses`

**Ответ:**

Shopify uses date-based API handles in YYYY-MM form, released quarterly (January, April, July,
October). A stable version is supported for at least 12 months; `publicApiVersions` exposes the
available versions and a boolean that tells you whether each one is currently supported.

Формат версии: `2026-07`, `2026-10` — YYYY-MM, где месяц соответствует квартальному релизу
(01, 04, 07, 10). Отдельный специальный handle — `unstable`: это не датовый релиз, а
development-версия, и её нельзя считать production-целью совместимости. Для Admin GraphQL,
например: `POST /admin/api/2026-07/graphql.json`.

Окно поддержки: стабильные версии выпускаются в 17:00 UTC первого дня каждого квартала. Каждая
стабильная версия поддерживается **минимум 12 месяцев**, соседние стабильные версии
перекрываются **не менее 9 месяцев** — это даёт приложениям время протестироваться на новой
версии и миграционное окно до потери поддержки.

На дату запроса опубликованное расписание указывает `2026-07` как Latest stable с доступностью
до 16 июля 2027, 15:00 UTC; `2026-10` — release candidate до своего квартального релиза.

Статусы `publicApiVersions`: возвращается список объектов `ApiVersion` с полями `handle`,
`displayName`, `supported`. Формального enum статусов в объекте нет; `supported` — авторитетный
признак. Ключевой нюанс: датовый handle сам по себе не доказывает поддержку — старая версия
может остаться видимой с `supported: false`. Unsupported включает release candidates, unstable и
end-of-life.

Рекомендации по интеграции: хранить версию явным конфигурационным значением; проверять в CI или
по расписанию, что настроенный handle существует и имеет `supported: true`; алертить до конца
поддержки, а не полагаться на fallback-поведение; тестировать очередной release candidate против
своего contract suite, держа production на последнем stable; `unstable` — отдельный лейн
совместимости. `[листинг сокращён: GraphQL-запрос publicApiVersions и пример проверки на PHP]`

**Источники:** shopify.dev/docs/api/usage/versioning

## Q3

**Запрос:** `Stripe API idempotency keys: exact semantics when same key is reused with a different request body, how long keys are retained, idempotency error type, recommended key generation. Also compare with Square/PayPal idempotency contracts.`

**Ответ:** (получен в табличной форме)

| Situation | Stripe behavior |
|:--|:--|
| Тот же Idempotency-Key, тот же POST endpoint и параметры | Возвращается сохранённый код ответа и тело первого исполнения; мутация не выполняется повторно. Реплей включает и сохранённый ответ 500. |
| Тот же ключ, другие параметры или другой endpoint | Возвращается `idempotency_error`. Stripe документирует этот тип ошибки именно для переиспользования, где endpoint и/или параметры не совпадают с первым запросом. |
| Тот же ключ, пока эквивалентный запрос исполняется параллельно | Возможен конфликт; документация связывает HTTP 409 Conflict с конфликтами запросов, включая использование одного и того же ключа идемпотентности. Результат не обязательно кешируется, если endpoint не начал исполнение. |
| Валидация не прошла до исполнения endpoint | Stripe не сохраняет результат идемпотентности, поэтому запрос можно исправить и повторить с тем же ключом. |
| Переиспользование после истечения/очистки | Stripe может вычищать ключи по достижении ими 24 часов. После очистки тот же ключ начинает новый запрос, то есть это не долговременный механизм предотвращения дублей. |

**Источники:** stripe.com (idempotent requests), docs.stripe.com (error types)

## Q4

**Запрос:** `PHP backward compatibility checking tools for library public API: roave/backward-compatibility-check, api-diff, tomasvotruba/class-leak, PHPStan @api and @internal enforcement. Which are maintained in 2026 and how are they used in CI for monorepo packages?`

**Ответ:** (получен в табличной форме)

| Tool | 2026 status | Что защищает | Рекомендация |
|:--|:--|:--|:--|
| `roave/backward-compatibility-check` | Поддерживается и активно релизится; Packagist показывает 8.22.0 от 16 сентября 2026; репозитории активно зависят от линии 8.x | Сравнивает PHP-видимый API двух git-ревизий и сообщает BC-разрывы: удалённые/переименованные символы, изменения сигнатур и наследования, изменения видимости и финальности | Основной CI-гейт для стабильных опубликованных PHP-пакетов |
| `api-diff` | Не является каноническим PHP-инструментом BC; заметный `radarlabs/api-diff` — npm CLI для сравнения JSON/HTTP REST API, а не PHP-классов и методов | Изменения контракта в схемах REST API или записанном HTTP-поведении | Только для внешнего HTTP API, дополнительно к Roave, а не вместо |
| `tomasvotruba/class-leak` | Поддерживается и в активном использовании экосистемы; применяется текущим тулингом Rector и Symplify, включая констрейнты 2.x в свежих метаданных пакетов | Обнаруживает классы, «утекающие» в публичный код, хотя они не предполагались частью поддерживаемой поверхности | Добавить как проверку гигиены API, особенно в модульном монорепо |
| PHPStan `@api` / `@internal` | Enforcement `@internal` поддерживается в ядре PHPStan; поддержка internal-символов документирована для PHPStan 2.1.13+ / bleeding edge на основе restricted-usage расширений, введённых в 2025 | Не даёт потребителям и пакетам использовать internal-символы; обнаруживает internal-типы во внешне видимых параметрах. `@api` помечает намеренные точки расширения, но сам по себе не даёт release-to-release BC-диффа | Использовать постоянно в статанализе каждого пакета; трактовать теги как метаданные владения API |

**Источники:** packagist.org (roave/backward-compatibility-check), packagist.org
(tomasvotruba/class-leak), github.com (radarlabs/api-diff), phpstan.org

## Q5

**Запрос:** `deptrac vs phpat vs custom PHPStan rules for enforcing package dependency boundaries in PHP monorepo 2026`

**Ответ:** (получен в табличной форме)

| Задача | Лучший инструмент | Почему |
|:--|:--|:--|
| Запретить одному пакету напрямую использовать другой | Deptrac | Нативно моделирует граф пакетов/слоёв: по умолчанию межслойные зависимости запрещены, разрешения задаются явным ruleset'ом |
| Зафиксировать DDD/Clean/Hexagonal правила внутри модуля | PHPat | Очень читаемые тесты вида «классы Domain не должны зависеть от Infrastructure», плюс структурные утверждения: наследование, интерфейсы, конструирование |
| Запретить конкретный вызов API, Laravel-фасад, helper или паттерн | Собственное правило PHPStan | Работает на AST и Scope, поэтому может проверять контекст, вызовы методов, типы, атрибуты, имена аргументов и реальные семантические условия |
| Показать архитектурный граф, найти неслойные классы, постепенно мигрировать легаси | Deptrac | Есть графовые форматтеры, отчёты об uncovered dependencies и baseline/skip-violations для поэтапного внедрения |
| Сделать правила ближе к PHP-коду и запускать вместе с PHPStan | PHPat | PHPat — расширение PHPStan; правила пишутся как PHP-тесты/DSL из selectors и assertions |

**Источники:** github.com/qossmic/deptrac, phpat.dev, phpstan.org, context7
