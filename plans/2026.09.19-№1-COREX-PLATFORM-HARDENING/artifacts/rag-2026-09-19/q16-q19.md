## Q16

**Запрос:** `PostgreSQL custom fields: EAV vs JSONB GIN index trade-offs for filtering and sorting`

**Ответ:**

Для custom fields в PostgreSQL обычно не стоит выбирать между «чистым EAV» и «одним JSONB + GIN»
как универсальной архитектурой. Практичный вариант — JSONB для редких/гибких полей, но B-tree
expression/generated индексы для полей, по которым реально фильтруют, сортируют и пагинируют;
наиболее критичные поля со временем выносить в типизированные колонки.

Ключевой факт: **GIN ускоряет поиск по содержимому JSONB, но не выдаёт строки в порядке
`ORDER BY`**. PostgreSQL может удовлетворить сортировку непосредственно из индекса только через
B-tree; после GIN-фильтра часто потребуется отдельный Sort или top-N heapsort.

Что реально умеет GIN по JSONB: стандартный `jsonb_ops` полезен для операторов `?`, `?|`, `?&`,
`@>` и JSONPath-операторов; `jsonb_path_ops` поддерживает меньший набор, но обычно выгоднее, если
основной паттерн — containment через `@>` (в частности, не поддерживает key-exists). Но GIN — это
inverted index для «содержимого документа», а не индекс упорядоченных скалярных значений: запрос
с фильтром `attrs @> '{"status":"active"}'` и `ORDER BY (attrs->>'score')::integer DESC LIMIT 50`
может использовать GIN для поиска, но не получит результат уже отсортированным — строки будут
отобраны и затем отсортированы, и на большой выборке это часто основная стоимость списка. GIN
также плохо отвечает на типичные «реестровые» запросы с диапазонами, `lower(...) LIKE` и
сортировкой по дате — там нужны expression indexes, триггерные/генерируемые колонки либо
нормализованная модель.

Рабочий JSONB-паттерн в три шага. (1) Хранить документ в JSONB рядом с обычными колонками.
(2) Добавлять GIN **только** если пользователи действительно собирают произвольные
equality/containment фильтры, и использовать `@>` с корректными типами — не смешивать `"7"` и `7`,
`"true"` и `true`. (3) Для «горячих» полей создавать B-tree expression indexes с partial-предикатом
по наличию ключа: например `(school_id, ((attrs->>'admission_date')::date) DESC, id DESC)
WHERE attrs ? 'admission_date'`. Индекс обязан буквально соответствовать выражению запроса:
одинаковый cast, направление сортировки, NULLS FIRST/LAST при необходимости. Добавление `id` в
конец — не косметика: это стабильный tie-breaker, позволяющий перейти на cursor/keyset-пагинацию
без «скачущих» строк между страницами. `[листинг сокращён: DDL, индексы и keyset-запрос]`

(4) Если поле стало продуктово важным, его выносят в колонку: тогда появляются настоящие
`NOT NULL`, `CHECK`, `FOREIGN KEY`, `UNIQUE`, статистика планировщика, предсказуемые типы,
простой SQL и отчёты, и заметно меньше риск падения запроса на грязном значении вроде `"unknown"`
там, где ожидается дата.

Когда оправдан EAV: когда custom fields — это формальная пользовательская схема, где нужны
каталог полей с типом, label, required, validation, options, visibility; отдельные permissions или
аудит на уровне конкретного поля; массовые изменения значения одного атрибута без перезаписи
всего документа; много tenant-defined полей с существенно разной структурой; отдельный жизненный
цикл значения, истории и источника данных. Но EAV для фильтруемых сущностей легко превращается в
набор self-join/EXISTS: при трёх-пяти фильтрах получается несколько независимых проверок по
таблице значений — это может быть приемлемо при хороших индексах, но усложняет планирование,
отчётность и динамические UI-фильтры. Если выбран EAV, не делать универсальное `value text`:
минимум — типизированные колонки (`text_value`, `numeric_value`, `date_value`, `bool_value`,
`option_id`) с `CHECK (num_nonnulls(...) = 1)` и индексами по типу и field ID вида
`(tenant_id, field_id, value, entity_id)` с partial-предикатами. Так EAV способен эффективно
фильтровать и сортировать по одному известному field ID, но динамическая сортировка по
произвольному полю всё равно требует генерации корректного SQL и аккуратной работы с
отсутствующими значениями. `[листинг сокращён: DDL EAV и индексы]`

Рекомендация для CRM/SIS — гибрид с эволюцией, а не «all-in»: обычные колонки для scope,
ownership, статуса, дат жизненного цикла, связей и финансовых значений; `jsonb` для редких и
только отображаемых полей; каталог метаданных поля; GIN для произвольных equality/containment,
если их действительно много; B-tree expression indexes или generated columns для полей из списка
«filterable/sortable/reportable»; materialized/reporting projection, когда нужно одновременно
фильтровать по множеству custom fields, сортировать и агрегировать в больших multi-tenant таблицах.

Важные ловушки: рассчитывать на GIN для сортировки; expression index без partial-предиката, когда
ключ есть у малой доли записей; cast в запросе, способный упасть на грязном значении (валидировать
на записи или использовать generated typed columns); отсутствие tenant-first индексирования (почти
каждый реестровый индекс должен начинаться с tenant/scope-колонки); низкая cardinality
одиночного индекса по статусу; отсутствие проверки через `EXPLAIN (ANALYZE, BUFFERS)`;
индексирование «полей» вместо фактических query shapes.

**Источник:** postgresql.org/docs/current/indexes-ordering

## Q17

**Запрос:** `Why OAuth client scopes must not replace per-user domain authorization and field-level security: layered authorization model in Salesforce and GraphQL field-level authorization guidance`

**Ответ:**

OAuth client scopes и пользовательская авторизация решают разные задачи. Scope ограничивает, что
токен приложения **может попытаться** сделать; пер-пользовательская доменная авторизация и
field-level security решают, может ли текущий principal выполнить конкретное действие над
конкретной записью и увидеть конкретный атрибут. Замена второго первым сворачивает необходимый
контекст — идентичность, tenant, владение, отношение, состояние записи и чувствительность
данных — в грубую возможность клиента.

Решение об авторизации должно быть **пересечением** слоёв, а не заменой: слой клиента/токена
(scope) → доменная политика (запись) → field-level контроль (атрибут). Scopes необходимы, но
принадлежат уровню клиента/токена: они сужают радиус поражения токена, а не образуют всю систему
прав.

Почему scopes не могут заменить пользовательскую авторизацию:

1. **Scopes обычно грубые и клиенто-ориентированные.** Salesforce описывает OAuth scopes как
   разрешения токена, определяющие, какие данные и действия connected app может выполнять от имени
   пользователя; метаданные Connected App документируют scopes вроде `Api`, `Full`,
   `RefreshToken` и identity/profile-связанные. Существенно, что даже `Full` ограничен данными,
   доступными **вошедшему пользователю**, и не создаёт независимую модель record- и
   field-security. Scope `crm.read` не может выразить политику «агент поддержки может читать
   контакт клиента только если назначен на его кейс, не может читать `credit_limit`, а `email` —
   только при наличии согласия на коммуникации».
2. **Один и тот же пользователь имеет разный доступ к разным записям.** Доступ к записи обычно
   контекстный: владение, команда, sharing, иерархия отчётности, лимит согласования, назначение
   на класс/кейс, активность обработки. Перенос этого в scopes даёт либо взрыв scope'ов
   (`read:invoice:123`), либо широкие scopes, которые молча становятся overprivileged.
3. **Доступ к полям различается внутри одной записи.** Даже имея право читать запись, пользователь
   может не иметь права читать каждое поле; `customer.read.email` начинает кодировать структуру
   схемы в OAuth-регистрацию, становится хрупким при эволюции схемы и всё равно не выражает
   владение, tenant, согласие и цель использования.
4. **Scopes не моделируют бизнес-действия безопасно.** `invoice:write` не различает
   «редактировать черновик», «отправить на согласование», «согласовать», «аннулировать»,
   «сменить банковские реквизиты», «переоткрыть оплаченный» — у этих действий разные требования к
   полномочиям и правила переходов состояния.
5. **Токены переносимы, доменные права должны оставаться авторитетными.** Токен может быть
   переигран скомпрометированным клиентом, использован из нового пути интеграции или жить до
   истечения после смены роли. Нужна глубина защиты: короткое время жизни и отзыв, allow-listing
   приложений и политики доступа, повторная проверка активности пользователя и прав, оценка
   tenant/владения/sharing, валидация состояния записи и инвариантов в транзакции, фильтрация
   полей на каждом пути ответа, аудит с пользователем, клиентом, subject токена, объектом,
   записью, полем/действием и решением.

Интерпретация для Salesforce: конфигурация connected app определяет, как внешнее приложение
аутентифицируется и какие широкие API-возможности может запросить; есть политики и назначения
(профили, permission sets, custom attributes, custom scopes). Но эффективный доступ к данным
должен по-прежнему зависеть от авторизационной позиции пользователя: object permissions,
field-level security, record-level sharing, permission sets, профили, иерархия ролей, sharing
rules, restriction rules, а Apex/system-context должен проектироваться так, чтобы кастомный код не
обходил намеренные sharing и field-security. Операционное различие: scope connected app может
разрешить интеграции вызывать API **как пользователь**, но не должен трактоваться как авторизация
на все записи и поля, которые разработчик интеграции решил запросить.

Руководство по GraphQL: GraphQL делает потребность в слоистой авторизации особенно заметной,
потому что один запрос обходит множество типов, связей и полей. GraphQL Foundation рекомендует
аутентифицировать до исполнения GraphQL и делегировать авторизацию бизнес-слою, а не держать
основную политику только в GraphQL-слое; решения должны приниматься для полей, включённых в
запрос. GraphQL.js аналогично рекомендует трактовать GraphQL как тонкий слой исполнения над
доменными сервисами, которые и обеспечивают контроль доступа.

Рекомендуемая архитектура: OAuth-проверки на границе (issuer, audience, подпись, expiry, client,
scopes, построение principal), бизнес-авторизация в переиспользуемом policy/доменном коде,
отдельная явная оценка чувствительного поля. Resolver оркестрирует проверки, но не является
единственным местом политики: та же политика обязана защищать REST-эндпоинты, фоновые джобы,
экспорты, webhooks, админ-интерфейсы и прямые вызовы сервисов. Object-проверки — до field-проверок:
field-level security уточняет доступ, но обычно не заменяет вопрос «может ли вызывающий видеть
объект вообще». GitLab формулирует это явно: field-авторизация уместна для скалярных полей,
требующих иного уровня защиты, но не заменяет object-level проверки, если авторизация объекта не
установлена в другом месте.

Выбор поведения при отказе в доступе к полю: `null` — распространённый паттерн скрытия, но
требует nullable-полей в схеме и ясного контракта с клиентом; GraphQL.js предупреждает, что
introspection и инструменты разработчика раскрывают структуру схемы, поэтому скрытие значения не
равно скрытию существования поля. Нельзя применять field-авторизацию только на UI или на корне
запроса: чувствительное поле достижимо альтернативными путями обхода, и каждый resolver/путь
обязан сходиться на одной централизованной политике — иначе гибкость GraphQL становится
поверхностью обхода авторизации.

Практические правила: трактовать scopes как грубые потолки уровня клиента/токена, а не как полную
модель бизнес-прав; требовать и подходящий scope, **и** актуальное доменное решение; оценивать
tenant-изоляцию как инвариант доступа к данным, а не как опциональную конвенцию resolver'а;
применять record-level политики до возврата объектов и коллекций; применять field-level политику
для чувствительных полей, включая вложенные пути связей и мутации; централизовать policy-функции;
использовать action-ориентированные права (`invoice.approve`, `student.medical.read`) вместо
сведения всего к CRUD-scope'ам; делать чувствительные GraphQL-поля nullable, если выбранное
поведение отказа — `null`; не полагаться на отключение introspection, скрытые UI-элементы,
клиентскую фильтрацию и недокументированные поля как на средства защиты; тестировать авторизацию
матрицей «клиент × роль × tenant × отношение к записи × поле × действие × состояние ресурса».

Краткое правило: scopes авторизуют широкую делегированную возможность клиента; доменные политики
авторизуют операцию актора над конкретным ресурсом; field-level контроль авторизует раскрытие или
изменение отдельного атрибута. Все три нужны, потому что каждый защищает от своего режима отказа.

**Источники:** developer.salesforce.com (connected app metadata), graphql.org/learn/authorization,
graphql-js (authorization strategies), docs.gitlab.com (graphql authorization)

## Q18 — несущий источник решения D2

**Запрос:** `API versioning strategy for self-hosted / on-premise products where server and clients upgrade independently: date-based versions vs semantic versioning vs capability negotiation. Recommendations and real examples (GitLab, Atlassian Data Center, Grafana).`

**Ответ:**

Для self-hosted/on-prem продукта, где серверы и независимо развёрнутые
клиенты/плагины/автоматизации обновляются по разным расписаниям, рекомендуется гибрид:
небольшое число долгоживущих major-версионированных контрактов API в URL (например `/api/v1`);
аддитивная эволюция каждого стабильного контракта (необязательные поля запроса, новые поля
ответа, новые endpoint'ы, новые capability); capability negotiation для опциональной и
зависящей от развёртывания функциональности — особенно того, что зависит от установленных
модулей, лицензионного уровня, флагов или пошаговой раскатки; date-based версии — только для
внешне управляемого быстро меняющегося публичного API со строгим публичным календарём вывода из
эксплуатации, а не как основной механизм для on-prem.

Иначе говоря: SemVer-подобные major-версии API для несовместимых контрактов; capabilities для
runtime-реальности; SemVer продукта — отдельно. Это ближе всего к устойчивым паттернам GitLab,
Atlassian Data Center и современной Grafana.

Ключевое различие: нельзя позволять одной «версии» отвечать на несколько несвязанных вопросов.
Клиент не должен выводить «фича X существует» из «сервер >= 4.8.0»: в on-prem реальности флаги,
опциональные плагины, лицензирование, поэтапная раскатка кластера, различия редакций,
конфигурация и бэкпорты делают такой вывод неверным. Правило: версионирование контракта
предотвращает несовместимую интерпретацию; capability discovery решает, что можно пытаться делать.

Рекомендуемый дефолт: `/api/v1/...` (и `/api/v2/...` только при обоснованном чистом
несовместимом контракте), `GET /api/meta` (информация о сервере/продукте/редакции/сборке/
протоколе), `GET /api/capabilities` (обнаруживаемый, эффективный набор возможностей),
`GET /api/openapi.json` (схема развёрнутого контракта). Логика клиента: аутентифицироваться;
однократно прочитать корни API/capabilities и кратко закешировать; выбрать наибольший взаимно
поддерживаемый стабильный major контракта; включать опциональное поведение только когда его
capability объявлена; трактовать неизвестные JSON-поля и неизвестные capability как нормальные;
корректно откатываться при отсутствии capability или неподдерживаемой операции; показывать
предупреждения об обновлении/депрекации операционно, а не как жёсткие отказы.

**GitLab: стабильный major контракта.** REST API использует `/api/v4`; документация явно
описывает `4` как major API. Аддитивные фичи приходят без явного minor в пути, несовместимое
изменение требует нового major. Major-изменения и удаление полной версии координируются с major
релизом GitLab. Экспериментальные/бета-элементы и поля за выключенными по умолчанию
feature-флагами исключены из обычного процесса депрекации. Что заимствовать: major контракта в
пути, а не полную версию продукта; новые операции и необязательные свойства внутри существующего
major; никогда не превращать ранее необязательное свойство запроса в обязательное внутри `v1`;
явно классифицировать alpha/beta/experimental/flag-gated как нестабильное; трактовать
документацию и release notes как часть операций совместимости. Чего не переинтерпретировать:
утверждение GitLab о соответствии SemVer относится к границе major API; URI не раскрывает каждый
семантический minor/patch — для стабильного серверного контракта это обычно и требуется.

**Atlassian: compatibility-first плюс capability detection.** Политика особенно релевантна для
Data Center-развёртываний с плагинами и независимо меняющимися инстансами. Сохраняются стабильные
URI и имена/типы JSON-свойств; новые query-параметры и распознаваемые свойства запроса обязаны
оставаться необязательными, а дефолты — сохранять прежнее поведение. Новые свойства ответа могут
добавляться, поэтому клиент не должен считать недокументированное свойство всегда присутствующим
или пространство значений навсегда закрытым. **Самое важное для on-prem: Atlassian пишет, что
ответы API не помечаются версией API, и рекомендует клиенту запрашивать capability и корректно
обрабатывать её отсутствие, потому что версия/набор возможностей развёртывания может измениться
без предупреждения — вплоть до изменения между запросами.** Политика также прямо оговаривает
расширения плагинами: плагины могут включаться, выключаться, обновляться и понижаться, поэтому
клиент не должен считать, что данные расширения существуют или что переданные данные расширения
будут сохранены. Отсюда правило: никогда не делать глобальную «версию сервера» единственным
детектором фич, если расширения, модули, лицензии или флаги влияют на эффективную поверхность
API. Atlassian также формализует сигналы депрекации заголовками `Deprecation`, `Sunset` и `Link`
с ссылкой на миграционное уведомление.

**Grafana: группы ресурсов плюс уровни зрелости.** Grafana 12+ ввела Kubernetes-подобную форму
`/apis/<group>/<version>/namespaces/...`. Версии различают `v1alpha1`, `v1beta1` и стабильную
`v1`; GA API включены по умолчанию и обещают обратную совместимость, alpha за feature-флагом и
могут измениться или исчезнуть; ломающее изменение схемы беты требует новой генерации беты
(`v1beta2`). Это полезно, если у продукта много ограниченных областей: предотвращает глобальную
миграцию на единый `v2` для несвязанных доменов. Grafana также демонстрирует реалистичную
дисциплину миграции: legacy `/api` депрекированы в пользу `/apis`, но остаются работоспособными
на время перехода, а удаление отложено до будущего major с заблаговременным уведомлением.

Конкретная архитектура. Обещания стабильного контракта `/api/v1`: существующие пути сохраняют
смысл; имена и JSON-типы существующих полей ответа не меняются; существующие обязательные поля
запроса продолжают приниматься; новые поля ответа могут добавляться в любой момент; новые поля
запроса необязательны и имеют обратно совместимые дефолты; клиенты обязаны терпеть неизвестные
поля ответа и неизвестные значения перечислений, если поле явно не объявлено закрытым набором;
пропущенное необязательное поле, `null`, пустая коллекция и «нет права видеть поле» имеют
документированные и различимые семантики; курсоры пагинации, ETag/версии ресурса и возвращаемые
сервером URL непрозрачны, клиент их не конструирует; транспортные 404, 403, 409, 412, 422 и 429
имеют стабильные документированные значения. Не использовать номер релиза продукта в путях
запроса; не использовать `/api/2026-09/...`, если вы не ведёте программу датовых релизов.

Документ capabilities отдаётся аутентифицированно, с ETag и коротким server-provided TTL и
содержит информацию о продукте (имя, версия, редакция, сборка), поддерживаемых стабильных версиях
API и эффективных capability с причинами недоступности (`module_not_installed`), лимитами и
ссылками на схему. Для внешних плагинов уместны reverse-DNS/namespace-ключи. Не превращать каждую
деталь реализации в capability: capability описывает стабильный документированный поведенческий
контракт, а не `postgresql-16-enabled`. Для capability, зависящих от principal/tenant/лицензии,
либо возвращать эффективные возможности текущего токена и тенанта, либо явно разделять
доступность на уровне инстанса и авторизацию principal'а — доступность capability не означает,
что текущий пользователь может выполнить каждую операцию, авторизация остаётся в доменном слое.
`[листинг сокращён: пример /api/meta с capabilities]`

Ошибка при отсутствии возможности — структурированная и машинно-обрабатываемая, например
`422 Unprocessable Content` с `application/problem+json`, полями `type`, `title`, `status`,
`code: capability_unavailable`, `capability`, `reason` и блоком `upgrade` со ссылкой на
документацию и минимальной версией сервера. Коды использовать аккуратно: 404 — ресурс/маршрут
действительно отсутствует (приемлемо при зондировании опционального endpoint'а); 403 — capability
есть, но у principal'а нет доступа; 409 — конфликт состояния, включая состояние миграции/раскатки;
412 — неудачное предусловие, обычно ETag/версия ресурса; 422 — маршрут есть и запрос синтаксически
валиден, но поведение невозможно в этом развёртывании; 501 в целом избегать для согласования фич.

Когда сохранять `v1`: новое необязательное поле ответа; новый фильтр или сортировка с неизменным
прежним поведением по умолчанию; новый endpoint; новый тип ресурса; новое необязательное свойство
в create/update; оптимизация производительности с сохранённой наблюдаемой семантикой;
дополнительные значения перечисления, если перечисление ранее не объявлено закрытым; фича,
включаемая capability, модулем или редакцией. Когда оправдан `v2`: смена JSON-типа поля; смена
смысла/области идентификатора; смена наблюдаемой семантики машины состояний; переход синхронной
записи в принципиально асинхронную без совместимой семантики ответа; смена модели пагинации,
которую клиенты не могут потреблять безопасно; материальная смена семантики аутентификации/
авторизации; удаление или перепрофилирование ранее стабильного endpoint'а; смена значения
null/missing/empty. Тогда публикуется `/api/v2`, `/api/v1` поддерживается документированный
период, и предпочтительно предлагается серверная конвертация/адаптеры для ценных интеграций.

Механика депрекации: для стабильного API удаление — событие жизненного цикла продукта, а не
неожиданность после обновления. Возвращать `Deprecation`, `Sunset` и `Link` с
`rel="deprecation"` (модель Atlassian). Для on-prem определять поддержку в релизных линиях, а не
только в календарных месяцах: introduced in, deprecated in, supported through, removal eligible
in, исключение для критических проблем безопасности/целостности/комплаенса. Поскольку клиенты
могут пропускать несколько версий, публиковать также руководства по обновлению с каждой
поддерживаемой линии, матрицу совместимости API, pre-upgrade проверки, находящие активные вызовы
депрекированных endpoint'ов, и dry-run/отчёт совместимости перед деструктивной миграцией.

Как сюда вписываются date-based версии: они убедительны, когда провайдер может обеспечить
предсказуемый публичный cadence и клиенты согласны регулярно миграции; Shopify — архетип, где
датовая версия становится ясным снимком, а формальное расписание релиза/вывода — часть
контракта. Но эта модель работает лучше всего, когда провайдер централизованно контролирует
раскатку сервиса и коммуникацию миграций. Для независимо обновляемых on-prem серверов тот же
подход создаёт неудобные вопросы: присутствует ли `/api/2026-09` в установке 4.7 клиента; должен
ли клиент 2026-09 держать пять лет датовых ветвей контракта; какая дата применима, когда клиент
установил бэкпортированный security-релиз, но не поезд фич; может ли плагин экспонировать лишь
подмножество датовой поверхности; что дата говорит о выключенном флаге или отсутствующем
enterprise-модуле. Разумный компромисс: релизы продукта — SemVer, major'ы контракта API — `v1`/`v2`,
снимки документации — датами, каталог capability — по развёрнутому релизу.

Практическая рекомендация для Laravel-продукта: один стабильный публичный REST API `/api/v1`;
OpenAPI на развёрнутый сервер с идентификатором сборки/ревизии; discovery-эндпоинт
(`/api/meta` или `/.well-known/product-api`) с продуктом, редакцией, включёнными major'ами API и
эффективными capability; явное экспериментальное пространство (`/api/experimental/...` либо
`v1alpha1`/`v1beta1`), которое никогда не называется стабильным; per-domain capability-ключи;
только аддитивные изменения `v1` с проверкой тестами совместимости; параллельные major'ы только
при настоящих разрывах; SDK, который согласовывает, а не предполагает; HTTP-депрекация и матрица
обновления; contract-тесты по путям обновления (старый клиент ↔ новый сервер, новый клиент ↔
старый поддерживаемый сервер, плагин отсутствует/присутствует, смешанное состояние раскатки,
переходы лицензии/флага). Клиент обязан обрабатывать и гонку, когда capability исчезла после
discovery, — путь запроса должен возвращать типизированный восстановимый отказ.
`[листинг сокращён: пример клиентской логики на PHP]`

Итог: выбирать семантические major-версии API как долговечный публичный контракт; держать
`/api/v1` стабильным и развивать аддитивно как можно дольше (модель GitLab `/api/v4`); применять
capability negotiation как first-class runtime-протокол (ключевое наблюдение Atlassian о
недостаточности версий развёртывания при наличии плагинов); при необходимости использовать
маркировку зрелости alpha/beta/GA в стиле Grafana и группы/версии ресурсов только когда доменным
контрактам действительно нужны отдельные жизненные циклы релиза; **не вести on-prem продукт с
date-based версиями в путях** — использовать даты для снимков документации и формальных
календарей депрекации, тогда как совместимость несут major'ы API и объявленные capability.

## Q19

**Запрос:** `stancl/tenancy v4 status 2026 for Laravel 12/13 multi-database tenancy: bootstrappers, queue tenancy, known caveats with long-running workers and Octane.`

**Ответ:**

stancl/tenancy v4 — текущая мажорная линия для современного стека Laravel и обоснованный выбор для
database-per-tenant SaaS на Laravel 12. Документированный базис — PHP 8.4+ и Laravel 12+, поэтому
Laravel 13 находится внутри целевого поколения совместимости, но для production-раскатки на
Laravel 13 всё равно следует запинить протестированный релиз v4 и сверить его CI-матрицу и
changelog с вашей конкретной комбинацией Laravel/PHP.

Ключевое архитектурное улучшение против v3 — более явное и обратимое переключение tenant-контекста,
особенно для очередей. Это делает v4 существенно безопаснее для демоноподобных воркеров, но не
снимает необходимости проектировать все stateful-сервисы, singleton'ы и сторонние интеграции с
учётом снятия контекста.

Для продукта, которому нужны сильная изоляция клиента, tenant-специфичный backup/restore,
независимая миграция БД и уменьшенный радиус поражения от ошибок в запросах, multi-database режим
v4 подходит: при инициализации тенанта `DatabaseTenancyBootstrapper` создаёт/использует
tenant-соединение и делает его соединением Laravel по умолчанию, поэтому обычные запросы без
явного соединения идут в БД тенанта. Provisioning — упорядоченный `JobPipeline`, обычно
CreateDatabase → MigrateDatabase → SeedDatabase, синхронно или через очередь; вокруг кастомных
инфраструктурных шагов (дампы схемы, S3, биллинг, внешняя identity) нужна собственная политика
идемпотентности и повторов. v4 также добавляет поддержку PostgreSQL RLS, параллельные
tenant-миграции и команды, pending tenants, новые bootstrapper'ы URL/broadcasting/logging и более
строгую валидацию database manager'а. Миграция с v3 на v4 нетривиальна: требования выросли до
PHP 8.4/Laravel 12, database-связанные неймспейсы переехали, конфигурацию нужно переопубликовать и
переприменить, ряд статических опций стал конфигурационными ключами, а `TenantConfig`
депрекирован в пользу `TenantConfigBootstrapper`.

**Bootstrapper'ы.** `tenancy()->initialize($tenant)` (обычно из middleware идентификации)
запускает lifecycle, и настроенные bootstrapper'ы переключают глобальное состояние Laravel в
tenant-контекст; `tenancy()->end()` откатывает. **Порядок критичен для корректности:**
bootstrapper'ы исполняются строго в порядке `tenancy.bootstrappers` и откатываются в обратном
порядке; зависящий от tenant-соединения (например database-backed cache scoping) обязан идти
**после** `DatabaseTenancyBootstrapper`. Кастомные bootstrapper'ы — singleton-экземпляры с
устойчивым внутренним состоянием: они обязаны захватить исходное центральное состояние до мутации и корректно
восстановить его в `revert()`; документация прямо рекомендует, чтобы `revert()` был
идемпотентным/безопасным после инициализации, включая пути частичного отказа. Важно: мутация
`config()` недостаточна — уже разрешённый singleton-клиент, закешировавший конфигурацию, тоже
должен быть сброшен. `[листинг сокращён: пример bootstrapper'а с сохранением и восстановлением]`

**Очереди и воркеры.** Дефолтный `QueueTenancyBootstrapper` — правильный дефолт для
мультитенантных production-очередей: при dispatch'е в активном tenant-контексте ключ тенанта
кладётся в payload; перед обработкой контекст инициализируется; после обработки происходит возврат
к предыдущему/центральному контексту. Это устраняет существенную опасность v3-образца —
сохранение контекста между джобами в одном воркере: в v4 каждый job получает свежую
инициализацию, а изменения состояния тенанта подхватываются следующим джобом.

Конфигурация database-очереди: при database queue плюс `DatabaseTenancyBootstrapper` таблица
`jobs` обязана жить в **центральной** БД, а не в той, откуда случился dispatch. Один воркер
потребляет общий поток джобов, а payload сообщает, в какой tenant-контекст войти — центральное
соединение задаётся явно в конфигурации соединения очереди, и нельзя полагаться на то, что
соединение по умолчанию останется центральным при активной tenancy. Конфигурация Redis-очереди:
если включён `RedisTenancyBootstrapper`, соединение, несущее трафик очереди, не должно входить в
его tenant-префиксованные соединения — нужно выделенное непрефиксованное соединение, иначе
задиспатченный в одном контексте job попадёт в tenant-префиксованную очередь и станет невидим для
общего воркера. Центральные джобы из tenant-кода (глобальная аналитика, сверка биллинга,
control-plane provisioning, уведомление оператора) v4 позволяет направлять в отдельную
центральную очередь — делать это явно, а не полагаться на «отсутствие tenant ID» как на случайное
поведение. Дисциплина payload: не кладите tenant-Eloquent-модели (или любые модели, привязанные к
динамическому tenant-соединению) в конструкторы джобов; предпочитайте скалярные идентификаторы и
перечитывайте записи в `handle()` после инициализации tenancy — это снижает связанность
сериализации, делает поведение повторов яснее и избегает падений в инструментах, десериализующих
джобы после снятия tenancy. `[листинг сокращён: пример джоба со скалярным payload]`

**Долгоживущие процессы и Octane.** Дефолтное поведение очередей v4 спроектировано для
долгоживущих воркеров: инициализация на job и откат после. Но долгоживущие PHP-процессы —
включая Horizon, `queue:work`, воркеры Octane, Reverb и кастомные демоны — делают ошибки lifecycle
значительно дороже, потому что глобальное/контейнерное/статическое состояние переживает запрос или
job. `QueueTenancyBootstrapper` предпочтителен, если нет проверенной несовместимости на уровне
слушателей; он восстанавливает контекст после джоба, поэтому job тенанта A не должен оставить
активными его соединение по умолчанию, префикс кеша, корни файловой системы, генератор URL и
runtime-конфигурацию для тенанта B или центральной работы. Тестировать под фактическим
долгоживущим воркером нужно: job A → job B; job тенанта → центральный job; упавший job тенанта →
следующий job; повторы, таймауты, `queue:restart`, завершение Horizon, рециклинг воркеров; ссылки
в письмах, файлы, ключи кеша, логи и ключи Redis до и после границы джоба; удаление/приостановка
тенанта при уже поставленном в очередь джобе.

`PersistentQueueTenancyBootstrapper` сохраняет tenant-контекст после джоба; основной кейс —
слушатель `JobProcessed`, которому нужно инспектировать/десериализовать tenant-привязанный job
(например job watcher Telescope). Существенные оговорки: с Redis-очередями его нельзя использовать
вместе с `RedisTenancyBootstrapper`; если Redis tenancy неизбежна, очередь обязана быть хотя бы на
непрефиксованном соединении; необходимо доказать, что `php artisan queue:restart` наблюдается
сразу после tenant-джоба — потерянное/отложенное поведение restart в комбинации с Redis и есть
причина, по которой persistent-модель перестала быть дефолтом. Для чувствительной к эксплуатации
системы это явный trade-off: либо переработать границу слушателя/сериализации, либо изолировать
этот класс воркеров и завести деплой-тест именно вокруг переходов тенанта и корректного
graceful-restart'а.

Octane-специфика: общие правила bootstrapper'ов применяются напрямую — bootstrapper'ы основаны на
singleton'ах и удерживают внутреннее состояние, поэтому каждый stateful-сервис приложения обязан
корректно восстановить центральное состояние или иначе быть пересобран/сброшен в конце
tenant-контекста. Практические правила: убедиться, что middleware идентификации тенанта работает
на каждом tenant-HTTP-запросе и lifecycle корректно завершается; не держать tenant-специфичные
Eloquent-модели, соединения БД, значения конфигурации, auth-объекты, API-клиенты, диски и
экземпляры репозитория кеша в статических свойствах или process-wide singleton'ах; быть
осторожным с конструкторно-инъектированными зависимостями, разрешёнными во время загрузки воркера
(если singleton прочитал конфигурацию или захватил клиент БД/кеша до инициализации тенанта,
изменение конфигурации само по себе не изменит существующий объект); использовать кастомные
bootstrapper'ы для мутации и восстановления состояния долгоживущих сервисов либо разрешать
tenant-зависимые сервисы лениво на запрос/job; тестировать межзапросные утечки на одном
переиспользуемом воркере Octane (тенант A → центральный маршрут → тенант B, включая исключения и
streamed/deferred работу); рециклировать воркеры при деплоях и после изменения конфигурации или
tenancy-кода. Отдельная ловушка multi-database, усиливаемая Octane: нельзя возвращать
Eloquent-модель из `$tenant->run()` и использовать/сериализовать её после выхода из замыкания —
динамическое tenant-соединение могло быть очищено при teardown, что даёт ошибки вида
`Call to a member function prepare() on null`; внутри контекста модель следует превратить в
массив/DTO.

Рекомендуемый базис для нового Laravel 12/13 DB-per-tenant приложения:
`DatabaseTenancyBootstrapper`, `CacheTenancyBootstrapper`, `FilesystemTenancyBootstrapper`,
`QueueTenancyBootstrapper` (дефолтная, не persistent реализация), `UrlGeneratorBootstrapper` плюс
обработка root URL, если очередные письма/уведомления формируют tenant-ссылки,
`TenantConfigBootstrapper` только для действительно tenant-вариативной конфигурации, кастомный
logging/correlation bootstrapper, если tenant-специфичных каналов недостаточно. Плюс: центральное
хранение очередей, выделенное непрефиксованное Redis-соединение очереди при включённой Redis
tenancy, скалярные ID в payload'ах, явные центральные очереди для control-plane работы и
интеграционные тесты, намеренно переиспользующие один воркер/процесс через границы тенанта и
центра. Пакет даёт примитивы переключения контекста; production-безопасность обеспечивается
трактовкой каждого долгоживущего объекта как потенциально «загрязнённого тенантом», пока его
поведение при teardown не доказано.
