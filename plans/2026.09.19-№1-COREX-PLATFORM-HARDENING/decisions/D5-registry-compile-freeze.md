# D5 — Реестры расширений компилируются в immutable snapshot с fingerprint'ом

**Actor:** plan-designer/frontier/high
**Evidence:** RAG:✅ 2026-09-19 — Symfony компилирует контейнер до обслуживания запросов,
tagged services имеют `priority`, но равный приоритет не является механизмом разрешения
конфликтов (нужен стабильный tie-breaker); Drupal кеширует definitions и чистит производные
кеши; Shopware даёт lifecycle install/activate/deactivate/uninstall и требует идемпотентности
по стабильному техническому ключу.
RAG:— в `packages/modules` есть `RegistryCompiler` → `CompiledRegistry` →
`CompiledModuleRegistry` (`failIfMissing` в production), но слово `freeze` в пакете не
встречается ни разу, и запрета дубликатов идентификаторов нет.

## Решение

Каждый типизированный реестр CoreX проходит три фазы: `collecting → compiled → frozen`.

- Дубликат идентификатора внутри точки расширения — **ошибка компиляции**, а не «побеждает
  последний». Замена допускается только явной декларацией `replaces`, с проверкой
  существования цели и ацикличности.
- Порядок детерминирован: `priority DESC, id ASC`. Порядок обхода файловой системы, порядок
  включения модулей и порядок вставки в массив публичными правилами предшествования не являются.
- Скомпилированный реестр несёт `fingerprint`, покрывающий набор и версии включённых модулей,
  нормализованные декларации, версию схемы точки расширения и версию сборки.
- После заморозки runtime-модификация запрещена или явно ограничена.
- Durable-решение (workflow, wakeup, bulk-операция, отложенный job) сохраняет id и версию
  использованного расширения либо fingerprint реестра, чтобы повтор не выполнил другую
  реализацию.

## Почему

Без заморозки поведение зависит от порядка запросов в Octane и воркерах, а без запрета
дубликатов случайная коллизия имён становится молчаливым переопределением. Внешние платформы
дают ровно это разделение: гарантии обеспечивают правила реестра, а не примитивы фреймворка.
Альтернатива «доверять существующему compile» отклонена: compile без freeze и без duplicate
policy не даёт ни одной из двух нужных гарантий.

## Consequences

P11 достраивает `packages/modules` и остальные реестры; P13 использует ту же механику для
профиля версии внешнего API (`ApiProfile` — тот же compile-then-freeze); P1 записывает
инварианты реестра как статью конституции. Fingerprint в durable payload затрагивает
`workflow`, `wakeup`, `tasks-workflow` и будущий bulk-store.
