# D7 — GraphQL-транспорт отложен и не входит в 1.0

**Actor:** plan-designer/frontier/high
**Evidence:** RAG:✅ 2026-09-19 — Lighthouse активен (6.70.1, 2026-09-02, зависит от
`webonyx/graphql-php` ^15, Laravel 9–13), но репозиторий планирует переезд с
`nuwave/lighthouse` на `spawnia/lighthouse`; в `webonyx/graphql-php` `QueryComplexity` и
`QueryDepth` — отдельные validation rules, по умолчанию выключенные.
RAG:— в дереве 0 файлов `*.graphql` и ни одного GraphQL-класса.

## Решение

Canonical abstraction внешнего API — операция; транспорты аддитивны. В 1.0 поддерживаются
HTTP/REST, OpenAPI-документ, MCP/AI-инструменты и консольный вызов. GraphQL-транспорт
переносится в `roadmap.md` §7 и не проектируется в P13/P14; каталог `GraphQL/` в структуре
пакета не создаётся.

## Почему

Ни одно измеренное требование не требует GraphQL: аудит просит его как возможный транспорт и
сам запрещает делать canonical. При этом цена реальна — смена vendor-пространства основной
Laravel-библиотеки и необходимость самостоятельно включать и настраивать ограничители
сложности, иначе GraphQL становится каналом перегрузки. Требование владельца «гибкий и надёжный
продукт» удовлетворяется capability-negotiation и bulk-операциями, а не вторым языком запросов.

Альтернатива «сделать тонкий GraphQL-адаптер сейчас» отклонена: тонкий адаптер без cost-анализа
и без field-level авторизации на всех путях обхода — это именно тот антипаттерн, который
описывают первичные источники по GraphQL-авторизации.

## Consequences

Владелец уточнил 2026-09-19: упор на GraphQL не делается, он может не использоваться вообще —
нужен только задел. Поэтому решение разделяется на две части, и вторая ограничена по объёму.

**Что НЕ делается (ни в одной фазе):** схема, резолверы, адаптер транспорта, каталог
`GraphQL/` в структуре пакета, зависимость на библиотеку GraphQL (ни runtime, ни dev),
`*.graphql` в репозитории, consumer-фикстура GraphQL-клиента, cost-модель по selection set,
упоминание GraphQL в capability-ответе. Ни один item плана не имеет GraphQL в Deliverables.

**Что и есть весь задел (побочный продукт транспорт-нейтральности, отдельной работы не создаёт):**

1. Операция остаётся canonical abstraction: определение, авторизация, валидация, идемпотентность,
   стоимость и наблюдаемость живут в слое операций, а не в HTTP-адаптере.
2. Контракт операции не содержит HTTP-специфичных допущений (метод, путь, статус-код, заголовки
   остаются в адаптере) — это и так требование P13 по разделению transport/application/domain.
3. Выбор полей выражен как параметр операции, а не как HTTP-специфичная строка запроса, поэтому
   будущий selection set подключается к уже существующей точке.
4. Авторизация поля и политика записи проверяются в бизнес-слое на каждом пути обхода, а не в
   контроллере — иначе любой второй транспорт стал бы обходом проверок.
5. Оценщик стоимости P14 принимает набор запрошенных полей и вложенность как входные данные,
   поэтому его можно будет вызвать из другого транспорта без смены контракта.

Каждый пункт — уже принятое требование P13/P14 по другим причинам. Задел фиксируется одним
абзацем в `docs/architecture/api-policy.md` («условия подключения будущего транспорта») и
проверяется тем же contract-тестом транспорт-нейтральности, что и MCP-поверхность: если
операция вызывается из двух разных транспортов без изменения контракта, задел есть.

Возврат вопроса возможен только при внешнем потребителе, которому недостаточно REST + bulk, и
оплаченной стоимости поддержки схемы. `roadmap.md` §7 держит это условие.
