# D8 — Сокращение `corex/core` через внутренние зоны, а не через десять новых пакетов

**Actor:** plan-designer/frontier/high
**Evidence:** RAG:— `packages/core/src` — 109 файлов и 17 верхних каталогов; из «возможностей»,
которые аудит предлагает вынести пакетами: `Money` = 1 файл / 59 строк, `Features` = 1 файл /
121 строка, `Departments` = 2 файла / 205 строк, `Settings` = 2 файла / 210 строк,
`Audit` = 6 файлов / 429 строк, `PubSub` = 7 файлов / 441 строка, `Storage` = 6 файлов /
393 строки, `Views` = 13 файлов / 453 строки, `Testing` = 2 файла (Testbench-харнесс).
Сам аудит предлагает зоны как первый шаг: «не нужно немедленно публиковать десять пакетов».

## Решение

`corex/core` сокращается введением внутренних dependency-зон с явными неймспейсами и
arch-тестами, запрещающими зависимости между зонами вне объявленных направлений. Зоны:
foundation (идентификаторы, clock, execution context, idempotency, транзакционные границы,
result/error-примитивы), messaging, settings, audit, saved-views, storage, tenancy-contracts.

Выделение зоны в отдельный Composer-пакет требует отдельного обоснования: собственный
release lifecycle, внешний потребитель без остального ядра либо тяжёлая зависимость.
Единственное безусловное исключение — `core/src/Testing`: Testbench-харнесс не должен
находиться в production-autoload и выносится в dev-поверхность.

## Почему

Пакет на один файл создаёт постоянную стоимость: composer-имя, split-зеркало, CHANGELOG,
CI-джоб, версия, матрица совместимости, — при нулевом выигрыше в границах, которые зона
обеспечивает уже arch-тестом. Обратный порядок («сначала зоны, потом при появлении причины —
пакет») сохраняет обе опции, тогда как немедленное дробление необратимо для потребителей.

## Consequences

P6 создаёт зоны и arch-гейт между ними; кандидаты на выделение фиксируются в `roadmap.md` §7
с условием возврата. Перенос публичных неймспейсов ядра требует owner-gate G-API и уведомления
FlexCRM. Пункт A30 матрицы вердиктов — `⊘ ОТКЛОНЕНО` с записью в `docs/rejected-optimizations.md`.
