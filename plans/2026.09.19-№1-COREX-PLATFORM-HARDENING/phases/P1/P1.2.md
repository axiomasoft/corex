### P1.2 — Таксономия: схема `extra.corex` и её заполнение в 20 пакетах

**Intent:** Создать `docs/architecture/taxonomy.md` со схемой блока `extra.corex` (`schema-version`, `module`, `package-type`, `stability`, `public-api`), двумя закрытыми наборами значений и объявлением ортогональности архитектурных осей осям Composer — и заполнить блок во всех 20 живых `composer.json`.

**Why:** `extra.corex` сегодня есть в 9 пакетах из 20 и содержит единственный ключ `module` (`RAG:—`, `research/00-baseline-metrics.md` §1, находка N04). Ни `package-type`, ни `stability`, ни `public-api` не объявлены нигде, поэтому P2 нечем классифицировать пакеты, а P3 нечем проверять направление зависимостей и публичную поверхность. `RAG:✅` `extra` — официально открытая точка расширения Composer, но категория установки принадлежит полю `type`, release-стабильность — версии пакета, а собственный блок обязан жить под владеемым неймспейсом и нести целочисленный `schema-version` (`research/P1-design-rag.md` §1, запрос P1-Q1). Отсюда D11: обе оси сохраняются, но документ обязан назвать их ортогональность явно, иначе в одном файле появятся два противоречивых ответа на вопрос «что это за пакет».

**Scope Included:** Файл `docs/architecture/taxonomy.md`: схема блока с таблицей ключей, закрытый набор `package-type` (шесть значений), закрытый набор `stability` (четыре значения), таблица ортогональности осей, таблица распределения по 20 живым пакетам, правило чтения метаданных потребителем. Заполнение блока `extra.corex` в `packages/*/composer.json` всех 20 живых пакетов: добавление `schema-version`, `package-type`, `stability`, `public-api`; существующий ключ `module` сохраняется без изменений там, где он есть. Строка в корневом `CHANGELOG.md`.

**Scope Excluded:** Изменение composer `type` в любом пакете — он Composer-facing и остаётся как есть (D11); изменение `extra.laravel` и любого другого блока `extra`; изменение `require`, `autoload`, `scripts` и версий; добавление `extra.corex` в `packages/import-export` — у тумбстоуна нет `composer.json` (D13); создание гейта, читающего эти метаданные (P3); заполнение `public-api` неймспейсами, которых нет в дереве; изменение любого PHP-файла; создание `table-ownership.md` и `configuration.md` (P2).

**Inputs:** `research/P1-design.md` §3 как нормативная спецификация: §3.1 таблица ортогональности осей, §3.2 готовый текст схемы и обоих закрытых наборов, §3.3 готовая таблица распределения по 20 пакетам с правилом сверки по дереву; `decisions/D11-extra-corex-orthogonal-axes.md` как основание формы; `decisions/D3-package-taxonomy-metadata.md` как исходное решение; `research/P1-design-rag.md` §1 и §4 (1) как внешнее подтверждение; `docs/architecture/constitution.md` (создан P1.1) как владелец статей `API-001` и `PKG-009`, на которые документ ссылается.

**Implementation Rules:** Правка `composer.json` — **только** внутри `extra.corex`. Любое изменение `name`, `type`, `require`, `autoload`, `scripts`, `extra.laravel` — дефект item'а. Порядок ключей внутри `corex`: `schema-version`, `module` (если есть), `package-type`, `stability`, `public-api`. `schema-version` = `1` во всех пакетах. `stability` = `experimental` во всех 20 пакетах: 1.0 не выпущен ни для одного, и `stable` было бы обещанием без гейта, который его проверяет. `package-type` берётся из таблицы `P1-design.md` §3.3 без импровизации: `foundation` — `core`, `modules`; `integration` — `search-intl`, `search-meilisearch`, `tasks-workflow`; `product` — `crm`; `capability` — остальные 14. Перед записью каждого элемента `public-api` исполнитель выполняет `ls packages/<pkg>/src` и **удаляет** из перечня неймспейс, каталог которого физически не существует; создавать каталог запрещено. Форматирование JSON сохраняется в стиле файла (4 пробела, как в существующих `composer.json`), без переформатирования остального документа. `packages/import-export` пропускается: у него нет `composer.json`. Документ `taxonomy.md` не переписывает статьи конституции, а ссылается на их идентификаторы (`API-001` — публичная поверхность, `PKG-009` — тумбстоун).

**Code Guidance:** Готовый JSON-пример и обе таблицы закрытых наборов — `research/P1-design.md` §3.2, переносятся в документ как есть. Таблица ортогональности осей — §3.1. Таблица распределения — §3.3 вместе с тремя примечаниями («почему `api` — `capability`, а не отдельный вид `gateway`», «почему `recurrence` — `capability` при composer `type: library`», «почему тумбстоун не получает метаданных»): они отвечают на вопросы, которые иначе будут заданы снова. Правило потребителя («метаданные — данные, а не полномочие»; «отсутствие блока и невалидный блок — разные состояния»; «неизвестные ключи игнорируются») — §3.2, обязательный абзац документа.

**Validation:** `python3 -c "import json,glob,sys; [json.load(open(p)) for p in glob.glob('packages/*/composer.json')]"` — без исключений. `composer validate --no-check-publish --working-dir=packages/<pkg>` для каждого из 20 живых пакетов — зелёный. Счётчик заполненности: `python3 - <<'PY'` со сверкой, что во всех 20 файлах присутствуют ключи `schema-version`, `package-type`, `stability`, `public-api`, что `package-type` входит в закрытый набор из шести значений и `stability` — из четырёх. Сверка `public-api` с деревом: для каждого перечисленного неймспейса существует соответствующий каталог в `packages/<pkg>/src`. A pre/post JSON snapshot removes only top-level `extra.corex` and proves every remaining semantic value byte-for-byte canonical-equal. The expanded actual write set equals the 23 literal Files paths exactly; any extra/missing path is red. `composer lint:check` из корня — зелёный. `git diff --stat -- 'packages/*/src' 'packages/*/database' 'scripts/' 'tests/' '.github/'` пуст.

**Deliverables:** `docs/architecture/taxonomy.md` со схемой, двумя закрытыми наборами, таблицей ортогональности и распределением по 20 пакетам; заполненный `extra.corex` во всех 20 живых `composer.json`; запись в корневом `CHANGELOG.md`.
