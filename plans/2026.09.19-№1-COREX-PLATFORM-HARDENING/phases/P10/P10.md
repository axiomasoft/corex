# P10 — Attributes: сменный источник определений, стабильная идентичность, эволюция схемы

## Phase Context

> СКЕЛЕТ — не детализирован, разворачивается `design-phase: task:plan-design 2026.09.19-№1-COREX-PLATFORM-HARDENING P10`

RAG:— Подтверждённый P1-дефект: каталог полей собирается только когда в контейнере связаны
**и** `EntityRegistry`, **и** `ModuleRegistry`; иначе возвращается `UnavailableAttributes`.
То есть storage уже сменный (jsonb/eav/ddl), а источник определений — нет: без модульной
системы динамических полей не существует.

Важная поправка к аудиту: вводить новый интерфейс `AttributeDefinitionSource` не нужно — порт
уже есть (`Contracts\FieldCatalogue::snapshot(DataScope, string $entity): FieldSnapshot`).
Нужны его реализации (статическая, БД, composite, кешированная) и снятие требования модулей.
Также опровергнуто предложение ввести тройку `SubjectType`/`SubjectId`/`SubjectRef`: `RecordRef`
уже несёт opaque-handle с валидацией и не равен классу модели или morph-алиасу.

Реальный пробел идентичности другой: поле идентифицируется только кодом, стабильного
идентификатора, живущего при переименовании, нет.

RAG:✅ PostgreSQL: GIN ускоряет поиск по содержимому JSONB, но не отдаёт порядок для `ORDER BY` —
сортировку из индекса умеет только B-tree; практичен трёхслойный подход (JSONB для редких полей,
B-tree expression/partial индексы для фильтруемых и сортируемых, продвижение горячего поля в
типизированную колонку); EAV оправдан при field-level lifecycle и правах.

> **Контракт фазы (contract-first).** Потребляет: Options P7, зону messaging P5.
> Производит: работающие attributes без модульной системы, реализации источника определений с
> формализованной conflict policy, стабильный идентификатор поля, lifecycle определения с
> dual-read/backfill, выбор движка хранения по subject type, цепочку проекции в поиск через
> события и outbox. Границы: существующая очередь DDL-операций не переписывается; связь
> attributes↔search остаётся отсутствующей (проекция строится снаружи).

## Scope Included

Снятие требования `ModuleRegistry`: базовые attributes работают с определениями из PHP, из БД
или из внешнего реестра; реализации порта определений — статическая, БД, composite, кешированная;
формализованная conflict policy composite-источника (дубликат ключа, дубликат стабильного id,
несовпадение типа, конфликт флагов required/default/index, precedence, удаление и депрекация);
стабильный идентификатор поля отдельно от переименуемого ключа; lifecycle определения
(draft → active → deprecated → migrating → retired) поверх существующих kinds
`add/change/retire/drop` и статусов операций; протокол изменения поля с dual-read, backfill,
верификацией и переключением записи; выбор движка хранения по subject type через резолвер
вместо глобального ключа конфигурации; третье состояние — продвижение горячего поля в
типизированную колонку с явной политикой индексов; разделение подсистем пакета
(Schema/Values/Query/Storage/Integration/Laravel); цепочка «мутация значения → доменное событие →
outbox → проекция поиска», не создающая зависимости attributes → search; применение восьми
независимых проверок при записи значений (существование поля, право видеть, право писать,
право операции мутировать, валидность типа и ограничений, владение subject'ом тенантом,
совместимость ревизии схемы).

## Scope Excluded

Переписывание очереди DDL-операций; создание зависимости attributes → search; введение
`SubjectType`/`SubjectId`/`SubjectRef` (опровергнуто: `RecordRef` уже opaque); выбор движка на
каждое отдельное поле (прямая анти-цель); EAV для системных инвариантов; переименования (P15);
структурная раскатка профилей по другим пакетам (P16).

## Dependencies

P7 терминальна (источники конфигурируются типизированно), P5 терминальна (outbox для проекции).
Owner-gate G-DDL при новой таблице. Внутри фазы: снятие требования модулей → реализации
источника → conflict policy → стабильный id → lifecycle и dual-read → резолвер движка →
проекция → восемь проверок записи.

## Validation (ожидаемая форма)

Оба лейна плюс обязательный `composer test:pg` (JSONB, EAV, индексы). Тест «attributes без
модульной системы»: пакет работает при отсутствии `ModuleRegistry` в контейнере. Тест conflict
policy: каждый класс конфликта даёт свою ошибку. Тест dual-read: старое и новое представление
читаются одновременно, backfill идемпотентен, переключение записи обратимо. Тест проекции:
мутация значения приводит к записи в outbox, а attributes не импортирует ни одного символа
`corex/search` — проверяется гейтом графа. Восемь проверок записи покрыты негативными тестами
по каждой.
