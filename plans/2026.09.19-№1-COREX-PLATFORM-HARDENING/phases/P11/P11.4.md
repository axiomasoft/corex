### P11.4 — Workflow definition stamps in existing durable carriers

**Intent:** Записывать и проверять exact workflow definition id/version и
registry provenance без изменения schema или `EngineAdapter`.

**Why:** `research/P11-design.md` §8–§9; D59; D103. `definition_ref`/`version_ref` уже
существуют, но registry provenance и fail-closed validation не связаны в один
durable intent.

**Scope Included:** Non-empty stable ref validation; trigger stamp derivation; stamp in existing JSON
and payload hash; exact-version replay/admission checks; explicit compatibility for legacy specific
version rows.

**Scope Excluded:** Workflow engine implementation; new queue; DDL/migrations; definition migration;
global-fingerprint-only invalidation; changes to external adapter contract.

**Implementation Rules:** Identity is `module:entityHandle:eventName`; version is `versionRef`.
Empty definition/version fails before insert. Stamp is inside the existing payload and payload hash,
but `registryFingerprint` is stored provenance outside canonical replay identity. Exact id+version is
replay authority; unrelated fingerprint change is diagnostic only. The versioned identity schema
selects the new algorithm; legacy non-empty refs retain their original comparison algorithm and are
never backfilled implicitly.

**Code Guidance:** Inject optional registry read dependency at composition; preserve module-free mode
with the explicit `module-free` provenance from §9. Keep public request constructor compatibility if
possible; otherwise require the already documented non-empty values at its validation boundary.

**Validation:** Feature/unit tests cover stamped insert/hash, empty refs, exact match, missing/current
mismatch, unrelated fingerprint drift, legacy non-empty refs and module-free binding; workflow
lint/analyse/test with no migration diff.

**Deliverables:** Version-pinned workflow intents, deterministic hash/provenance and backward-compatible
legacy admission tests.
