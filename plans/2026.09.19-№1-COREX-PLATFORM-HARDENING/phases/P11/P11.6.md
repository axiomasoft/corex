### P11.6 — Complete tasks-workflow materialization provenance

**Intent:** Исправить incomplete recurrence wakeup payload, пинить exact
materializer handler version и заменить silent success на typed failure.

**Why:** `research/P11-design.md` §11; D59. Producer не пишет required
`definitionHash`, а handler при его отсутствии молча выходит, поэтом
запланированная materialization может никогда не выполниться.

**Scope Included:** Payload definition hash and materialization window; canonical `versionRef`;
versioned wakeup definition config; strict decode/consistency checks; observable typed failure;
completion reschedule symmetry.

**Scope Excluded:** Recurrence semantics redesign; new tables/columns; generic retry policy; wakeup
registry implementation; notifications consumer.

**Implementation Rules:** Producer always emits series id, immutable revision, definition hash and
window; handler validates all before mutation. `versionRef` is the canonical definition hash/version
described in §11.1. Missing/inconsistent fields throw the package's typed stale/unsupported error;
never return as success. Initial and completion-triggered scheduling use identical stamp rules.

**Code Guidance:** Centralize payload construction/decoding next to the hasher instead of duplicating
array keys. Register handler version `tasks-materialization/1` through P11.5 structured config. Keep
idempotency keys and current transaction ownership unchanged.

**Validation:** Feature and isolated PG tests prove valid schedule executes, missing/tampered hashes
fail visibly with no write, window survives round-trip, completion reschedule is equivalent, exact
handler mismatch is quarantined by wakeup and duplicate delivery remains idempotent; package checks.

**Deliverables:** Complete materialization payload, exact handler version, strict failure behavior
and end-to-end regression for the previously silent no-op.
