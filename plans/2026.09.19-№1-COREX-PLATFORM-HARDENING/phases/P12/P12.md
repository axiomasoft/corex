# P12 — Таксономия ошибок и наблюдаемость операций

## Phase Context

> СКЕЛЕТ — не детализирован, разворачивается `design-phase: task:plan-design 2026.09.19-№1-COREX-PLATFORM-HARDENING P12`

RAG:— Для ядра CRM/CMS наблюдаемость — часть контракта, а не поздняя надстройка. Сейчас в
`packages/api` есть `requestId` и маппинг исключений в коды, но нет отдельного correlation-id,
нет категорий ошибок, нет признака повторяемости, нет единого пути наблюдения длительной
операции. В ядре шесть общих исключений, а часть пакетов отдаёт общий `Unavailable`, скрывая
причину: отсутствие возможности, выключенная возможность, неподдерживаемая операция, отказ
доступа и отсутствие права по лицензии — это пять разных ответов.

RAG:✅ OpenTelemetry PHP стабилен для traces, metrics и logs, автоинструментация зрела для
типового HTTP/DB-контура, поддержка Laravel 6–13 — собственную tracing-платформу строить не
нужно, нужен bridge. Отдельно подтверждено требование ограниченной cardinality: tenant id не
должен быть неограниченным label'ом метрики.

RAG:✅ По модели ошибок первичные источники расходятся: IETF RFC 9457 и Zalando требуют
`application/problem+json`, Microsoft и Google используют собственный конверт со стабильной
иерархией строковых кодов. Поэтому принято двухслойное решение: стабильные коды в собственном
конверте (он уже существует) плюс problem+json по контент-негоциации.

> **Контракт фазы (contract-first).** Потребляет: envelope и correlation P5. Производит:
> таксономию ошибок с категориями и признаком повторяемости, правило result vs exception,

> который потребляет эту таксономию); не меняет поведение impersonation, только достраивает
> отсутствующие инварианты.

## Scope Included

Таксономия ошибок: категории (authentication, authorization, validation, conflict, not_found,
rate_limit, unsupported, unavailable, internal), стабильный код, путь к проблемному полю,
признак повторяемости, документированные детали; правило, что человекочитаемое сообщение не
является контрактом. Правило result vs exception: ожидаемый бизнес-отказ — типизированный
результат; ошибка программиста или конфигурации — исключение; инфраструктурный сбой — исключение
с безопасным контекстом; частичный отказ батча — отчёт с ошибками по записям; конфликт
параллелизма — доменное исключение или типизированный конфликт. Конкретные пакетные ошибки
вместо общих, с разделением пяти разных «недоступностей». Наблюдатель длительной операции
(старт, завершение, отказ) с обязательным контекстом: идентификатор операции, correlation,
ссылка на аккаунт и воркспейс, актор, имя пакета и операции, длительность, исход, номер
повтора, отредактированные детали отказа. Bridge к PSR-3 и OpenTelemetry вместо собственной
платформы. Правила ограниченной cardinality метрик. Сверка фактических инвариантов
impersonation против полного списка и достройка отсутствующих.

## Scope Excluded

Собственная tracing-платформа и собственный формат трасс; изменение внешнего конверта ответа
(P13); обязательный экспортёр телеметрии в поставке (только контракт и bridge); изменение
поведения существующих guard'ов impersonation; переименования (P15).

## Dependencies

P5 терминальна (correlation и causation живут в envelope). Внутри фазы: таксономия → правило
result/exception → пакетные ошибки → наблюдатель операции → bridge → cardinality → impersonation.

## Validation (ожидаемая форма)

Оба лейна. Тест стабильности кодов: изменение существующего кода краснит гейт контракта. Тест
редакции: детали отказа не содержат секретов и персональных данных. Тест cardinality:
попытка использовать неограниченный идентификатор как label метрики отклоняется. Тест
наблюдателя: для длительной операции фиксируются старт, завершение или отказ с полным
контекстом. Негативные тесты по каждому инварианту impersonation.
