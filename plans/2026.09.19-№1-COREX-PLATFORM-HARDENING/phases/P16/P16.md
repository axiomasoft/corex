# P16 — Раскатка профилей структуры по остальным пакетам

## Phase Context

> СКЕЛЕТ — не детализирован, разворачивается `design-phase: task:plan-design 2026.09.19-№1-COREX-PLATFORM-HARDENING P16`

RAG:— Два крупнейших пакета уже перестроены (ядро в P6, tenancy в P9). Остаются пакеты профиля B,
организованные по типу PHP-класса, а не по подсистемам: `intl` 67 файлов (`Contracts` 10,
`Data` 26, `Internal` 22), `tasks` 59, `api` 55, `notifications` 44, а также `modules` 88 —
там семантические каталоги уже есть, но публичный корень непоследователен (восемь файлов в корне
`src`). Плюс пакеты профиля A, где структура уместна и менять её не нужно: доказать это —
тоже результат фазы.

Отдельно: у `attributes` подсистемы разведены в P10, у `transfer` целевая карта подсистем
принята как карта роста — при 32 файлах полный набор каталогов не создаётся. `panels`
(11 файлов) получает не переименование, а обязательное исследование: пять реальных примеров
панели, из которых следует, остаётся ли имя.

Правило фазы: каталог двигается только если это уменьшает число верхних папок, затрагиваемых
одним use case. Перенос ради соответствия шаблону — прямая анти-цель конституции.

> **Контракт фазы (contract-first).** Потребляет: профили структуры P1, целевые имена P15,
> вердикты классов P2. Производит: применённые профили по остальным пакетам, расформированные
> или обоснованные каталоги `Internal`/`Support`/`Data` в пакетах профиля B/C, результат
> исследования `panels`, доказательство неизменности поведения. Границы: поведение не меняется;
> ни один пакет не создаётся и не удаляется; DDL не меняется.

## Scope Included

Профиль B для `intl` (Locale, Translation, Currency, Territory, TimeZone, Formatting как
предметные подсистемы вместо `Data`/`Internal`); профиль B для `notifications`, `tasks` и
внешнего API по структуре, утверждённой P13; приведение публичного корня `modules` к
последовательному виду (восемь файлов в корне получают место по семантике); расформирование
или обоснование `Internal`, `Support` и `Data` в пакетах профиля B/C по политике P1;
исследование `panels` (пять реальных примеров панели и вывод об имени и структуре);
подтверждение, что пакеты профиля A остаются как есть; обновление allowlist'ов гейта графа,
PHPStan-конфигов, путей CI и `extra.corex.public-api` под новую структуру; карта роста
подсистем `transfer` — как документ, не как пустые каталоги.

## Scope Excluded

Создание и удаление пакетов; изменение DDL; переименования символов (выполнены в P15);
создание каталога, содержащего один класс и не выражающего границу; полный набор слоёв там,
где слоя фактически нет; каталог `GraphQL/` в структуре API (D7).

## Dependencies

P15 терминальна (каталоги двигаются под целевыми именами). Внутри фазы: `intl` →
`notifications` → `tasks` → API → `modules` → исследование `panels` → подтверждение профиля A →
обновление конфигов и гейтов.

## Validation (ожидаемая форма)

Оба лейна по каждому затронутому пакету плюс `composer test:packages` и `composer test:pg` для
пакетов с SQL-путями. Доказательство неизменности поведения: диф содержит только перемещения,
изменения неймспейсов и импортов; публичные сигнатуры не изменились. `composer package-graph-gate`,
`composer test:arch`, гейт публичной поверхности и BC-дифф зелёные — последний доказывает, что
перемещение не сломало потребителя.
