## Q1 — Версионирование Shopify Admin API

**Поддержанное утверждение.** Формат версии — `YYYY-MM`, квартальные релизы (01/04/07/10),
каждая стабильная версия поддерживается **не менее 12 месяцев**, соседние стабильные версии
перекрываются ≥9 месяцев; `publicApiVersions` возвращает `handle`/`displayName`/`supported`,
причём датовый handle сам по себе не доказывает поддержку. `unstable` — не датовый релиз.

**Источник:** shopify.dev/docs/api/usage/versioning.
**Где используется:** `findings/audit-verdicts.md` S03, S04; решение D2.

## Q2 — Cost-based throttling GraphQL Admin API

**Поддержанное утверждение.** Лимит считается по стоимости выбранных полей, не по числу
HTTP-запросов; leaky bucket; скорость восстановления зависит от тарифа магазина
(Standard 100 points/s, Advanced 200, Plus 1 000, enterprise/Commerce Components 2 000).

**Источник:** shopify.dev/docs/apps/build/apis/graphql-admin/rate-limits.
**Где используется:** S08–S11.

## Q3 — Семантика idempotency-ключей Stripe

**Поддержанное утверждение.** Тот же ключ + тот же endpoint и параметры → возвращается
сохранённый код и тело первого исполнения (включая сохранённую 500). Тот же ключ с другими
параметрами или другим endpoint → `idempotency_error`. Параллельный эквивалентный запрос →
конфликт (409). Если валидация не прошла до начала исполнения, результат не сохраняется и
ключ можно переиспользовать. Ключи вычищаются по достижении ≥24 часов, поэтому idempotency —
не долговременный механизм дедупликации.

**Источник:** docs.stripe.com (idempotent requests, error types).
**Где используется:** S23, S24.

## Q4 — Инструменты BC-контроля публичного API в PHP

**Поддержанное утверждение.** `roave/backward-compatibility-check` поддерживается и активно
релизится (8.22.0, 2026-09-16); сравнивает публичный API двух git-ревизий. `api-diff` —
не PHP-инструмент (npm CLI для REST/JSON). `tomasvotruba/class-leak` — живой инструмент
обнаружения случайно публичных классов. PHPStan поддерживает enforcement `@internal`
(документировано для 2.1.13+/bleeding edge); `@api` — метаданные владения, не BC-дифф.

**Источники:** packagist.org (roave/backward-compatibility-check, tomasvotruba/class-leak),
phpstan.org.
**Где используется:** A18, A83; решение D4.

## Q5 — Гейты границ пакетов в PHP-монорепо

**Поддержанное утверждение.** Deptrac нативно моделирует граф слоёв/пакетов с явным
ruleset'ом, baseline и графовыми отчётами; PHPat — расширение PHPStan с читаемыми правилами

конкретного вызова, фасада или паттерна.

**Источники:** github.com/qossmic/deptrac, phpat.dev, phpstan.org.
**Где используется:** A85, P3 (выбор инструмента при детализации: собственный гейт уже есть,
внешний инструмент — только при доказанной выгоде).

## Q6 — Модель ошибок HTTP API

**Поддержанное утверждение.** IETF RFC 9457 задаёт `application/problem+json` с `type`
как основным идентификатором; Zalando требует problem+json для 4xx и 5xx; Microsoft API
Guidelines используют собственный конверт `{error:{code,message,innererror}}` со стабильной
иерархией строковых кодов; Google JSON Style Guide — собственный объект ошибки.

**Источники:** rfc-editor.org (RFC 9457), opensource.zalando.com, github.com/microsoft/api-guidelines,
google.github.io/styleguide/jsoncstyleguide.
**Где используется:** S20–S22 (принято двухслойное решение: стабильные коды в конверте +
problem+json по контент-негоциации).

## Q7 — Контракт курсорной пагинации

**Поддержанное утверждение.** Курсор — подписанная continuation-capability для одной
неизменной формы запроса: кодируется полный кортеж сортировки с уникальным tie-breaker,
версия формата, версия порядка, привязка к tenant/фильтрам, expiry и подпись; резюмирование
строгим лексикографическим предикатом; base64 не является защитой; сервер строит SQL только
из собственного allowlist'а порядков, никогда из имён полей в курсоре; мутируемый ключ
сортировки в принципе не даёт «без дублей и без пропусков».

**Источники:** graphql.org/learn/pagination, postgresql.org (indexes-ordering), RFC 7519.
**Где используется:** S25, S26.

## Q8 — Transactional outbox

**Поддержанное утверждение.** Бизнес-изменение и вставка в outbox — одна транзакция; relay
берёт lease (`FOR UPDATE SKIP LOCKED`) и публикует вне транзакции; доставка at-least-once,
поэтому consumer обязан быть идемпотентным через inbox с unique-constraint в той же
транзакции, что бизнес-запись; `dispatch()->afterCommit()` не заменяет outbox; `event_type`
не должен быть именем PHP-класса; нужен `event_version`.

**Источник:** laravel.com/docs (queues) + сводка практики.
**Где используется:** A91, A92, N05.

## Q9 — Типизированная конфигурация в Laravel-пакете

**Поддержанное утверждение.** Слои: `config/<pkg>.php` знает про дефолты и публикацию;
фабрика/`Options::fromArray()` нормализует и валидирует, получая массив; service provider —
единственное место, где вызывается `config()`; сервисы пакета получают Options через
конструктор и про `config()` не знают.

**Где используется:** A06, A20, A76, N12.

## Q10 — Octane и долгоживущие воркеры

**Поддержанное утверждение.** Всё мутируемое за пределами текущего lifecycle (singleton,
статика, глобали, мутация конфига) может переехать в следующий запрос или job. `scoped()`
сбрасывается на границе запроса/джоба, но **не** сбрасывает статику, собственные глобали,
мутации репозитория конфига и состояние внутри произвольных singleton'ов. Инъекция
`Application`/`Request`/`Config` в конструктор singleton'а — задокументированный антипаттерн.
Восстановление locale — в `finally`. Payload джоба — скаляры, не живые контекстные объекты.
Перезапуск воркеров — гигиена деплоя, не механизм изоляции.

**Источники:** laravel.com/docs/12.x/container, laravel.com/docs/12.x/octane, laravel.com/docs (queues).
**Где используется:** A19, P4.

## Q11 — Long-running и bulk-операции у крупных платформ

**Поддержанное утверждение.** Единый набор у четырёх независимых платформ: явный id операции,

Shopify — `BulkOperation` с JSONL-результатом, доступным 7 дней.

**Источники:** google.aip.dev/151, learn.microsoft.com (Graph LRO),
developer.salesforce.com (Bulk API 2.0), shopify.dev (bulk operations).
**Где используется:** S12–S14, S19; решение D9.

## Q12 — Практика доставки webhooks

**Поддержанное утверждение.** Standard Webhooks: заголовки `webhook-id`,
`webhook-timestamp`, `webhook-signature`; подпись HMAC-SHA256 над строкой
`{id}.{timestamp}.{raw_body}`; окно проверки времени ~5 минут; `webhook-id` — ключ
идемпотентности; список подписей в одном заголовке даёт zero-downtime ротацию секретов;
успех — только 2xx, 410 отключает endpoint, учитывается `Retry-After`; retry с
экспоненциальным backoff и jitter; обязательны история доставок, диагностика и ручной replay;
payload обычно <20 KB, для больших сущностей — ссылка.

**Источник:** github.com/standard-webhooks/standard-webhooks (spec).
**Где используется:** S29, S30, N06.

## Q13 — Реестры расширений: Drupal / Symfony / Shopware

**Поддержанное утверждение.** Надёжный общий паттерн: discover/declare → normalize →
validate uniqueness → sort по явным правилам → compile/cache → инвалидация на контролируемых
границах lifecycle. Symfony компилирует контейнер до обслуживания запросов (ошибки на
warmup/деплое), tagged services имеют `priority`, равный приоритет **не** является механизмом
разрешения конфликтов — нужен стабильный tie-breaker. Drupal кеширует definitions и чистит
производные кеши (включая prototypes). Shopware даёт операционный lifecycle
install/activate/deactivate/uninstall и требует идемпотентности по стабильному техническому
ключу, а также уважения `keepUserData()`. Отдельно подтверждено: durable-решение должно
хранить id/версию расширения или fingerprint реестра, иначе повтор джоба может выполнить
другую реализацию.

**Источники:** api.drupal.org (TypedDataManager), symfony.com/doc (tags, compiler passes),
developer.shopware.com (plugin lifecycle).
**Где используется:** A21, A87–A89, S05; решение D5.

## Q16 — EAV против JSONB в PostgreSQL

**Поддержанное утверждение.** GIN ускоряет поиск по содержимому JSONB, но **не** отдаёт строки
в порядке `ORDER BY` — сортировку из индекса умеет только B-tree. Практичная стратегия —
три слоя: JSONB для редких/гибких полей, B-tree expression/partial индексы (с точным
совпадением cast'а и направления) для полей, по которым реально фильтруют и сортируют,
и продвижение продуктово важных полей в типизированные колонки. EAV оправдан, когда нужны
каталог полей, field-level права/аудит, отдельный lifecycle значения; типизированные колонки
значений и индексы по `(tenant, field_id, value, entity)` обязательны. Ловушки: cast, падающий
на грязном значении; expression index без partial predicate; индексы без ведущего tenant-скоупа.

**Источник:** postgresql.org/docs/current/indexes-ordering.
**Где используется:** A55, A56.

## Q17 — Scope клиента против доменной авторизации и FLS

**Поддержанное утверждение.** Решение об авторизации — пересечение слоёв, не замена: scope
токена ограничивает клиента, доменная политика решает про конкретную запись, field-level
контроль — про конкретный атрибут. Salesforce: даже `Full` ограничен данными, доступными
вошедшему пользователю; object/field/record-sharing остаются основной моделью.
GraphQL Foundation и GitLab: field-авторизация не заменяет object-авторизацию, а политика
должна жить в бизнес-слое, единая для REST, GraphQL, очередей, экспортов и админки.

**Источники:** developer.salesforce.com (connected app), graphql.org/learn/authorization,
docs.gitlab.com (graphql authorization).
**Где используется:** S28, A100.

## Q18 — Версионирование API self-hosted продукта *(несущий источник решения D2)*

**Поддержанное утверждение.** Для сервера и клиентов, обновляющихся независимо, рекомендуется
гибрид: небольшое число долгоживущих мажоров в пути + аддитивная эволюция внутри мажора +
capability-negotiation для всего, что зависит от установленных модулей, лицензии и флагов.
GitLab держит `/api/v4` как долгоживущий мажор (несовместимость — только новый мажор,
экспериментальные и flag-gated поля вне процесса депрекации). Atlassian: URI и типы полей
стабильны, новые параметры обязаны быть необязательными с сохранением поведения по умолчанию,
**ответы не помечаются версией API**, и клиент обязан запрашивать capability и корректно
обрабатывать её отсутствие, потому что доступная поверхность меняется вместе с плагинами —
вплоть до изменения между запросами; депрекация сигнализируется заголовками
`Deprecation`/`Sunset`/`Link`. Grafana: группы ресурсов и уровни `v1alpha1`/`v1beta1`/`v1`,
GA-совместимость обещана, alpha за feature-флагом. Date-based версии уместны, когда провайдер
центрально контролирует раскатку (модель Shopify), и не должны быть основным механизмом
совместимости для on-prem.

**Источники:** docs.gitlab.com/api/rest, developer.atlassian.com (REST API policy),
grafana.com/docs (apis).
**Где используется:** решение D2; S03, S04, S06, S07, S31.

## Q19 — stancl/tenancy v4 и долгоживущие процессы

**Поддержанное утверждение.** v4 — текущая мажорная линия, базис PHP 8.4+/Laravel 12+;
bootstrapper'ы исполняются строго в порядке конфига и откатываются в обратном, поэтому
зависящий от tenant-соединения bootstrapper обязан идти после database-bootstrapper'а;
bootstrapper — singleton с состоянием, обязанный сохранить и восстановить центральное
состояние в `revert()`. Очередной `QueueTenancyBootstrapper` кладёт ключ tenant'а в payload и
инициализирует контекст перед джобом, возвращая предыдущий после — это устраняет утечку
контекста между джобами v3-образца. Таблица `jobs` обязана жить в центральной БД; при Redis
tenancy очередь — на непрефиксованном соединении; payload — скаляры; нельзя использовать
Eloquent-модель, возвращённую из `$tenant->run()`, после выхода из контекста.

**Источник:** v4.tenancyforlaravel.com (changelog, bootstrappers, queue, multi-database).
**Где используется:** P4 (worker/Octane reset proof), P9 (порядок bootstrapper'ов).
