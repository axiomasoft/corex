## Phase Context

После P02–P04 static `Config` в `src` почти не используется: из 134 ссылок 132 — миграции, тесты и скрипты.
Реальный долг другой: Options пересобираются на каждый `make()`; 11 из 16 пакетов с config читают массив по
ключам; 4 runtime-класса получают config repository; 37 файлов с фасадами и 255 вызовов глобальных хелперов
лежат вне моста; providers ядра и operations держат по 20–29 биндингов и анонимные классы с логикой;
lifetime-гейт не видит биндингов в registrars.
Фаза переводит конфигурацию на «прочитать один раз → проверить форму при boot → проверить runtime-требования до
приёма работы → инъектировать значения», а композицию — на «публичный provider → registrars → фабрики из одного
`return`» с проверяемым временем жизни. Числа — ориентир покрытия; приёмка — нулевые выходы гейтов.

## Pitfalls

- Options в `register()` через `instance()` теряет `defineEnvironment` и host-config (E1).
- Проверка наличия секрета в `fromArray` ломает сборку образа; при первом использовании — слишком поздно (E9).
- `mergeConfigFrom` не сливает вложенные ключи: дефолты — в `fromArray` (E4).
- Порядок registrars значим для `extend` и `bindIf`.
- Замена `DB::` на захваченный `ConnectionInterface` — запись в базу чужого tenant (E6).
- Конструкторная инъекция вместо `app()` меняет время жизни: singleton не держит scoped (L2).
- Baseline `runtime-globals` — только `Impersonation/**`; allowlist lifetime-гейта пуст; расширять их нельзя.
- Golden baseline меняется только через reviewed semantic delta; слой routes неизменен.
- Локальный GREEN при запущенной PostgreSQL не доказывает sqlite-лейн: sqlite-стек запускается как `test:hermetic` (D74 п.5).
