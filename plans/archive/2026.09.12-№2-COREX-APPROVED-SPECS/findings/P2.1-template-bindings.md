## 3. Build, seal and lock protocol proposal

1. Resolve independently approved expected manifest target and immutable template identity. Acquire an **exclusive session advisory lock on one dedicated non-pooled connection to the common root/coordination database**. All builder, verifier/clone, pool/activation, wave admission, mutation and retirement actors use this exact coordination endpoint and key derivation. A lock opened on golden/tenant/another cell DB does not coordinate them. Proposed key: first 8 SHA256 bytes of UTF-8 `corex-template-lock/v1\0` + approved logical deployment/cell/template UUID, interpreted signed big-endian int64; qualified test vectors and collision/identity serialization are required before implementation. Collision serializes extra work; one identity must never get two keys.
2. Builder writes building state only in its separately authorized build workflow, applies selected immutable migrations to a disposable PG16 DB, verifies catalogue against manifest and a clean pinned system/extension baseline, creates/signs/publishes the immutable manifest, seals privileges, re-reads catalogue/generation/permissions, records schema_hash and built_at and marks ready **last**. Manifest availability must precede ready visibility. Partial build or sidecar publication never yields trusted ready state; failed building rows remain non-ready. Source artifact immutability is independent of git_ref. Production implementation/build is outside this invocation.
3. Sealed database remains connectable **only by the qualified read-only verifier** (no ALLOW_CONNECTIONS toggle on failed verification). Consumer/application role has no CONNECT via PUBLIC, membership or ownership, and no object/schema/database mutation rights; library must not use that role for verifier. Dedicated build/maintenance principals and any superuser bypass are operator-controlled. A sealed generation is immutable; further mutation requires retirement under the same lock and a separately authorized new build/identity/generation, never in-place live mutation followed by a silent ready reset.
4. Admission under the lock verifies trusted manifest digest/signature/version/context/generation, ready state, expected==recorded==actual hash and privilege/seal invariant. Use consistent read-only golden catalogue snapshot; disconnect **the golden backend**, retaining the independent coordination backend throughout all dependent writes and physical clone. PostgreSQL disallows cloning a template with connected sessions and CREATE DATABASE outside a transaction is required: [PG16 CREATE DATABASE](https://www.postgresql.org/docs/16/sql-createdatabase.html). No failed verification may terminate other backends, change privileges, retire/quarantine state or perform DDL. Read/lock queries alone are permitted.
5. Before clone, save/claim/status/domain/event/count/wave writes, revalidate root row/context under lock. Hold coordination session until dependent transaction commits and all clone grants/ownership writes finish. Async enqueue is a boundary: hold through enqueue, then queued job independently reopens verification/lock with the same approved immutable target, including the existing-DB no-op branch. It must not trust serialized model contents or fresh mutable global configuration. If target drifts, deny before any new writes; previous legitimate enqueue/params writes cannot retrospectively be called zero-write.
6. Use deterministic lock order: template identities in UTF-8 byte order, then account/batch/root-row locks. For SKIP LOCKED pool selection, read a tentative candidate without writes, acquire its template lock, lock/re-read candidate and verify all identity/context/cleanup predicates before claim; retry a changed candidate without mutation. Empty pool fallback is verified before Account::create. Claim cleanup-marked or stale-schema pool entries must be denied. A pool DB's actual schema/embedding/context is checked before activation; current golden proof alone cannot certify an existing shell.
7. Unlock/disconnect in finally, disable reconnect/transaction pooling on coordination session; verify held connection identity through work. Loss/timeout is admission failure and stops further dependent writes. Current account-operation and per-tenant DDL locks are distinct and insufficient. Lock cannot make cross-connection PostgreSQL actions atomic or undo writes preceding a runtime failure; acceptance distinguishes a rejected initial verifier (zero writes) from interrupted work requiring explicitly scoped recovery. Consumer must prove its sealed-generation operator invariant and lock-loss behavior; cooperative advisory locks cannot restrain a superuser or rogue privileged actor. Missing capability proof remains NO-GO.

Advisory locks are database-local and session locks last until release/session termination: [PG16 pg_locks](https://www.postgresql.org/docs/16/view-pg-locks.html), [PG16 explicit locking](https://www.postgresql.org/docs/16/explicit-locking.html). These primary-source constraints informed the proposed topology; no live topology is asserted.

Wave: authenticate immutable target sidecar before runBatch's **first** status save, targetAccountStates creation/bulk update and per-account migrating status. Recheck per-account/source expectations and target identity before migrations, then verify actual resulting schema before current_version/status=ok writes. Admission failure does not save running/failed/blocked/quarantine or emit events. A migration error after valid admission may write an explicitly defined failure result under the retained target lock; separate it from rejected-verifier zero-write evidence. New target creates new wave; storage outside root DB columns is qualified separately.
