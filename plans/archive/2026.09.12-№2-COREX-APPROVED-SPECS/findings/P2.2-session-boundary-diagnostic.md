# P2.2 — Session-boundary diagnostic

**Status:** corrected; diagnostic record, not an execution qualification.

## Incident

The P2.2 execution session temporarily changed P2.3 write-path consumers
(clone, provisioning, pending-pool, lifecycle, migration-wave, and queued-job
paths). It also attempted to hand off P2.3 before P2.2 had execution evidence.
That violated the one-session/one-plan-item rule.

## Evidence

- The combined admission for `P2.2,P2.3` returns `BATCH_STALE` because P2.2
  has no execution evidence; P2.2 alone is admissible.
- `plan-lint.py` initially reported the generated P2.2/P2.3 bundles stale and
  P2 still carrying unresolved `[NEEDS CLARIFICATION]` gates. P2.2's bundle
  was regenerated and byte-fresh; P2.3 remains intentionally untouched by
  this one-item session.
- The temporary changes were removed from every P2.3 write-path consumer.
  A source scan for `TemplateIntegrityVerifier`, `templateIntegrity`,
  `assertCurrent`, and `assertAccount` across those consumers is empty.

## Cause

The recommended B2 grouping was treated as permission to implement both
items, instead of as scheduling advice subject to item admission and the
explicit P2.3 dependency on P2.2 execution evidence.

## Repair and prevention

- P2.3 consumer changes and P2.3-only tests/evidence were removed.
- P2.2 retains only the integrity-core migration, canonical catalogue hash,
  signed-manifest verifier, lock, fail-closed configuration, and P2.2 tests.
- Before any code change, run admission for both the requested item and its
  proposed combined batch. A non-`ALLOW` combined result means execute only
  the admitted item.
- Do not emit a next-session handoff for a current item that has not reached
  its own valid terminal state.

## Remaining owner gate

This correction does not qualify a live template, signing-key distribution,
or operator privilege. The declared `TEMPLATE-SCHEMA` and `TEMPLATE-SEAL`
qualifications remain required before the plan item may receive a terminal
plan state.
