**Code Guidance:** 1. Предложить отдельный additive ALTER: schema_hash varchar(64) NULL и named CHECK, принимающий NULL либо ровно 64 lowercase hex символа. Существующие rows остаются NULL/untrusted; нет default, fake hash или backfill из git_ref. Формат определяется подписанным manifest, не длиной строки.
2. Формат v1: имена schema/table/object сортируются по UTF-8 bytes, columns по ordinal position. Включить type/nullability/default, PK/FK/check, indexes/predicates/opclasses, semantic sequence parameters, extension names/versions, selected module set, embedding model/dim. Исключить database name/owner/ACL/OID/timestamps/rows/environment paths и mutable sequence values. Выражения — только versioned PG16 catalogue deparser; произвольное whitespace stripping запрещено. Canonical JSON: sorted keys, compact UTF-8, explicit scalar encoding, no duplicate keys; SHA256 lowercase64. Unknown objects/versions fail closed.
3. Manifest содержит format_version/template_version/canonical_schema_sha256, migration/module source refs, serializer/tool digest, PG/extensions, embedding metadata, seal generation, manifest digest/signature и trusted key identity. Provenance refs не входят в semantic schema hash, но связаны подписью manifest. Неподписанный/неизвестный manifest не допускается.
4. Consumer builder применяет точные migrations в disposable PG16, сверяет catalogue, seal generation и manifest, записывает hash/built_at и выставляет ready последним. Read-only verifier закрывает golden DB backend до clone. Общий session advisory lock по стабильной template identity удерживается от verify до всех зависимых writes; builder/mutation/retirement используют тот же lock. Root row lock не защищает от независимого cross-DB DDL.
5. App role не имеет CONNECT/mutation прав на golden DB; verifier имеет только квалифицированное catalogue чтение. Протокол seal не должен требовать DDL ради неуспешной verification. Суперпользовательский bypass покрывается operator permissions/invariant, не фиктивной гарантией library. Все identities/permissions/storage/key bindings фиксируются до adoption.
6. Wave target — immutable manifest sidecar по batch identity, без новых root columns. Изменение target создаёт новую wave; exact sidecar storage/trust/lock входит в qualification. Approval относится к конкретному hash amendment и manifest protocol; более широкий DDL отдельно. Live rebuild/backfill/remediation не включены.
7. Подготовить exact old/new source hashes, SQL/check/rollback, format test vectors, seam/earliest-write map и scoped owner review packet. Concrete amendment approval записать новым owner D#, не приписывать D14 разрешение на DDL.

**Validation:** V-AMENDMENT: exact nullable64/check/upgrade/backfill/down candidate с source hash, конкретное approval pending. V-CANON: equivalent catalogue vectors дают одинаковые bytes/hash, changed type/index/check — разные; provenance refs отдельно связаны manifest. V-SEAMS: перечислены account create, params save, pool claim, activation status/domain/event, clone job и wave status writes. V-AUTHORITY: каждый незаполненный operator/key/permission/sidecar input явно указан; отсутствующий input не считается GREEN adoption. V-BOUNDARY: нулевая product/Brain/DDL/external delta.
