## 3. Durable generation, local epoch, serialization and clock proposal

These are exact **logical records and transitions**, not DDL. Physical table/column/store names, migration/backfill/downtime/retention and schema version are **UNFILLED** under DI-20/26/34; do not append columns to frozen migrations. Existing root_identity_accounts migration only stores status/sync_status/timestamps and cascades deletion: it cannot itself prove durable membership or revoke history. User/session schema JSON payload availability alone is not approval for new semantic metadata.

Central record keyed (identityId,accountId): revision R, revokeGeneration G, state, membershipId/tombstone, last commitRef. Every committed membership transition increments R. Every newly committed revoke transition increments G, including revoke while already nonactive if accepted as a new revoke operation; replay of the same idempotency key increments neither. Regrant increments R and preserves G. Deletes/account teardown preserve a durable pair fence/tombstone before removing referential rows. Revoke and its G/R/state/notification intent/idempotency receipt commit atomically at the sole central writer. Notification dispatcher retries stable eventId/commitRef with a freshly signed300s envelope, current signing key and fresh deliveryId. Consumer durable inbox first validates authenticity then stores event identity+digest+pending refresh/cleanup; ack only durable admission, not fabricated apply success; failed refresh remains pending and reconciliation does not depend on inbox delivery.

Authoritative read proposes a consistent primary SELECT after read admission in a fresh transaction/statement snapshot, not a transaction snapshot opened before the defined read-start. Snapshot includes state/R/G/IDs from the same commit view. PostgreSQL READ COMMITTED statement visibility is a mechanism, not proof of replicated failover consistency. Failover routing must reject a primary that lost previously acknowledged commits. Replica/cache/304 are disallowed. Revision increases without decreasing G; equal R must have identical authority content, excluding request ID/audit read time. R regression, G regression, equal-R content conflict, or higher G with nonadvancing R gives deny+protocol alarm, never MAX() plus boolean trust. A new read with same R/G may renew only from its new local t0.

Tenant logical pair record: highest applied R/G, localEpoch E, durable operationFence F, committedApplicationFence AF, serial owner operationId/deadline, deny flag, cleanupTarget (G,E), cleanupCompleted (G,E), live user binding. E/F do not reset on regrant, process restart, delete/recreate or backup restore. E advances once when a newly detected local invalidation barrier is entered (lease expiry, time-domain loss, explicit local credential invalidation); repeats of that same pending barrier are idempotent. G advances only from verified central snapshot, never lease expiry or event body. Credential binding is (accountId,identityId,G,E), plus opaque credential ID and issued-after-cleanup issuance admission. R is projection ordering, not credential equality: ordinary nonrevoke updates/lease renewal must not log everyone out. F orders writers/operations, not ordinary session validity. AF records the last committed application accepted for a lease. A newly admitted refresh may bump F while the previously committed AF/lease remains usable until its original expiry; deny clears that lease/AF. Publication verifies its admitted F and writes AF atomically with its matching application.

Recommend durable serial owner/fencing in the same tenant transactional store as user/session fences: acquire a brief locked pair transaction, increment F, bind operationId/admission deadline; only one refresh owner per pair may issue a pull at a time. Pull runs outside the DB transaction, after durable admission and t0 capture. Owner spans pull/validation/apply/lease publication; other refreshes wait/coalesce within DI-24's actual read-start budget. Takeover after qualified owner death/deadline increments F, invalidating all old-holder applications/publications. Check F+operationId under locked pair row in every local apply. A cache mutex may reduce contention but is never the correctness fence. Exact deadline/lease-store semantics remain **UNFILLED**, not a Redis lock lifetime default.

Local expiry/deny has priority: it cannot queue behind an unbounded network pull. A short expiry transaction locks the pair, clears positive authorization, increments E for this barrier and F to cancel any previous positive apply/lease publication; pending refresh response with old F must abort and repull under a new admission. This does not admit a competing active refresh before takeover: all refresh/apply owners remain serialized. An old network request may still finish physically, but has no write authority. All compare-and-write boundaries are durable. Row lock hold/DB connection wait must fit FE-60; holding a DB row transaction over the entire5s pull+5s apply could already consume the5s expiry-admission budget and is not assumed safe.

Central G/R and local E/F require nonrollback durability through acknowledged failover and restore. Ordinary backup can roll counters and session payloads back together, resurrecting old credentials. Required restore protocol: keep admission closed, consult a separately nonrollback durable high-watermark/witness for all counter/fence namespaces, recover/reseed above every issued/committed watermark, invalidate restored credentials, complete cleanup and freshly pull before login. Never reset G with an invented deployment epoch; if exact witness/storage cannot prove nonreuse, restore qualification remains **UNFILLED** and cloud auth remains disabled. Counter exhaustion fails closed before increment, not wraparound. Fence/tombstone deletion requires proof no old sessions/recallers/callbacks/jobs/backups can reappear; absent such proof retention is indefinite logical requirement, physical policy **UNFILLED**.

Clock/lease logical format proposal: clockDomainId, processIncarnationId, t0Ticks, expiresTicks, pair/R/G/E/F and pull requestId. t0 is captured after admission immediately before outbound request; expiry=t0+45s, published only after matching fenced apply commit; no cached response, receipt time, central timestamp or JWT skew can extend it. Clock service supplies a conservative elapsed upper bound accounting for drift/error; effective permitted error/rate calibration is **UNFILLED**. If elapsed upper bound≥45s, deny at equality. PHP hrtime is monotonic but its arbitrary epoch/OS behavior is not proof of cross-host or suspend-safe expiration. Linux CLOCK_MONOTONIC stops on suspend; CLOCK_BOOTTIME includes suspend. Recommend qualified suspend-aware elapsed service scoped to one boot domain; cross-domain reader denies and requests a new pull. Process incarnation mismatch on restart invalidates old lease even if boot matches. Shared integer monotonic ticks from different hosts cannot be compared. An alternative shared qualified lease service needs explicit timing/loss proof, not a wall-clock DB expiry by default. No clock extension/library/install is selected by this proposal.

If clock-domain loss is discovered, immediate authorization deny precedes DB cleanup; durable E advance/cleanup retries on recovery, and fresh login stays closed until committed. A fresh active pull is not allowed to mask an uncommitted expiry barrier: admission/application checks whether the previous trusted lease already expired/lost its domain and performs the invalidation/cleanup first. Renewal started before expiry but committed afterward must honor this barrier and cannot revive prior credentials. Lease publication is a candidate bound to committed F/G/E; delayed cache publisher must never overwrite a newer pair state or count as fresh read.

## 4. Atomic final-write fencing proposal and proof

Recommend a consumer-registered **composition** of the session handler and authentication/provider integration, using supported driver/DI extension points; no monkey-patching and no inheritance from final CoreX concrete classes. Proposed package adapter file packages/tenancy/src/Session/FencedDatabaseSessionHandler.php implementing the deployed version's PHP SessionHandlerInterface, delegating serialization/anonymous storage only as qualified. Exact deployed interface signatures and driver registration remain DI-25/30; no PHP file is created here. Membership projection, credential metadata and authenticated session writes must use the same resolved tenant DB transaction/connection and locked pair fence. Cross-DB/cache fencing cannot be called atomic without a separate proven equivalent.

Trusted server-side request context retains credential binding captured at restoration/issuance; final writer never replaces old G/E with current G/E merely because is_active became true. User/account and credential ID must agree with authenticated payload and qualified guard names. Anonymous data cannot smuggle any guard login key, user_id, remember credential or claimed binding; demotion strips all auth state or rejects the save. All configured authenticated guards represented by a session are inspected, not just the container default guard.

Final save sequence (proposed transaction, not executable SQL):

1. Resolve trusted account→tenant connection; begin short transaction; lock persistent pair fence row for update (missing row is deny, never synthesize an active row). All writers acquire pair first, then user, then credential/session records in deterministic order.
2. Reload committed user active/not-deleted state, G/E, deny+cleanup status, verify exact original credential binding, and verify current conservative positive lease with its matching committed application fence. OperationFence is used to validate the lease application, not to reject valid credentials on a harmless refresh.
3. Within that same transaction perform authenticated session INSERT/UPDATE and durable credential metadata write; zero/ambiguous target or any failed comparison aborts. Do not catch transaction/deadlock failures and fall back to an unfenced stock INSERT. Bound retries by the remaining deadline; on denial remove queued auth/remember cookies and reject/demote authentication before response release. Driver returns failure/typed denial that the response adapter must handle explicitly; a boolean ignored by the framework is not proof.
4. Commit is final-write linearization point. Release authenticated cookie/response only after successful commit. A revoke/local-epoch transaction using the same pair lock either commits first (stale save fails), or follows this save (and deletes/invalidate it). Old cookie arriving late after a correctly committed earlier issuance remains harmless because generation/epoch restoration denies it.

Revocation/local expiry transaction locks the same pair row, enters deny, records G (only authoritative)/increments E (local barrier as applicable), bumps F to reject older positive operations, disables users.is_active, invalidates remember registrations, deletes account-local invalid-generation sessions and records cleanup completion. Recommend deleting all this pair's sessions while login is blocked; no fresh-generation credentials may exist before cleanup. If cleanup is too large for one bounded transaction, durable deny+cleanup target commits first; cleanup batches idempotently delete through the target, regrant/login stay blocked, final completion is separately locked+committed. This two-stage path is not atomic physical cleanup and needs its own≤10s FE-60 proof. It never relies on cross-store transaction magic.

Remember-enabled consumer: durable credential registration binds opaque hashed token/credential ID to G/E, and issuance/rotation provider write executes the same locked comparison+write transaction. Recaller restoration verifies existing binding and live lease before session issuance. Late queued cookie cannot establish current binding or replace a rotated token; every restore repeats checks. Consumer disabling remember must reject all old recallers, prohibit every guard's issuance and strip already queued cookies; optional PrincipalUserProvider alone is insufficient deployment proof. Neither mode adds remember_token to frozen cloud schema by inference.

Fresh login/OIDC callback records an issuance attempt binding before/with authentication evidence; after cleanup it must recapture fresh authentication and current G/E, not relabel a pre-revoke callback. Validate nonce/PKCE/state/issuer separately; none is membership. Local cloud password login, Fortify two-factor continuation, loginUsingId/login/once/setUser, impersonation, PAT/OAuth mint/refresh and session regeneration need equivalent issuance/decision fences. Cleanup completion and new active pull permit new credentials; regrant never restores any old row/recaller/principal. Final profile hydration writes cannot modify is_active, E/G, or bypass the barrier.

The pair transaction proves the late-delete/reinsert race under PostgreSQL row locking only when **every** writer uses it. It does not freeze central membership for a whole request or retract business effects authorized earlier. The bound applies to each new decision and durable credential writes. Long jobs/websocket messages recheck at each later decision; any stronger business final-write requirement needs its own consumer transaction fence.

## Обсуждение

Recommend the above same-tenant transactional pair fence, durable central G/local E, priority expiry invalidation and composition of consumer session/provider extensions.
