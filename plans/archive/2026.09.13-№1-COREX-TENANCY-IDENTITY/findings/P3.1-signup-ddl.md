## 3. JSON and key semantics proposed for approval

| JSON member | Stored type and invariant |
|:--|:--|
| `signup_key` | JSON string; exact opaque key, globally unique among predicate-matching rows in this root DB |
| `signup_request_digest` | JSON string; 64 lowercase hex SHA-256, supplied canonical immutable request digest |
| `signup_cluster_id` | JSON string; canonical lowercase UUID, equal to reserved account cluster |
| `signup_template_id` | JSON string; canonical lowercase UUID of qualified template; persist identity in addition to existing integer template_version |

Key-policy identifier **ascii-token-128-v1**: accept `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$` using an ASCII/full-string matcher; 1–128 bytes. No trimming, case folding, Unicode normalization or implicit casting. Reject whitespace/control/NUL, empty, non-string and oversized values before any claim write. This narrows P1.2's opaque ASCII candidate and requires exact API/schema owner acceptance. Central must supply an already namespaced opaque key if multiple products share root DB; L0 does not derive keys from emails, roles or checkout policies. The key is an idempotency identifier, never a bearer credential; redact it from ordinary logs.

The exact B33 index has **no** type/length/nonempty constraint: `->>` extracts non-string scalar/object JSON as text, JSON null/missing is SQL NULL, empty string is indexed; multiple missing/null keys are permitted. Its predicate is not changed to exclude invalid keys, since that would silently allow invalid-key duplicates. Only approved Action writers may establish bindings; deployment inventory must resolve existing invalid/partial bindings before admission. Direct SQL can violate these JSON invariants; this index alone is not input validation. Additional CHECKs/triggers would require another explicit delta.

Byte-distinct case-sensitive keys require the deployed expression collation to preserve their distinctness. Inspect and qualify actual database/expression collation and compare `Key:A`/`key:a` in the isolated PG16 fixture. No collation override is added to the exact candidate; a deployment using incompatible/nondeterministic equality must revise the candidate or key policy before approval. Digest and explicit cluster/template members are compared on replay, never advisory-lock hashes alone.

**Tombstone policy proposed: retain-deny-v1.** Compensation never clears or transfers a committed binding. Lookup includes soft-deleted rows and status=`deleted`; encountering either denies new claim and returns no usable provisioning success. A live matching row returns its original accountId; mismatched digest/cluster/template rejects. A row with `status='deleted'` but `deleted_at IS NULL` still participates in the index; a soft-deleted row does not. The partial index permits physical key reuse after soft delete; retain-deny is Action/caller policy, not cross-tombstone DB enforcement. Restoration can collide if an out-of-protocol writer reused the key and must fail, never merge accounts. Physical purge loses the binding: P6.25 must approve an authoritative durable dedup record/retention covering replay lifetime before purge. Strict forever-unique keys would require a different index/storage delta, not this SQL.

Central owner must explicitly accept retain-deny, replay/purge retention and restoration policy, or supply a replacement candidate with a key generation/epoch and durable routing protocol. Unknown policy is fail-closed for P3.2; no implied key release after rollback, compensation, soft delete or purge.

## 4. Read-only collision and tombstone inventory method

No production/root connection was opened and no counts are asserted. Schema operator runs this method against an approved snapshot or approved read-only root connection before rollout, records environment/source schema SHA and row counts, and returns redacted remediation decisions. Short REPEATABLE READ READ ONLY transaction makes counts consistent; it does not protect the subsequent build from new writers. Drain or constrain writers before the final recheck/build.

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;
-- Exact build-blocking collisions, including status='deleted' with no soft delete.
SELECT data->>'signup_key' AS signup_key, count(*) AS rows
FROM root_accounts
WHERE data->>'signup_key' IS NOT NULL AND deleted_at IS NULL
GROUP BY data->>'signup_key' HAVING count(*) > 1;
-- Tombstone/history ambiguity; include all rows for the retain-deny decision.
SELECT data->>'signup_key' AS signup_key, count(*) AS rows,
       count(*) FILTER (WHERE deleted_at IS NOT NULL OR status = 'deleted') AS tombstones
FROM root_accounts WHERE data->>'signup_key' IS NOT NULL
GROUP BY data->>'signup_key'
HAVING count(*) > 1 OR bool_or(deleted_at IS NOT NULL OR status = 'deleted');
-- Invalid keys that the exact index would otherwise index as text.
SELECT id, deleted_at, status
FROM root_accounts WHERE data ? 'signup_key'
  AND (jsonb_typeof(data->'signup_key') IS DISTINCT FROM 'string'
       OR octet_length(data->>'signup_key') NOT BETWEEN 1 AND 128
       OR (data->>'signup_key') COLLATE "C" !~ '^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$');
-- Orphan binding members require remediation even when key is NULL/missing.
SELECT id FROM root_accounts
WHERE data->>'signup_key' IS NULL
  AND (data ? 'signup_request_digest' OR data ? 'signup_cluster_id' OR data ? 'signup_template_id');
COMMIT;
```

For each non-null key, the operator also checks JSON member types, digest 64-hex format, UUID canonical form, cluster equality, and approved template identity/version linkage using the approved schema's real template mapping; missing/incompatible linkage is not invented from a guessed FK. Check both deleted and nondeleted rows. Report index-name/definition collisions with `pg_get_indexdef`, validity with `pg_index`, exact root schema, collation and concurrent writers. No raw keys or owner data in a public receipt.

**Backfill proposal: none.** Do not invent keys for historical accounts, select a “winner”, delete duplicates or rewrite digests. Keyless existing rows retain ordinary lifecycle semantics. Invalid/duplicate/partial historical bindings block adoption until the schema and central owners approve per-class remediation; remediation gets its own exact data delta and rollback. Empty result counts and matching catalog checks must be measured, not assumed.
