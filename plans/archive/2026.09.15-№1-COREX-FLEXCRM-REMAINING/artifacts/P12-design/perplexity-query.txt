--- Q1 : optional-driver ---
PHP Composer library: correct way to handle an OPTIONAL driver dependency — "suggest" section
plus class_exists() guard plus fail-closed configuration exception. Is it bad practice for a
service provider to silently bind a null/unsupported implementation when configuration is
invalid? Best practice for two service providers competing for the same container binding,
and how a driver manager registry avoids provider load-order dependence.

--- Q2 : rename ---
Renaming a PHP Composer package and its PSR-4 namespace before 1.0.0 stable release: hard
rename vs composer "replace" key vs class_alias bridge. What exactly does the composer
"replace" field do and does it help PHP namespace backward compatibility? Recommended
migration steps and what breaks for consumers.

--- Q3 : typed-config ---
Laravel package design: why should a reusable package read configuration ONCE into a typed
immutable value object injected via constructor instead of calling the global config() helper
inside repositories, storage engines and domain services? Benefits for Octane, testability and
validation. Also best practice for configurable database table names / table prefix in a
library package (typed table-map object resolved in the service provider).

--- Q4 : closure-boundary ---
PHP Laravel: why must a Closure never be stored in a data-transfer/context object that crosses
a queue job or workflow boundary? What exactly happens on serialization (Serialization of
'Closure' is not allowed), what laravel/serializable-closure does and why it is not a
substitute for an explicit authorization policy interface returning a decision object.
