A Closure should not be part of any DTO/context that crosses a queue, delayed job, event bus, or durable-workflow boundary because that boundary must carry data, not a live piece of PHP runtime behavior. A closure is executable code plus lexical/environment state; it is not a stable, versioned, inspectable domain fact.
PHP itself rejects native closure serialization, so a normal queued job containing one eventually fails with:
```
Serialization of 'Closure' is not allowed
```
PHP’s serialize() creates a byte-stream representation intended to preserve a value’s type and structure for later restoration, but native Closure objects are explicitly not serializable.

## What fails in Laravel

Consider a context object:
```
final readonly class ImportContext { public function __construct( public int $actorId, public int $schoolId, public Closure $canImport, ) {} }
```
It may appear to work during a normal HTTP request:
```
$context = new ImportContext( actorId: auth()->id(), schoolId: $school->id, canImport: fn () => auth()->user()->can('import', $school), );
```
But as soon as it becomes part of a queue payload:
```
RunImport::dispatch($context);
```
Laravel must persist the job so another process—possibly another container, host, deployment, or a worker running minutes later—can reconstruct it. Queue backends such as database, Redis, SQS, and Beanstalkd require a transportable payload; Laravel describes queues precisely as a mechanism for background processing through such backends.
The relevant lifecycle is roughly:
```
HTTP process → construct job + context → serialize payload → write payload to Redis / database / SQS → process ends Later, potentially elsewhere → worker reads payload → unserialize / hydrate job → invoke handle()
```
When PHP recursively serializes the job properties, it reaches the closure in ImportContext::$canImport. Native PHP has no general, safe representation for:
- the anonymous function’s source and lexical scope;
- values captured via use (...);
- a bound $this object;
- static variables;
- the exact class definitions, file versions, autoloader behavior, and loaded extensions needed to reproduce it;
- process-local dependencies such as request state, authenticated user, container instances, DB connections, file descriptors, sockets, streams, locks, or service clients.
So serialization stops rather than silently producing a misleading or non-restorable payload. PHP’s documentation also notes that many objects cannot be serialized unless they explicitly support serialization hooks; for closures specifically, the documented result is the Serialization of 'Closure' is not allowed exception.

## Why “it works on sync” proves nothing

This is a common trap:
```
RunImport::dispatchSync($context);
```
A synchronous dispatch runs in the current process, so it may never need to cross a durable persistence boundary. Laravel documents that dispatchSync executes immediately in the current process rather than being queued.
Therefore:
```
QUEUE_CONNECTION=sync
```
can hide a design defect that immediately appears after moving to Redis, database, SQS, a job batch/chain, retry, Horizon worker, or a workflow engine.
The stronger rule is:
If an object could ever be persisted and resumed, model it as a durable message: identifiers, scalar values, arrays/maps of durable values, enums, timestamps, versioned commands, and explicit result/decision records.
This rule also protects you from bugs that do not manifest as a serialization exception:
- Retry drift: a retry runs later under a different permission state.
- Deployment drift: code behind the closure changes between enqueue and execution.
- Identity drift: a closure captured a stale user/model/request object.
- Authorization bypass: a decision made in one security context is accidentally reused in another.
- Audit failure: you cannot answer which policy or rule led to an allow/deny result.
- Replay failure: an old durable workflow cannot reliably reproduce implicit code behavior.
- Test opacity: assertions must execute hidden behavior instead of inspecting a message and decision.

## What laravel/serializable-closure actually does

Laravel does support closures in certain framework-level features. For example, its queue APIs support chained closures, and Laravel has a CallQueuedClosure job type whose closure property is a SerializableClosure.
The laravel/serializable-closure package is Laravel’s fork of opis/closure 3.x. It wraps a closure in a serializable object and provides __serialize() / __unserialize() behavior so the wrapper can later restore a callable closure. Laravel’s own README illustrates the process:
```
use Laravel\SerializableClosure\SerializableClosure; SerializableClosure::setSecretKey('secret'); $serialized = serialize( new SerializableClosure(fn () => 'james') ); $closure = unserialize($serialized)->getClosure(); echo $closure(); // james
```
The package also recommends configuring a secret key.
Conceptually, it is a closure transport/reconstruction mechanism. It does not turn an arbitrary closure into a durable domain policy or a stable security decision. It gives Laravel a pragmatic way to support ergonomic APIs—such as queued callbacks and closure-based job chains—where Laravel owns the serialization and invocation semantics.
It also has explicit technical limitations. Its README lists, among others:
- anonymous classes cannot be created inside such closures;
- attributes cannot be used inside them;
- serializing closures in REPL environments such as Tinker is unsupported;
- closures referencing objects with readonly properties are unsupported.
Those caveats alone should rule it out as a foundational workflow/context format.

## Why it is not authorization

A serializable closure answers:
“Can we attempt to reconstruct and invoke this callback later?”
An authorization policy answers:
“Given the current authoritative facts, is this operation permitted—and why?”
Those are fundamentally different abstractions.
A secret key in SerializableClosure is important for the package’s payload integrity/security model, but it is not an authorization mechanism. A signed payload can establish that the callback data was not modified by an unauthorized party; it cannot establish that the actor may perform the action now, that the resource still belongs to the same tenant, that the account is still active, or that the policy has not changed.

## The correct shape

Keep command/context, policy, and decision separate.

## 1. Persist only durable context

```
final readonly class ImportStudentsCommand { public function __construct( public string $operationId, public int $actorId, public int $tenantId, public int $schoolId, public string $sourceFileId, public int $requestedAtUnix, public int $schemaVersion = 1, ) {} }
```
No closures, no Request, no Auth facade result objects, no service/container instances, no open Eloquent builders, no PDO connections, and ideally no entire hydrated object graph.
Laravel itself follows the “small durable reference” pattern for queued Eloquent models: when a model is sent with a queueable job, Laravel serializes its identifier and retrieves the full model when the job runs. For business workflows, explicit IDs are often even clearer because tenant scope, missing-resource behavior, lock strategy, and reauthorization are then visible in your code.

## 2. Make policy an injected executable dependency

```
interface ImportStudentsAuthorizationPolicy { public function decide( ImportStudentsCommand $command, Actor $actor, School $school, ): AuthorizationDecision; }
```
```
final readonly class AuthorizationDecision { public function __construct( public bool $allowed, public string $code, public string $policyVersion, public array $metadata = [], ) {} public static function allow( string $code, string $policyVersion, array $metadata = [], ): self { return new self(true, $code, $policyVersion, $metadata); } public static function deny( string $code, string $policyVersion, array $metadata = [], ): self { return new self(false, $code, $policyVersion, $metadata); } }
```
The interface itself never crosses the boundary. The worker resolves its implementation from Laravel’s container in handle().

## 3. Rehydrate facts and decide at execution

```
final class RunStudentImport implements ShouldQueue { use Queueable; public function __construct( public ImportStudentsCommand $command, ) {} public function handle( ImportStudentsAuthorizationPolicy $policy, ImportService $imports, ): void { $actor = Actor::query() ->whereKey($this->command->actorId) ->where('tenant_id', $this->command->tenantId) ->firstOrFail(); $school = School::query() ->whereKey($this->command->schoolId) ->where('tenant_id', $this->command->tenantId) ->firstOrFail(); $decision = $policy->decide( $this->command, $actor, $school, ); if (! $decision->allowed) { ImportAudit::recordDenied( operationId: $this->command->operationId, actorId: $this->command->actorId, schoolId: $this->command->schoolId, code: $decision->code, policyVersion: $decision->policyVersion, ); return; // or throw a domain exception } $imports->run($this->command); } }
```
This makes authorization a deliberate execution-time concern. If the user was disabled, their membership was revoked, the tenant changed, or the school was archived while the job waited in Redis, the worker sees that current state.

## When should a decision be persisted?

There are two valid patterns; choose deliberately.

## Re-authorize at execution time

Use this for most queued commands that cause side effects:
```
request authorizes intent → durable command is queued → worker reloads authoritative state → worker authorizes execution → worker performs side effect
```
This avoids a time-of-check/time-of-use gap. It is the right default for imports, tenant data access, sending messages, billing actions, provisioning, and destructive changes.

## Persist an explicit authorization grant or decision

Use this only when the business rule genuinely says that approval at time T0 remains valid for a defined window or workflow stage—for example, a signed approval, a finance approval, or a teacher’s approved export request.
Then persist a data record, not a callback:
```
final readonly class AuthorizationGrant { public function __construct( public string $grantId, public string $operationId, public int $actorId, public string $action, public string $resourceType, public string $resourceId, public string $policyVersion, public string $factsHash, public int $issuedAtUnix, public int $expiresAtUnix, ) {} }
```
At execution, validate it:
- Was it issued by the expected policy/version?
- Is it unexpired?
- Does it match the exact operation, tenant, actor, and resource?
- Have revocation conditions occurred?
- Does the current resource version still match the approved facts hash?
- Is the command idempotency key the same?
That creates an auditable, reviewable business artifact. A serialized closure cannot provide that contract.

## Practical boundary rule

Treat a queue/workflow payload as if it will be:
- written to durable storage;
- inspected in Horizon or incident tooling;
- retried several times;
- processed after a deployment;
- executed on a different host;
- replayed months later; and
- reviewed by security or compliance staff.
If a field fails that thought experiment, do not put it in the context object.
A compact rule for Laravel code review:
```
Crossing a durable boundary: - Serialize commands, facts, identifiers, and versions. - Resolve services, policies, and callbacks on the executing side. - Return/persist explicit decisions and outcomes. - Never serialize authority or behavior as hidden captured code.
```
Laravel’s closure serialization support is useful for framework-managed convenience features. It is not a substitute for an explicit policy interface because transportability of executable code does not provide authorization semantics, current-state validation, audit evidence, stable versioning, or durable workflow correctness.
