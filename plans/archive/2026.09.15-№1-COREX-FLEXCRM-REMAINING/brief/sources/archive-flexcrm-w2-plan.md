## 1. Context

Дизайн-программа Flex (plans/flex, Этапы 0–8) завершена: B-10..B-26 покрывают ядро,
tenancy, workflow-движок, CRM-домен (воронки, лиды/сделки, задачи-базис `tsk_`,
timeline, MCP v1), commerce, атрибуты, спутники Vaulter/Chatom, inbox, editions.
Волна 2 закрывает продуктовые гапы против Битрикс24 / amoCRM / HubSpot (см. D2).
**Это план ПРОЕКТИРОВАНИЯ, не исполнения**: цель — многослойная детальная проработка
(решение пользователя D8/D9): сначала research по гапу, затем blueprint-драфт с
ключевыми решениями, затем отдельные аспектные deep-dive проходы по ВСЕМ модулям
волны сразу — БД-срез, процессы-срез, контракты/MCP-срез, права-срез, НФТ/лимиты-срез.
База данных и процессы принципиально не проектируются «за один заход» — каждый аспект
получает собственный проход с собственным фокусом. Запись в реальный vault (P5) —
отдельный этап, стартует только по явной команде пользователя. Новые артефакты живут
в `plans/flex/` (R-24+, B-27+, T-050+); этот план — управляющий контур волны.

## 2. Execution Rules

### Cold-start протокол (D10) — каждый item = свежая сессия

Пользователь сбрасывает контекст перед КАЖДЫМ item'ом. Запуск:

1. `/clear`
2. `/model claude-fable-5` (фазы P1–P4) · sonnet (фаза P5)
3. `/task:plan-exec FLEXCRM-W2 Pn.m` — Pn.m берётся из **Next** в `handoff.md`

Sonnet-пин текста команды /task:plan-exec переопределён Routing §3 этого плана:
модель уже выбрана на шаге 2, исполнитель её НЕ переключает. Порядок чтения при
холодном старте — строго протокольный: plan.md → handoff.md → phases/Pn.md
(Phase Context + свой item) → Required Reads item'а по списку. **Ни один item не
полагается на память предыдущей сессии**: всё межitem'ное состояние живёт в файлах —
спеки B-2X (правятся по месту), реестры открытых вопросов внутри спек, срезовые
логи `slices/S*.md`, `handoff.md`. Если для работы не хватает контекста, которого
нет в Required Reads, — это дефект плана: эскалация, не самодеятельный поиск по репо.

### Общие правила

- **Фазы P1–P4 — чистое проектирование** (артефакты в `plans/`); **P5 — исполнение в реальный vault**, стартует ТОЛЬКО по отдельной команде пользователя.
- Один item за раз; статус обновляется В ПЛАНЕ (Phase Status + Status Board здесь) до завершения работы.
- Статусы — 6 канонических строк байт-в-байт (⬜ Not started · 🟡 In progress · 🟢 Done · 🟠 Done with deviations · 🔴 Blocked · ⛔ Skipped by decision).
- План разошёлся с канонами plans/flex или vault — не импровизировать, эскалировать (Escalation Needed + 🔴).
- После закрытия item/фазы — перезаписать `plans/FLEXCRM-W2/handoff.md` целиком.
- Все research-факты — только через RAG (`.ai/guidelines/perplexity-mcp.md`, mcp perplexity-web); без источника → пометка `[UNVERIFIED]`.
- Зафиксированные решения программы (00_MASTER_PLAN §3, D1–D17 + чекпойнты D-001..D-005) НЕ пересматривать.
- Открытые вопросы КАЖДОГО артефакта волны собираются в его секции и наследуются вниз по слоям: R-отчёт → blueprint-драфт §9 → соответствующий deep-dive срез P3 обязан их явно закрыть или эскалировать. Молча потерять вопрос нельзя — P4.1 проверяет сквозной реестр.
- Wiki-ссылки в vault-документах — только `[[Имя файла]]` (`.ai/guidelines/obsidian.md`).
