## 3. Feature bundles и revenue motions (кратко — не BRD)

FlexCRM продаётся не по модулям, а по «мотивам» (jobs), которые упаковывают несколько engine-модулей + продуктовых расширений в один пользовательский сценарий.

| Motion | Кто | Engine-модули + расширения B-24 | Edition |
|---|---|---|---|
| **Sales** (воронка продаж, quote-to-cash v1) | Sales rep, sales manager | `crm_deals`+`crm_pipelines`+`crm_deal_items`+Quote-render (§4) + forecast_category (§4) | pro+ (base — только amount, без line items) |
| **Service/CS** (удержание, upsell, churn-раннее предупреждение) | CSM, account manager | `crm_companies` + `crm_account_health`/`crm_health_overrides` (§4) + activities/timeline | enterprise |
| **Ops/Inbox** (омниканальный приём, роутинг, дедуп до квалификации) | Оператор/SDR, диспетчер | `crm_conversations` (§6) → `crm_leads` → `crm_deals` | pro+ |
| **Delivery/Tasks** (исполнение обязательств после Won) | Исполнитель, project owner | `tsk_tasks`+`tsk_projects` (кросс-мотив, вне CRM-специфики) | все editions |
| **Vertical** (отраслевой пресет поверх любого мотива) | Владелец вертикального бизнеса | `vrt_*` installer + любой мотив выше | отдельная покупка (см. §5) |

Полный BRD/user stories по каждому мотиву — вне периметра этого блюпринта (`pm/brd.md` skill, отдельная задача); здесь — только архитектурная привязка мотив→модуль→edition.

## 4. Roadmap boundary — v1 / v1.1 / v2 (quote-to-cash, R-20 подтверждено)

### 4.1 v1 — Deal + line items + Quote-как-рендер (без Order/Contract в CRM-ядре)

Явно подтверждённый (R-20 §4.1) preliminary decision, зафиксирован без изменений:

```sql
-- Новая таблица (не JSONB на deal) — консистентно с конвенциями B-13 §2 (UUIDv7, minor units, ACTOR)
CREATE TABLE crm_deal_items (
  id            uuid PRIMARY KEY,
  deal_id       uuid NOT NULL REFERENCES crm_deals(id) ON DELETE CASCADE,
  product_ref   varchar(190),          -- handle каталога commerce, когда появится (B-14); до этого — свободный product_name
  product_name  varchar(255) NOT NULL, -- денорм на момент добавления (снапшот названия)
  qty           numeric(14,3) NOT NULL DEFAULT 1,
  unit_price    bigint NOT NULL,       -- minor units
  currency      char(3) NOT NULL,
  discount_pct    numeric(5,2),
  discount_amount bigint,
  position      int NOT NULL DEFAULT 0,
  created_by    jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(), updated_at timestamptz NOT NULL DEFAULT now(),
  deleted_at    timestamptz
);
CREATE INDEX crm_deal_items_deal_ix ON crm_deal_items (deal_id) WHERE deleted_at IS NULL;
COMMENT ON TABLE crm_deal_items IS
  'Типизированные строки товаров/услуг сделки (R-20 §2.4 урок HubSpot: свободный текст в line items — источник миграционной боли; здесь с первого дня строгие колонки, не JSONB-свалка)';

-- Ровно один Primary quote per deal — явная колонка (hot-path, не universal-relations кандидат, R-20 §5 в.2)
ALTER TABLE crm_deals ADD COLUMN primary_quote_doc_id uuid;  -- ссылка на сгенерированный документ (media, без FK — B-13 §2.4 паттерн crm_doc_templates.file_id)
```

Quote — не новая доменная сущность, а конкретизация существующего `crm_doc_templates` (B-13 §2.4): рендер `crm_deal_items` + `mapping jsonb` в docx/pdf. Один шаблон-код (`entity_type='crm.deal'`) с назначением «quote» помечается конвенцией кода (`code LIKE 'quote_%'`), явного нового поля не заводим в v1.

Forecast и account health — см. §4.2/§4.3 (перенесены сюда из R-20 без изменений по содержанию, только организационно сгруппированы с quote-to-cash под одну roadmap-границу v1).

### 4.2 Forecast category — read-model, без `ForecastingItem`-объекта (R-20 §4.2)

```sql
ALTER TABLE crm_deals ADD COLUMN forecast_category varchar(16)
  CHECK (forecast_category IN ('pipeline','best_case','commit','omitted'));
  -- NULL = вывести из crm_stages.probability по умолчанию (авто-маппинг)
ALTER TABLE crm_deals ADD COLUMN forecast_category_is_manual boolean NOT NULL DEFAULT false;
  -- true = ручной override менеджера переживает смену стадии

CREATE MATERIALIZED VIEW crm_forecast_rollup AS
SELECT workspace_id, owner_id, pipeline_id, date_trunc('month', close_date) AS period,
  COALESCE(forecast_category,
           CASE WHEN status='won' THEN 'closed'
                WHEN s.probability >= 80 THEN 'commit'
                WHEN s.probability >= 40 THEN 'best_case'
                ELSE 'pipeline' END) AS category,
  currency, sum(amount) AS amount_sum, count(*) AS deal_count
FROM crm_deals d JOIN crm_stages s ON s.id = d.stage_id
WHERE d.deleted_at IS NULL
GROUP BY workspace_id, owner_id, pipeline_id, period, category, currency;
```

**Refresh: event-driven** — `REFRESH MATERIALIZED VIEW CONCURRENTLY` по событиям `crm.deal.stage_changed`/`crm.deal.won`/`crm.deal.lost` (queued listener, тот же паттерн, что `crm_tml`-запись B-13 §5.3), не по cron — дешевле на средних объёмах (R-20 §4.2). Ролловер по manager/team — джойн с `sys_departments`/`aut_role_matrix` (B-11), отдельной таблицы иерархии не заводим.

### 4.3 Account health — read-model + override-таблица (R-20 §4.3)

```sql
CREATE TABLE crm_account_health (      -- append-only snapshot per company (как crm_stage_history)
  id            uuid PRIMARY KEY,
  company_id    uuid NOT NULL REFERENCES crm_companies(id) ON DELETE CASCADE,
  computed_at   timestamptz NOT NULL DEFAULT now(),
  score         smallint NOT NULL CHECK (score BETWEEN 0 AND 100),
  band          varchar(8) NOT NULL CHECK (band IN ('green','yellow','orange','red')),
  pillars       jsonb NOT NULL,        -- v1: {"engagement": N, "commercial": N} — 2 столпа, расширение до 4-5 требует нового домена (тикеты/NPS)
  trend_delta   smallint,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX crm_ah_company_ix ON crm_account_health (company_id, computed_at DESC);

CREATE TABLE crm_health_overrides (    -- ручные флаги CSM, переживают пересчёт
  id          uuid PRIMARY KEY,
  company_id  uuid NOT NULL REFERENCES crm_companies(id) ON DELETE CASCADE,
  reason_code varchar(32) NOT NULL,    -- 'sponsor_leaving','budget_freeze','exec_escalation', ...
  note        text,
  actor       jsonb NOT NULL,
  active      boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(), resolved_at timestamptz
);
```

**Refresh: nightly batch** (не event-driven — health не реагирует на единичное событие, это композит за период). v1: 2 столпа (engagement из `crm_activities`/`crm_tml`, commercial из billing/`com_payers`, R-17) — полный 4–5-столповый композит (+support/+sentiment) блокирован отсутствием доменов тикетов/NPS в программе Flex (см. §9).

## 6. Inbox / «Неразобранное» — `crm_conversations` (закрывает B-13 §9 п.1, канон R-21)

### 6.1 Решение

Подтверждена 3-слойная модель (HubSpot-паттерн, R-21 §2.4): **raw message → `crm_conversations` (routing + identity resolution) → `crm_leads` (qualification, уже канон B-13 §2.3) → `crm_deals` (уже канон)**. Routing и qualification НЕ смешиваются в одном объекте — прямое требование Т2 R-21, подтверждённое всеми тремя разобранными системами (HubSpot/Front/Intercom).

### 6.2 Сущность

```sql
CREATE TABLE crm_conversations (
  id               uuid PRIMARY KEY,                  -- UUIDv7
  workspace_id     uuid REFERENCES wsp_workspaces(id) ON DELETE CASCADE,
  channel          varchar(16) NOT NULL CHECK (channel IN ('email','chat','messenger','form','call','sms')),
  external_thread_id varchar(255),                    -- id треда в Chatom/канале-источнике (идемпотентность)
  status           varchar(16) NOT NULL DEFAULT 'unassigned'
                   CHECK (status IN ('unassigned','assigned','pending_review','linked','closed','spam')),
  assignee_id      uuid REFERENCES users(id),
  team_id          uuid,                              -- очередь/отдел-роутинг (sys_departments; иерархия не спроектирована в B-10/B-11, см. §9 п.8 ниже)
  contact_id       uuid REFERENCES crm_contacts(id) ON DELETE SET NULL,   -- резолвится sync/async-матчером
  match_confidence varchar(8) CHECK (match_confidence IN ('exact','fuzzy','none')),
  lead_id          uuid REFERENCES crm_leads(id) ON DELETE SET NULL,      -- заполняется conversation.convert_to_lead
  source_id        uuid REFERENCES crm_sources(id) ON DELETE SET NULL,
  first_message_at timestamptz NOT NULL,
  last_message_at  timestamptz NOT NULL,
  created_by       jsonb NOT NULL,                    -- ACTOR (обычно source:system, канальный адаптер)
  created_at timestamptz NOT NULL DEFAULT now(), updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE NULLS NOT DISTINCT (channel, external_thread_id)
);
CREATE INDEX crm_conv_queue_ix    ON crm_conversations (team_id, status) WHERE status IN ('unassigned','pending_review');
CREATE INDEX crm_conv_contact_ix  ON crm_conversations (contact_id) WHERE contact_id IS NOT NULL;
COMMENT ON TABLE crm_conversations IS
  'Слой routing (HubSpot Conversations Inbox / Front conversation паттерн). Не квалификация — только приём и
   идентити-резолюция. Сырые сообщения — в crm_tml с type=conversation_message (расширить CHECK B-13 §2.4),
   НЕ дублируются здесь. lead_id заполняется только через conversation.convert_to_lead (guard §6.4)';
```

Переиспользование существующих механизмов B-13 (не изобретаем третий, R-21 Т6):
- Сырые входящие сообщения — не новая таблица: `crm_tml` (добавить `'conversation_message'` в CHECK B-13 §2.4) + `crm_tml_targets(entity_type='crm.conversation')`.
- Очередь ревью дублей/неоднозначных матчей — `crm_relations` (`src_type='crm.conversation', dst_type='crm.contact', label='candidate_match'`), не отдельная таблица; мастер слияния (B-13 §9 п.6, v1.1) читает эти рёбра.
- Вертикали расширяют `crm.conversation`/`crm.lead` только через `fields:` манифеста (§5), не создают параллельных inbox-объектов на вертикаль.

### 6.3 State machine

```php
enum ConversationStatus: string {
    case Unassigned='unassigned'; case Assigned='assigned';
    case PendingReview='pending_review'; case Linked='linked';
    case Closed='closed'; case Spam='spam';
}
```

| Переход | from → to | Guard / Action |
|---|---|---|
| `conversation.route` | unassigned → assigned | action: назначение `assignee_id`/`team_id` по правилам роутинга (канал/команда) |
| `conversation.resolve_identity` | assigned → assigned (contact найден) / pending_review | **sync-resolver**: exact email/phone match по существующим GIN-индексам `crm_contacts_emails_ix`/`crm_contacts_phones_ix` (B-13 §2.2, без изменений) → `contact_id`+`match_confidence='exact'`; неоднозначно/нет — `status=pending_review` + `crm_relations(label='candidate_match')` для async fuzzy-дозматчинга (v1.1 «мастер слияния», B-13 §9 п.6) |
| `conversation.convert_to_lead` | assigned, pending_review → linked | guard: `contact_id IS NOT NULL` (сначала идентичность, потом квалификация — правило Front: «лид создаётся только на первое несопоставленное квалифицирующее сообщение»); action: создаёт/находит `crm_leads`(`status=open`), проставляет `crm_conversations.lead_id`. **Единственный путь появления `crm_leads`-записи из омниканального входа** — прямое создание `crm_deals` из conversation запрещено (safety-инвариант, аналог B-13 §7.3 «единственный путь записи status») |
| `conversation.close` / `conversation.mark_spam` | любой → closed/spam | ручное или AI-триаж (естественное 9-е применение агентного слоя B-13 §5.7, не зафиксировано отдельным агентом в v1) |
| `lead.convert` | без изменений (B-13 §3.1/§3.3) | open → converted — существующий `LeadConverter` |

Итоговый инвариант: **raw message → `crm_conversations` → `crm_leads` → `crm_deals`**, ни один слой не совмещает routing с qualification.

### 6.4 Дедуп — конкретное правило

- **Sync** (request-path): только точные нормализованные ключи (email/phone exact-match, существующие GIN-индексы B-13 §2.2). Однозначный match → авто-attach.
- **Async** (v1.1): fuzzy-резолвер (имя+телефон, транслитерация RU↔EN) → candidate edges с confidence, никогда auto-merge — очередь ревью оператора. v1 может ограничиться заглушкой «нет exact-match → всегда `pending_review`», не блокирует запуск omni-inbox.
- Явный инвариант: **auto-merge по fuzzy-совпадению запрещён** (индустриальное правило, R-21 §2.5) — зафиксировать при спецификации мастера слияния v1.1.

### 6.5 Edition

`crm_conversations` — pro+ фича (§2); base-издание работает без буфера: формы создают `crm_leads`/`crm_deals` напрямую, как в текущем v1 B-13 (меньше каналов на base — риск дублей из failure modes R-21 §2.6 ниже).

## 7. Analytics / read-model слой

Восемь read-моделей: пять покрывают операционную аналитику воронки/активностей/задач (base+ для просмотра, детализация по edition), три — revenue motions из R-20 (§4). Общее архитектурное правило (R-20 §2.3, §4.2): **read-model — производный индекс над транзакционными таблицами, не источник правды**; первичные данные (`crm_deals`, `crm_stage_history`, `crm_activities`, `crm_tml`) остаются каноном.

| Read-модель | Ключевые колонки | Источник | Refresh |
|---|---|---|---|
| `crm_deal_metrics_daily` | `workspace_id, pipeline_id, day, deals_created, deals_won, deals_lost, amount_won_sum, amount_lost_sum, avg_cycle_days` | `crm_deals`+`crm_stage_history` | **batch, nightly** (календарный агрегат по дню — не событие) |
| `crm_owner_pipeline_daily` | `workspace_id, owner_id, day, open_count, open_amount_sum, stalled_count (rotten_days превышен)` | `crm_deals`+`crm_stages.settings.rotten_days` | **batch, nightly** |
| `crm_activity_rollups` | `workspace_id, user_id, day, calls_done, emails_done, meetings_done, avg_response_time_sec` | `crm_activities` | **batch, nightly** (агрегат по дню; при высокой потребности в near-real-time — v1.1 event-driven инкремент) |
| `crm_conversion_funnel_daily` | `workspace_id, pipeline_id, day, from_stage_id, to_stage_id, entered_count, converted_count, conversion_rate` | `crm_stage_history` | **batch, nightly** |
| `crm_rotten_queue` | `workspace_id, entity_type, entity_id, stage_id, stage_entered_at, rotten_days_threshold, days_over` | `crm_deals`/`crm_leads`+`crm_stages.settings` | **event-driven триггер + периодический sweep**: пересчитывается на `crm.deal.stage_changed` (сброс отсчёта) и лёгким cron (ежечасно) — единственная из восьми, где чистый nightly-batch недостаточен (используется reminder-агентом, B-13 §5.7, для проактивных напоминаний внутри дня, не только наутро) |
| `crm_forecast_rollup` | см. §4.2 | `crm_deals`+`crm_stages` | **event-driven**: `crm.deal.stage_changed`/`.won`/`.lost` → `REFRESH MATERIALIZED VIEW CONCURRENTLY` |
| `crm_account_health` | см. §4.3 | `crm_activities`/`crm_tml`+billing (`com_payers`, R-17) | **batch, nightly** (append-only snapshot) |
| `crm_health_overrides` | см. §4.3 | ручной ввод CSM | не read-model — транзакционная таблица override-слоя, персистентна между пересчётами |

Правило разделения (R-20 §2.2/§2.3, обобщено на всю таблицу): **событие меняет что-то мгновенно значимое для решения «сейчас»** (стадия сделки → forecast; момент застревания → rotten queue) — event-driven refresh; **всё, что по определению агрегат за календарный период** (day/night rollups для дашбордов) — nightly batch, дешевле cron на среднем объёме и не требует queued listener на каждую активность.

Edition: базовые операционные пять доступны на всех изданиях в объёме собственных данных пользователя (base: свои сделки, pro: команда через scope, enterprise: полная орг-иерархия через `sys_departments`); `crm_forecast_rollup` — pro+ (командная аналитика, Roadmap P3); `crm_account_health`/`crm_health_overrides` — enterprise (§2).

## 8. Открытые вопросы (перенесены из R-20/R-21, к решению на синтезе)

1. **Порог v1→v1.1 quote-to-cash** (R-20 §5.1): recurring/ramped pricing / конкретное число SKU на сделку / необходимость rev-rec — зафиксировать числом на синтезе, не оставлять неявным (урок MonetizeNow). В §4.4 стоит заглушка «>25 SKU», не решение.
2. **Primary quote per deal** (R-20 §5.2): явная колонка `crm_deals.primary_quote_doc_id` (принято в §4.1) vs `crm_relations(label='primary_quote')` — зафиксировано в пользу колонки (hot-path, правило границы R-02 §4.7), подтвердить на архитектурном ревью.
3. **`crm_forecast_rollup` — MATERIALIZED VIEW vs append-only снапшот-таблица** (R-20 §5.3): v1 — обычный MV достаточен; отдельная снапшот-таблица (Salesforce Pipeline Inspection «changes since» паттерн для трендовой Moved In/Out аналитики) — v1.1 вопрос, требует решения при появлении спроса на трендовые отчёты.
4. **Account health pillars за пределами v1** (R-20 §5.4): support/sentiment зависят от доменов, которых нет в программе Flex (support-тикеты, NPS-опросник) — решить на уровне B-01 (явный будущий домен или интеграция с внешним CS-инструментом), не в B-13/B-24.
5. **Manager forecast adjustments** (R-20 §5.5): персистентный override поверх ролловера зависит от дизайна иерархии `sys_departments` (имя канона закрыто D-002 п.3, сам parent/child-дизайн ещё не специфицирован в B-10/B-11) — блокирующая зависимость, если понадобится раньше v2.
6. **Auto-attach приоритет каналов** (R-21 §5.1): правило приоритета email > phone > ИНН (B2B) при разрешении дублей не проработано — отдельный ADR при спецификации мастера слияния (B-13 §9 п.6).
7. **AI-триаж входящих** (R-21 §5.2): авто-классификация intent (sales/support/spam) как 9-й режим агента FlexCRM — пересечение с R-06 Т2, не зафиксировано ни там, ни здесь; естественное расширение `conversation.route`/`conversation.mark_spam`.
8. **`crm_conversations.team_id` → `sys_departments`** (R-21 §5.3): та же зависимость, что и п.5 — иерархия/manager-отношения `sys_departments` ещё не спроектированы (имя уже канон, D-002 п.3), общая блокирующая зависимость для §4.2 и §6.2.
9. **Feature-flag на `crm_conversations`** (R-21 §5.4): нужен ли per-workspace флаг (аналог `crm.lead_mode`) для аккаунтов без омниканальности — вероятно да, консистентно с D16; технически реализуется через `licensed_features`-реестр B-22 (см. §2), отдельного флага не заводим.
