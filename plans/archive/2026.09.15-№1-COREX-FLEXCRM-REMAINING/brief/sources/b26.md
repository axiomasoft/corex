## 1. Границы и состав

**Что это.** Механика операционного жизненного цикла таблиц **внутри тенантской БД** (D1: физическая БД на аккаунт) — партиционирование, архивация, реиндекс, интеграционные свипы, health-check. Это **не** про схему конкретного домена (та живёт в B-13/B-14/B-17) и **не** про DDL кастомных полей (`fld_ddl_ops`, R-13/B-15) — это общий контракт, который **любой** append-only/высоконагруженный модуль подключает без переизобретения.

**Что не это.**
- Не DDL кастомных полей пользователя (R-13: `fld_ddl_ops`, статусная машина `pending→applying→done`, CIC-протокол) — там источник схемы = реестр `fld_*`; здесь источник схемы = сам модуль (crm/cms/commerce), а предмет — эксплуатация уже существующих append-only таблиц.
- Не инфраструктура пулинга/ячеек (R-15: PgBouncer, cluster_id, 500-2000 БД на ячейку) — B-26 **переиспользует** `cluster_id` как throttling-ключ (§4), не определяет его.
- Не бизнес-логика ретеншна конкретного домена (сколько хранить `crm_tml` — решает B-13; B-26 даёт **механизм**, которым любой ретеншн исполняется).

**Потребители (product-agnostic, оба уровня Flex):** FlexCRM (`crm_tml` — полиморфная timeline, `crm_stage_history` — append-only лог переходов воронки), FlexCMS (`cms_entry_versions` — ревизии контента, `cms_form_deliveries` — лог доставки форм), в перспективе FlexStore (`com_stock_moves`, `com_order_log` — уже спроектированы в B-14 §2.6/§2.9 как append-only, но операционализация партиционирования/архивации для них — тоже через этот блюпринт, не заново).

## 2. Классификация таблиц по профилю мутации

Любая таблица тенантской БД относится ровно к одному классу; класс определяет, какие операционные контракты (§3-§7) к ней применимы. Классификация — не про домен (CRM/CMS/Commerce), а про паттерн записи/чтения.

| Класс | Профиль | Применимые контракты B-26 | Примеры (существующие блюпринты) |
|---|---|---|---|
| **reference** | Редко меняется, читается часто, обычно маленькая (десятки-сотни строк) | Ничего из B-26 не требуется; обычный `pg_dump`/backup хватает | `crm_pipelines`, `crm_stages`, `crm_sources`, `crm_lost_reasons` (B-13); `cms_blueprints`, `cms_sites` (B-17) |
| **transactional** | Регулярный CRUD, updated_at меняется, размер растёт линейно с бизнесом, но не «событие на каждый клик» | Health-check (§7) — bloat/autovacuum релевантны; партиционирование обычно не нужно | `crm_deals`, `crm_contacts` (B-13); `cms_entries` (B-17); `com_orders`, `com_customers` (B-14) |
| **append-only** | INSERT-only (или почти), UUIDv7 PK = хронология, растёт неограниченно, редко читается целиком (окно времени/entity) — **основной предмет этого блюпринта** | Партиционирование (§3), архивация (§4), health-check (§7) | `crm_tml`/`crm_stage_history` (B-13); `cms_entry_versions`/`cms_form_deliveries` (B-17); `com_stock_moves`/`com_order_log` (B-14) |
| **projection** | Материализованная read-модель, пересчитывается детерминированно из append-only/transactional источника, **свой** цикл обновления (dirty-флаг + батч-джоб), не подлежит партиционированию/архивации сама по себе | Health-check применим (staleness метрика — вне §7, домен сам решает); архивация НЕ применяется (можно пересобрать из источника) | `com_price_index`, `com_stock_levels` (B-14, dirty-флаг + пересчёт); аналог для CRM — гипотетический `crm_forecast_rollup` (пока не спроектирован ни в одном блюпринте — если появится, обновление по dirty-флагу, не через архивацию B-26) |
| **installation-metadata** | Конфигурация модуля/тенанта, редко меняется, критична для интерпретации остальных данных | Health-check не требуется; обязателен в PITR-снапшоте (не подлежит отдельному бэкапу) | `sys_feature_flags`, `sys_settings` (B-10); `fld_schema_state` (R-13/B-15) |
| **runtime-ephemeral** | Кеши/сессии/временные локи, переживаемая потеря допустима | Вне PITR-контракта, вне §3-§7 целиком (не персистентный источник истины) | Redis-структуры (вне PG, упомянуты для полноты классификации — таблиц в PG обычно нет) |

**Правило:** append-only — единственный класс, где партиционирование+архивация **обязательны** (не опционально) при определённом объёме (§3). Projection **никогда** не архивируется тем же механизмом (§4) — она пересобирается, а не хранит историю.

## 3. Партиционирование append-only таблиц: политика графации

Механизм — `pg_partman` внутри тенантской БД (R-23 §2.1). Для **новых** append-only-таблиц (заводимых после принятия этого блюпринта) политика по умолчанию — партиционирование включается на этапе провижининга таблицы, если модуль декларирует её как append-only, а не «графация по достижении порога» — так дешевле, чем мигрировать уже выросшую таблицу.

**Исключение (grandfathering):** `crm_tml` уже спроектирована в B-13 (принято раньше этого блюпринта, исполнено в реальный vault на Этапе 6) с явной opt-in-графацией — v1 одна таблица, переход на помесячные партиции `pg_partman` при **>20M строк аккаунта** (`Database_Schema (FlexCRM).md`, комментарий к таблице, AC-2). Это решение не пересматривается задним числом: B-26 не навязывает provision-time для уже закоммиченных доменных решений, только для новых append-only-таблиц, заводимых начиная с этого блюпринта. Модуль явно декларирует режим в манифесте провижининга: `partition_mode: provision_time | threshold_triggered(rows_per_account)` — оба режима используют один и тот же механизм ниже (`create_parent`/`retention`), различается только момент вызова `create_parent`.

```sql
SELECT partman.create_parent(
  p_parent_table => 'public.crm_tml',
  p_control      => 'happens_at',        -- или created_at для таблиц без "случилось в" семантики
  p_interval     => 'monthly',
  p_premake      => 3
);
UPDATE partman.part_config
SET retention = '18 months',             -- домен решает срок (B-13/B-17), механизм — единый
    retention_keep_table = true,         -- партиция детачится, не дропается сразу — archive-job §4 решает дальше
    infinite_time_partitions = true
WHERE parent_table = 'public.crm_tml';
```

**Выбор интервала (monthly vs weekly)** — единственная переменная графации, объёмо-зависимая:

| Ожидаемый объём таблицы (строк/месяц на тенант) | Интервал партиции |
|---|---|
| < ~500K | monthly (дефолт) |
| ≥ ~500K | weekly |

Порог **эвристический** [UNVERIFIED — R-23 не даёт конкретного числа, только рекомендует range-by-time monthly/weekly без порога перехода; цифра здесь — рабочая оценка по аналогии с общей практикой partman-based ротации, требует калибровки на PoC (§9)]. Конкретное значение для `crm_tml`/`cms_entry_versions` — задача домена (B-13/B-17) при заведении таблицы через провижининг-конфиг модуля, не хардкод в B-26.

`run_maintenance_proc()` вызывается `pg_cron` **внутри самой тенантской БД** (не из root) — совпадает с принципом «состояние — там же, где данные» (R-13 §3: бэкап/PITR тащит партиции атомарно вместе с реестром).

Партиционирование **не** применяется к projection-таблицам (§2) — они не растут неограниченно тем же образом; если проекция логически большая (напр. `com_price_index` на крупном каталоге), её масштабирование — вопрос домена (переиндексация/шардинг по другой оси), не предмет B-26.

## 4. Архивация/экспорт: обязательный, не опциональный механизм

`DETACH PARTITION CONCURRENTLY` → Parquet → `archive_manifest` → `DROP TABLE` — единственный разрешённый путь освобождения места на append-only партициях; ручной `DROP PARTITION` без манифеста запрещён (то же самое действие без аудита превращает архивацию в необратимую потерю данных).

```sql
-- шаг 1: без ACCESS EXCLUSIVE на родителя (PG14+), безопасно днём
ALTER TABLE crm_tml DETACH PARTITION crm_tml_2025_01 CONCURRENTLY;
```

`DETACH ... CONCURRENTLY` — двухфазная операция: короткий ACCESS EXCLUSIVE лок только на партицию (не на родителя) для пометки отсоединяемой, затем ожидание снятия конфликтующих локов и завершение без блокировки чтений/записей родителя; не может идти внутри транзакции с другим DDL.

```
шаг 2: экспорт standalone-таблицы в Parquet (DuckDB/pg_parquet/COPY TO Parquet) на object storage
шаг 3: INSERT INTO archive_manifest (см. схему ниже)
шаг 4: DROP TABLE crm_tml_2025_01;   -- только после подтверждённой записи манифеста
```

`archive_manifest` — обязательная таблица **в каждой тенантской БД** (не в root — тот же принцип атомарности PITR: без неё детач не оставляет доказательства, что произошло с данными и где их искать):

```sql
CREATE TABLE archive_manifest (
  id              uuid PRIMARY KEY,             -- UUIDv7
  table_name      text NOT NULL,                -- 'crm_tml' | 'cms_entry_versions' | ...
  partition_name  text NOT NULL,                -- 'crm_tml_2025_01'
  ts_range        tstzrange NOT NULL,
  row_count       bigint NOT NULL,
  size_bytes      bigint NOT NULL,
  location        text NOT NULL,                -- object storage URI (Parquet)
  archived_at     timestamptz NOT NULL DEFAULT now(),
  retention_until timestamptz,                  -- NULL = хранить бессрочно (регуляторный/бизнес-повод — решает домен)
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX archive_manifest_table_ix ON archive_manifest (table_name, ts_range);
```

**Порядок шагов 2→3→4 — инвариант, не последовательность по умолчанию**: DROP разрешён только после успешного commit шага 3; провал шага 2 (экспорт) или 3 (запись манифеста) должен блокировать шаг 4 — иначе либо orphaned Parquet без учёта в manifest, либо дропнутые данные без экспорта. Реализация — job с явным чекпоинтом между шагами (не одна транзакция: экспорт в object storage не транзакционен относительно PG).

## 5. Реиндекс/ребаланс как первоклассная ops-команда

PostgreSQL не имеет встроенного per-tenant throttling для DDL/maintenance — `REINDEX CONCURRENTLY` не создаёт длинный AEL, но потребляет CPU/IO без ограничения, и никакого resource governor на уровне БД нет. Обвязка — обязательно на уровне приложения.

### 5.1 Реестр `ops_maintenance_jobs` (root БД)

Живёт в **root**, не в тенантской БД — в отличие от `fld_ddl_ops` (R-13, тенантская БД, т.к. там состояние — часть схемы конкретного тенанта). Здесь состояние — fleet-уровня (какие тенанты в какой волне, throttling per cluster):

```sql
-- root БД
CREATE TABLE ops_maintenance_jobs (
  id            uuid PRIMARY KEY,              -- UUIDv7
  account_id    uuid NOT NULL,
  op_type       text NOT NULL CHECK (op_type IN
                ('reindex_concurrently','partman_run_maintenance',
                 'archive_partition','integrity_sweep')),
  target        jsonb NOT NULL,                -- {table, index} | {relation_config}
  wave          text NOT NULL CHECK (wave IN ('canary','wave_1','wave_2','wave_3')),
  not_before    timestamptz NOT NULL,           -- окно с джиттером
  status        text NOT NULL DEFAULT 'pending' CHECK (status IN
                ('pending','running','done','failed','skipped')),
  cluster_id    uuid NOT NULL,                  -- throttling-бакет — ячейка (R-15), не тенант
  attempts      smallint NOT NULL DEFAULT 0,
  last_error    jsonb,
  created_at    timestamptz NOT NULL DEFAULT now(),
  started_at    timestamptz,
  finished_at   timestamptz,
  updated_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ops_maintenance_jobs_pending_ix ON ops_maintenance_jobs (cluster_id, wave, not_before)
  WHERE status IN ('pending','running');
```

Явный ops-API (`POST /internal/tenants/{id}/ops/reindex`, `.../ops/run-partman`, `.../ops/integrity-sweep`) — не только cron: SRE/support ставят внеочередной прогон по алерту health-check (§7), обычный проход идёт волнами.

### 5.2 Fleet-scale scheduling policy

Прецедент «self-service reindex как явная tenant-facing операция у конкретного вендора (Shopify/Gusto)» **не подтверждён** в открытых источниках — паттерн (registry + orchestrator + maintenance agent) правдоподобен и совпадает с нашим op-log из R-13, но это архитектурный синтез, не задокументированный прецедент [UNVERIFIED, см. R-23 §2.3].

- **Волны**: `canary` (2-5 внутренних/пилотных тенантов) → `wave_1` (низкий риск/малый объём) → `wave_2` (средний) → `wave_3` (крупные/high-value). Переход к следующей волне только после soak-периода без роста error-rate/lock-wait на предыдущей.
- **Джиттер**: `not_before = window_start + uniform(0, window_duration)` внутри maintenance-окна — не «все в 03:00».
- **Throttling per `cluster_id` (ячейка R-15), не per tenant**: конкурентный ресурс — общий CPU/IO физического PG-кластера, не тенант сам по себе. `max_concurrent_maintenance_jobs_per_cluster` — основной рычаг (стартовое значение — PoC, §9).
- **Health-watcher с авто-паузой**: превышение порога CPU/lock-wait/replication-lag на кластере → оркестратор перестаёт брать новые job'ы для этого кластера; начатые донашиваются; resume ручной/авто после нормализации.
- **Приоритет бизнес-трафика**: maintenance-джобы никогда не конкурируют с обычными операциями за приоритет очереди — backpressure всегда в сторону maintenance.

Всё в этом подразделе, кроме факта отсутствия PG resource governor (§5, подтверждено документацией), — синтез общей практики per источникам R-23, не воспроизведённый конкретный кейс; параметры волн/throttling — предмет PoC (§9), не финальные числа.

## 6. Data-repair команды для орфан-целей/связей

Паттерн для полиморфных связей без реальных FK (`*_targets`/`owner_type+owner_id`) — например `crm_tml_targets(entity_type, entity_id, tml_id)` (B-13), `com_addresses(owner_type, owner_id)` (B-14): БД не может проверить целостность декларативно, FK требует одного конкретного родителя.

### 6.1 Схема

```sql
-- root или общий конфиг-модуль (метаданные связей, не тенантские данные)
CREATE TABLE integrity_sweep_relations (
  id                 smallint PRIMARY KEY,
  child_table        text NOT NULL,             -- 'crm_tml_targets' | 'com_addresses'
  child_pk           text NOT NULL DEFAULT 'id',
  target_type_value  text NOT NULL,              -- 'deal' | 'com.customer'
  parent_table       text NOT NULL,              -- 'crm_deals' | 'com_customers'
  parent_pk          text NOT NULL DEFAULT 'id',
  soft_delete_column text                        -- 'deleted_at', если у parent есть мягкое удаление
);

-- в тенантской БД, per relation, батчем 1000
CREATE TABLE integrity_sweep_findings (
  id           uuid PRIMARY KEY,                 -- UUIDv7
  relation_id  smallint NOT NULL REFERENCES integrity_sweep_relations (id),
  child_id     uuid NOT NULL,
  found_at     timestamptz NOT NULL DEFAULT now(),
  class        text NOT NULL CHECK (class IN ('hard_orphan','soft_deleted_parent')),
  action       text NOT NULL DEFAULT 'pending_review' CHECK (action IN
               ('pending_review','auto_fixed','manual_fixed','ignored')),
  reviewed_by  jsonb,
  resolved_at  timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now()
);
```

### 6.2 Правила

1. **Report-first по умолчанию.** Находки пишутся в `integrity_sweep_findings` со статусом `pending_review`; ничего не удаляется автоматически, кроме единственного исключения ниже.
2. **Единственный класс авто-фикса** — `soft_deleted_parent`: родитель существует, но `soft_delete_column IS NOT NULL` (мягко удалён) → каскадное мягкое удаление/деактивация ребёнка допустимо автоматически (низкий риск, обратимо).
3. **`hard_orphan`** (родителя нет вообще, даже мягко-удалённого) — только ручной review; авто-delete запрещён по умолчанию — данные могли осиротеть из-за бага в приложении, слепое удаление опасно.
4. **Батч 1000 строк**, `LEFT JOIN + LIMIT`, цикл до 0 найденных на relation, не держит долгих транзакций/локов:

```sql
WITH orphan_batch AS (
  SELECT c.id FROM crm_tml_targets c
  LEFT JOIN crm_deals p ON c.entity_id = p.id
  WHERE c.entity_type = 'deal' AND p.id IS NULL
  ORDER BY c.id LIMIT 1000
)
SELECT id FROM orphan_batch;
```
5. **Индексы обязательны** — `(target_type/entity_type, target_id/entity_id)` на каждой полиморфной дочерней таблице, иначе свип превращается в full scan на каждую итерацию.
6. **Расписание**: nightly per relation per tenant, распределено по волнам §5.2, тот же throttling-бакет per cluster (партман/реиндекс/свип конкурируют за общий `max_concurrent_maintenance_jobs_per_cluster`).
7. **Метрика для health-check** (кандидат в §7 v2): `count(integrity_sweep_findings WHERE action='pending_review' AND found_at > now() - interval '7 days')` — рост очереди ревью сигнализирует баг в приложении, не «грязные данные».

## 7. Tenant health checks

Шесть сигналов, все читаемы из системных каталогов + `pgstattuple`, без сторонних агентов на каждой из тысяч тенантских БД:

| # | Метрика | Источник | Warn | Critical | Прецедент/статус |
|---|---|---|---|---|---|
| 1 | Unused indexes | `pg_stat_user_indexes.idx_scan=0 AND NOT indisunique`, с учётом `stats_reset` (`pg_stat_database`) | ≥30 дней с нулевым scan | размер >1GB и unused ≥90 дней → кандидат на drop | источник подтверждён (jmorano/postgres.ai) |
| 2 | Index bloat (в т.ч. GIN) | `pgstattuple(index_oid).dead_tuple_percent` | ≥20% | ≥40% | источник подтверждён (`pgstattuple`), гонять раз в сутки/неделю — дорогой I/O-скан |
| 3 | Table bloat | `pgstattuple(table_oid).dead_tuple_percent` | ≥20-30% | ≥40-50% | **[UNVERIFIED — эвристика отрасли, не спецификация PG, порог workload-специфичен]** |
| 4 | Autovacuum lag | `n_dead_tup/(n_live_tup+n_dead_tup)` из `pg_stat_all_tables`; либо `last_autovacuum` старше N часов при высоком `n_tup_upd` | ≥0.3 | ≥0.5 или lag > N часов | общий совет по autovacuum-тюнингу, не жёсткий стандарт |
| 5 | Pending/долгий DDL | `pg_stat_activity` (ALTER активен дольше `statement_timeout`) + `ops_maintenance_jobs`/`fld_ddl_ops` (R-13) статус age | age >5 мин без прогресса | age >15 мин | внутренний, по аналогии с R-13 §3.3/§3.6 — смежно, не дублирует физлимит-колонок метрику R-13 |
| 6 | Физлимит колонок (ссылка на R-13 §3.6, не дублировать) | `count(pg_attribute) incl. attisdropped` | 1000 | 1600 (жёсткий лимит PG) | R-13 |

**Инструмент**: не разворачивать PgHero/pganalyze-collector на тысячи тенантских БД как UI-дашборд на каждую — прогонять SQL из таблицы выше **fleet-джобом** (расписание §5.2), писать снапшоты в root:

```sql
CREATE TABLE tenant_health_snapshots (
  id          uuid PRIMARY KEY,
  account_id  uuid NOT NULL,
  metric      text NOT NULL,          -- 'unused_indexes' | 'index_bloat' | ... (см. таблицу выше)
  value       numeric NOT NULL,
  severity    text NOT NULL CHECK (severity IN ('ok','warn','critical')),
  checked_at  timestamptz NOT NULL DEFAULT now(),
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX tenant_health_snapshots_account_ix ON tenant_health_snapshots (account_id, metric, checked_at DESC);
```

PgHero/pganalyze — годный референс формулировок запросов и локальный dev-инструмент для ручного дебага одной БД, не fleet-решение для нашего масштаба.

## 9. Открытые вопросы

1. **Точные параметры волн** (размер `wave_1/2/3`, длительность soak-периода, `max_concurrent_maintenance_jobs_per_cluster`) — зависят от реального распределения тенантов по размеру; зафиксировать после PoC на стенде (можно объединить с PoC R-13 §3.8 в один общий maintenance-PoC).
2. **Порог графации monthly→weekly партиционирования** (§3) — рабочая эвристика (~500K строк/месяц), не подтверждена источником, требует калибровки на реальном профиле `crm_tml`/`com_stock_moves`.
3. **Единый оркестратор для трёх типов fleet-джобов** (partman maintenance, reindex, integrity sweep) — один `ops_maintenance_jobs` с `op_type` (как здесь) или три отдельные очереди с общим throttling-слоем: решить вместе с деталями Laravel-джоб-мидлвари (`WithoutOverlapping`/rate limiting, по аналогии с R-13 §3.2 unique job per account).
4. **Инструмент bloat-мониторинга** (PgHero vs pganalyze collector vs самописный SQL-раннер) — деталь реализации, не блокирует дизайн §7; таблица метрик и пороги в B-26 не зависят от выбора инструмента.
5. **Прецедент self-service reindex у реального вендора масштаба (Shopify/Gusto и т.п.)** — не подтверждён источниками (R-23 §2.3); если появится подтверждение при дальнейшем ресёрче — обновить §5.2, пока трактовать как архитектурный синтез, не заимствованный факт.
6. **Проекции с собственным жизненным циклом крупного объёма** (гипотетический `crm_forecast_rollup` уровня B-14 `com_price_index`) — если появится в CRM/CMS, требует отдельного решения по staleness/пересборке; B-26 намеренно не архивирует projection-класс (§2).
