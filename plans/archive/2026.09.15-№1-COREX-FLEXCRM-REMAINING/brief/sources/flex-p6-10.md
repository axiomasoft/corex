### P6.10 — corex/crm + corex/tasks (ядро сущностей B-13 §2) → GREEN

> **Дельта D37:** дополнительно required ADR-002 §5–6 и P9.4: Tasks как corex-module/lifecycle; UUIDv7 taskable storage; DTO/EntityReference вместо чужой Model на публичной границе; validation account/process/stage; report composition proof. Эти требования реализуются у владельца CoreX до P9.4. До-D29 имя corex/crm читать как flex/crm; не создавать дубликат Tasks в app.

**Intent:** Довести пакеты `corex/crm` (`crm_*`: лиды/сделки/контакты/компании/воронки/активности) и `corex/tasks` (`tsk_*`: задачи, проекты, чек-листы) из текущих каркасов до спеки B-13 §2 — новый план в репе corex (напр. `COREX-CRM`), exec до GREEN + теги.
**Why:** Ядро предметной области продукта: на `crm_*`/`tsk_*` стоят все модули волны (B-27 — аддитивная дельта `tsk_`; B-29 — пара «активность↔событие»; B-30 — сегменты по сделкам; B-31 — воронки/StageableRegistry; B-36 — read-model JOIN). RAG:✅ DB_SCHEMA §2 (`crm_` ~24 табл. — corex/crm; `tsk_` 8 — corex/tasks) + факт каркасов в репе 2026-07-13.
**Scope Included:** новый план в репе corex; дельта существующего кода `packages/crm`, `packages/tasks` до B-13 §2 (не переписывание с нуля); DDL `crm_`/`tsk_` по DB_SCHEMA; StageableRegistry (воронки-стадии как контракт); exec до GREEN + теги.
**Scope Excluded:** app-слой FlexCRM (продуктовая композиция, вертикали, UI — P6.18); дельта B-27 (P6.11); commerce (P6.19); agentic-тулзы CRM (P6.15/P6.22 — карты §7).
**Inputs:** B-13 §2 (сущности) + §5.4 (вертикали — только контракт) · B-24 (продуктовая архитектура — граница пакет↔app) · DB_SCHEMA (`crm_`/`tsk_`, FROZEN) · текущий код `packages/crm`, `packages/tasks`.
**Files:** `~/projects/packages/corex/packages/{crm,tasks}/**` + новый план `corex/plans/<COREX-CRM>/**` · Status Board этого файла.
**Required Reads:** 1) `05-Projects/01-Products/FlexCRM/plans/FLEX-2/findings/P6-implementation-map.md` 2) `05-Projects/01-Products/FlexCRM/plans/flex/30_blueprints/B-13_crm.md` (§2 сущности, §2.5 задачи) 3) `05-Projects/01-Products/FlexCRM/plans/flex/30_blueprints/B-24_flexcrm-product-architecture.md` (граница OSS-пакет ↔ проприетарный app) 4) `05-Projects/01-Products/FlexCRM/plans/flex/60_contracts/DB_SCHEMA.md` (`crm_`, `tsk_`)
**Implementation Rules:** предусловия — P6.3, P6.4 закрыты (модули + tenancy/RBAC), P6.1 закрыт (контракт). Существующий код `corex/crm`/`corex/tasks` — считаем ДЕЛЬТУ к спеке, не переписываем (принцип roadmap «дельта, не переписывание»). Граница «что в пакете, что в проприетарном app» берётся из B-24, не изобретается. Права — через `corex/auth` ScopeResolver (не своя проверка доступа). **Дополнено P8.6 (C-99b §4.8 → Q93):** `corex/crm` переименовывается в `flex/crm` (D29, L2 — тематический модуль); расщепление `corex/tasks`/`flex/tasks` (L1-примитивы / L2-модуль, D29, B-38 §2.1 сноска ²) — на scaffold-item'е этого расщепления, НЕ здесь; до расщепления владелец префикса `tsk_` един.
**Code Guidance:** ДЕЛЕГИРОВАНИЕ + package-дисциплина. Протокол: cwd = `~/projects/packages/corex`, `/task:plan-design <COREX-CRM>` (фазы: crm-сущности → tasks-ядро → StageableRegistry) → exec phase-first → audit GREEN → теги. Обязательно: сначала инвентарь существующего кода (что уже реализовано в каркасах), потом дельта — item «переписать заново» = дефект. Полиморфные связи — через morph-map модульной системы (не строковые классы в БД). Запрещено: row-level tenancy-хаки (изоляция — DB-per-account, B-11); своя система прав; DDL мимо FROZEN-контракта.
**Validation:** `task:plan-audit <COREX-CRM>` = GREEN; DDL `crm_`/`tsk_` совпадает с DB_SCHEMA поколоночно; composer-гейт зелёный; теги `corex/crm`/`corex/tasks`; тест RBAC-скоупа на сделках (менеджер видит только свои) зелёный.
**Deliverables:** `corex/crm` + `corex/tasks` соответствуют B-13 §2 + план закрыт + теги + Status Board.
