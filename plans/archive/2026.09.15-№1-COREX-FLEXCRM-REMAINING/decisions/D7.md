## Decision

P2.1 qualified P1 intake → P2.2 identity/auth/wire proposals и P2.3 generic exact contract proposals
→ P2.4 versioned local catalogue/12-input seal/precise protected request set. Все 52 R/365 parents,
A01–A09 и ownership/gates сохранены. Catalogue format p2-contract-catalogue/1 не новый library API.
Execution all four frontier/high gpt-5.6-sol: семантическая квалификация/открытые contract choices,
точные BC/profile/type constraints и межфазовая согласованность требуют frontier; Review light
означает scoped semantic self-check and structural gates, **не** independent phase audit consent.
P2.2/P2.3 recommended shared batch, ready subsets допустимы. P2.1 separate producer baseline;
P2.4 separate seal consumes both proposals after финальных bytes. Child agents не назначены.

P2.3 читает immutable specs полного дизайна P3–P8 до исполнения, не их produced runtime:
обратного execution edge нет. Whole-plan-first D4 сохраняется. Exact new runtime signatures/files
выбираются owning later phase design, P2.3 сверяет их с actual P1 inventory и emits reviewable bytes.
Material qualification conflict требует affected design/finish revision до dependent implementation.

Local P2 acceptance означает полный согласованный catalogue с exact **proposals**, а не grant.
Actual accepted-contract change всё ещё только с major owner receipt по AGENTS; schema/source/
private/profile/release/live branch — отдельная scoped authority. P3 membership adoption ждёт
accepted target/profile для affected subset; P10 отвечает effective deployment/all DI/AP.
Independent pure/headless/intl/recurrence rows не ждут чужой production deployment.

## Alternatives

Один giant API item смешивает qualification, auth/profile и headless surfaces с gate seal.
По item/interface на каждый R создаёт лишние ports и повторяет source reads. Четыре bounded
carriers позволяют параллельный по DAG semantic work без child agents и единую финальную проверку.
Переизобрести storage/tenancy/auth/API/registry или categorical external placement search/notifications
отвергнуто локальной doctrine: минимальная недостаточность и non-CRM scenario решают конкретную delta.
Новый HTTP error format/CloudEvents bus не выбран: optional wire mapping только при exact need.

**Consequences:** Только P2 specs/routing/design evidence, D6/D7 и общие plan policy/integrated views; narrowly corrected P1→P2.1 successor pointers
меняются. Product execution Not started; P1 outputs не созданы ради дизайна, P3–P11 остаются skeleton.
Общий finish pending, Next continuation design P3 в отдельном routed root; automatic execution нет.
